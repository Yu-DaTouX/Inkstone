## 1. 门禁三组对照（确定性、不联网、不花钱）

```bash
node scripts/hook-probe.mjs workmode           # clarify + 写文件的命令
node scripts/hook-probe.mjs workmode-standard  # standard + 同一条命令（对照）
node scripts/hook-probe.mjs workmode-allow     # clarify + \`yan goal status\`
```

实测（`--tools bash,read,write,edit` 起手，故意多给写工具）：

| 模式 | `getActiveTools` 变化 | 假 provider 收到的工具表 | 工具副作用 | 结果 |
|---|---|---|---|---|
| `workmode`（clarify） | `[bash,read,write,edit]` → `[bash,read]` | `["bash","read"]` | marker **不存在** | `Tool execution was blocked` |
| `workmode-standard` | 不变 | `["bash","read","write","edit"]` | marker **存在** | 正常执行 |
| `workmode-allow`（clarify + `yan goal status`） | → `[bash,read]` | `["bash","read"]` | 命令真的跑到 CLI | `{"ok":false,"error":"identity_mismatch"}` |

三点值得记下来：

1. **工具表的变化会体现在真正发出去的请求里** —— 不是「扩展内部改了改」。
   所以门禁是硬门禁，不是提示词。
2. **对照组必须存在**：`workmode-standard` 里同一条命令真的写了文件，
   证明「clarify 组没写文件」不是命令本身坏了。
3. **bash 必须留一条缝**：就绪提交的通道是宿主 CLI，而敲 CLI 要用 bash。
   完全拿掉 bash → 澄清档永远提交不了；完全放开 → 等于没门禁。
   所以白名单是「**只接受 `yan goal status|ready|report` 这一种形状**，
   且整条命令不得含 shell 元字符」—— 是允许列表，不是对任意命令做只读判断。

## 2. 就绪转移端到端（`test:live -- goal`，cost 1）

探针只做两件事：把模式切到澄清档、把命令原样交给模型（内联参数 —— 澄清档不能写文件）。
其余全部是被验对象：

```
✓ 宿主侧已切到澄清档（{"mode":"clarify","revision":1}）
✓ 目标还没开始（planning / rev0）
✓ 模式自动切到标准（{"mode":"standard","revision":2}）
✓ 目标进入 executing / ✓ revision = 1（恰好推进一次）
✓ 出现目标状态工具卡 / 标签：["目标 · 砚内置"]
✓ bash 调用里含 yan goal ready
退出后：goals.json=executing(rev1)、transitions 只有一条（tr-probe-1）、
        五栏（含验收标准）完整、work-modes.json=standard(rev2)
```

这条链路里有**五段**只有真实运行才能验：bash → `yan` 启动器 → 环境变量身份注入 →
能力服务身份校验 → 宿主 goal 服务。任何一段断了，单测与假 provider 都看不见。

## 3. 单测覆盖（`scripts/test-goal.mjs`，66 条）

契约（五栏 / 置信度 / 未决问题 / 两种 revision 过期 / 完成要证据 / blocked 要原因 /
`stopped` 不许模型自报 / 已完成不许回退 / 同因两次强制 blocked / 换签名计数归零 / 脏值清洗）
与存储（幂等**先于**校验 / 重放不推进 revision / 提交返回前已落盘 / 多会话不串 /
脏 JSON 不抛 / 落盘失败**必须抛**且内存态回退）。

## 4. 跨轮续行（S3b）

**通道**：只有扩展 API 能发 `custom` 角色消息并触发回合 ——
`pi.sendMessage({customType,content,display},{triggerTurn:true})` 在空闲时走 `_runAgentPrompt`，
消息角色是 `custom` 而不是 `user`（RPC 面没有对应命令）。
`custom` 角色正是「**这不是用户说的话**」的机器可判形式（§4 的要求）。

**分工**：宿主写「待发续行」快照（`goal-resume/<runnerId>.json`，与转移**同一次落盘**）；
薄层 `resources/pi-extensions/goal-resume.js` 在回合空闲时把它变成一条真实回合。

**三道防护的落点**：

| 防护（§4） | 实现 |
|---|---|
| 唯一 `operationId` | 就是转移的 `transitionId`：一次转移一个续行 |
| 消费幂等 | 发之前先写 `goal-resume/<runnerId>.consumed.json`；崩溃后据此判断，**不盲发两次** |
| 先持久化再启动 | `commitReady` 返回时 resume 已经在磁盘上（同一次 `persist`） |
| 用户停止优先 | `yan:abort` 与 `yan:setWorkMode`（切成非标准档）都会 `clearResume` + 清快照 |

**实测时间线**（`test:live -- goal` 的扩展诊断日志，决定性证据）：

```
message_end(assistant, turnEnd=false)   ← 提交轮的 toolCall 消息
message_end(toolResult)
message_end(assistant, turnEnd=true)    ← 提交轮最终消息 → 调度二次确认
（1800ms）
check hasResume=true operationId=tr-probe-1
resume_sent operationId=tr-probe-1
message_end(role=custom)                ← 控制消息本身（不是 user）
```

退出后：会话文件里同时有 `yan-goal-resume` 与 `yan-goal-ready` 两类自定义条目；
`goal-resume/r1.consumed.json` 记下了 operationId。

**一个踩过的坑**：探针最初用顶层 `store.getState().isAgentRunning` 判空闲，
而它在 `session` 里 —— 读错字段会让「空闲」在第一次 `toolResult` 的空档就成立，
于是本轮在模型写下最后一句之前就被判定收尾，续行永远等不到机会（现象是日志停在 `toolResult`）。

## 5. 剩余限制（S3b 之后）

1. **控制消息在界面历史里看不到**：`session-reader` 只读 `type:"message"` 条目，
   把 `custom_message` 渲染成「砚 · 控制消息」卡片是后续小活（留痕在会话文件与模型上下文里）。
2. **目标级「停止目标」没有界面入口**：`GoalStore.stop()` 有实现与单测，
   但界面上没有「放弃目标」按钮（回合级的停止已接，只清续行、不标 stopped）。
3. **真实多轮模糊请求**：澄清档的逐步澄清（问 → 答 → 再问 → 就绪）没做成场景。
4. **`pendingMode`** 仍未用（与 S2 的限制同一条）。
5. 续行靠 `message_end` 近似「回合结束」（pi 没有 agent_end 钩子）—— 1.8s 二次确认是保险，
   不是精确同步。

## 1. 两个必须讲清的设计取舍

### 1.1 工具卡按**命令文本**判定，而不是让宿主关联 toolCallId

理想做法是宿主在处理 `tasks.apply` 时记下「ps 里那次 bash 调用的 id」，界面据此精确打标。
**做不到**：pi 的 bash 工具不把 toolCallId 传进子进程环境，宿主没有任何信道拿到它。

可选的两条路：

| 方案 | 结论 |
|---|---|
| 让 `yan` CLI 从环境变量读 toolCallId 回传 | pi 不注入这个变量；要它注入就得改 pi（不允许） |
| 按命令文本匹配 + 宿主写入回执 | 回执无法与某一张卡对齐（同一回合可能并行多条 bash），硬对齐就是猜 |

所以选**文本匹配**，并把代价写进代码注释与测试：

- 判到只是**展示标记**：不改变写入语义、不给权限 —— 任务是否真的被改写，
  永远由宿主服务（收到 `tasks.apply` 请求）决定；
- 被标记的那条本来就是一条真实存在的 bash 调用，可展开看原文；
- 已知边界单测里**显式断言**（`git commit -m "yan tasks apply"` 也会命中），
  不假装它是个安全判据。

反过来宁松不宁紧的理由：判漏会让用户以为迁移没生效，判多的代价只是一个标签。

### 1.2 `/panel` 是**隐藏**，不是删除

`/panel` 从补全里消失（任务由内置任务计划维护），但**必须留在注册表**：

- 用户扩展可能注册同名 `panel`（实测 `taskext` 场景：`source=extension` 且 `executable:true`）；
- 删掉兼容那条，pi 那条就会变成唯一命中项 —— 手打 `/panel` 会被当成命令发给模型；
- 所以「隐藏」与「谁执行」分开：界面按 `source === 'compatibility'` 判定，
  命中就给反馈、不动输入框，`hiddenInMenu` 只影响补全列表。

## 2. 顺带修掉的真问题：`yan.mjs` 整个 CLI 语法错误

`taskcli`（cost 1）第一次重跑时红了，且现象有误导性：界面上 `todos` 为空、
模型反复调 bash、助手回复是空串 —— 看起来像「模型不配合」。
给探针补一条诊断（把 `tasks apply` 调用的 `output` 尾部打出来）后当场见底：

```text
tasks apply 调用 1 次，尾部：[{"status":"error","out":")\r\n at #getOrCreateModuleJobAfterResolve (node:internal/modules/esm/loader:564:36)…"}]
```

`resources/yan-cli/yan.mjs` 的 `USAGE` 是模板字符串，而 S3 补进去的 help 文案里
写了 `` `tasks apply` `` —— 嵌套反引号提前终止模板，`node --check` 都过不了。
**所有** `yan` 调用都直接崩在 Node 的 ESM 加载阶段。

修完加了两条单测（真跑 CLI，不再只读文件内容）：

- `node --check resources/yan-cli/yan.mjs` 退出码 0；
- `node resources/yan-cli/yan.mjs --help` 退出码 0 且打出用法、
  并含 `tasks apply`（迁移后的入口要能被模型发现）。

> 这个坑值得记：S3 的「yan 启动器」单测只断言**启动器文件内容**包含
> `ELECTRON_RUN_AS_NODE=1` 与 `yan.mjs` 路径，CLI 自己坏掉它一条都照绿。
> 自动检查的洞是「只验文本、不跑程序」。

## 3. 顺带修掉的真问题：扩展来源诊断在说 S3 之前的话

`extensions-inventory.ts` 第 3 行原文是「当前任务清单仍由扩展写入 `left-panel-tasks`，
砚只读取并显示」——S3 之后宿主**已经**在写任务日志，这句话会让用户按错误前提排障。

改成两条路径 + 优先关系（都不越界）：

> [来源] 检测到用户扩展：它可能仍在写会话里的 `left-panel-tasks`；砚内置任务计划写宿主日志
>（数据目录下的 task-plans）。同一轮两者都有时以宿主日志为准，旧条目只读、不会被覆盖，也不会被回写

措辞为什么是「可能仍在写」而不是「仍在写」或「已经不写」：砚禁不了用户扩展，
写不写由它自己决定；能确定说的只有「两条路径各写各的」与「同一轮宿主优先」。

## 8. 剩余限制（不改就是已知行为）

1. **工具卡来源是文本判定**：`echo "yan tasks apply"` 也会被打标（单测里显式记着这条）。
   它不改变任何权限或写入语义；要更精确得等 pi 提供 toolCallId 到子进程的信道。
2. **只认 `tasks apply`**：`yan capabilities search` / `operations status` 的卡片仍是普通 bash 卡。
   扩展判定要连带决定「别的能力要不要各自归属」，属于 04（能力自主选择）。
3. **内置能力区不可交互**：没有禁用、没有版本、没有卸载 —— 这是刻意的
   （它能落地到宿主服务 / 随包 CLI，卸载它没有意义）。文案兜底：主进程新增薄层
   而渲染端未登记文案时，界面显示文件名 + 「（还没有说明文案）」。
4. **`/footer` 只统一了反馈**，没有迁移它的语义（S4 表里写明「不额外迁移 footer」）。
5. **`hiddenInMenu` 只影响 `/` 补全**，不影响 `commands` 列表本身
   （来源分布统计、tastext 的同名断言都要能看到它）。
6. **应用与包未做**：随 01-S5 / 09 一起验收；本片不新增运行期资源
   （新 IPC 是只读查询，内置能力清单从既有 `--extension` 路径派生）。
7. **`taskcli` 是 cost 1**，仍不在 `check` 默认门槛里；本片的 cost 0 证据是
   `slashcmd` 第 3/20 节与 `taskext` 第 4 节。

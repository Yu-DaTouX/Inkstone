# 证据 · 实施-05 S1：钩子的能力边界与安全点

> 2026-09-19。对应 [实施-05](../plan/实施-05-工作模式与长任务续接-已完成.md) §4 / §6 里
> **「S1 必须先验证」**的四个可行性问题。
> 全部结论来自**可复现实验**：假 provider + 五组对照，不联网、不花钱、不调用真实模型。
> 复现命令见文末。

## 0. 结论（先看这里）

| # | 问题（出处） | 结论 | 依据 |
|---|---|---|---|
| 1 | 同一工具循环里能不能刷新模式与工具集（§4） | **可实现** | 01-S1 已实测：`setActiveTools` 运行时可用且持续到后续请求（[证据-01-S1 §4](../evidence/证据-01-S1-可行性验证.md)） |
| 2 | 只读门禁能不能做成真硬限制（§4） | **可实现，且要从工具表里移除** | `--tools read,ls` 真移除（01-S1 §3）；本次补测 `tool_call` 返回 `{block:true}` **真的不执行**（实验 1） |
| 3 | hook 能不能**阻止下一个请求**（§6） | **能，但不是「暂停」** | `ctx.abort()` 让第 2 个请求**不发出**；代价是整轮以 `Request aborted` 结束（实验 2） |
| 4 | 能不能在钩子里做压缩（§6） | **不能** | `ctx.compact()` 在 `tool_call` 里返回 `undefined` 并把当前 run 打断（实验 3）；安全点在**宿主侧 RPC `compact`**（已有实现，见 §4） |
| 5 | 装不下的请求能不能不发（§6） | **能改写请求体** | `before_provider_request` 返回新 payload → 假 provider 收到的消息数当场变化（实验 4） |

一句话：**「拦住」的手段有三条，但语义各不相同** ——
改工具表（最干净）/ 改写 payload（能救预算）/ `ctx.abort()`（最粗暴，整轮结束）。
`ctx.compact()` 不是安全点，压缩必须由宿主在空闲时发起。

## 1. 怎么取的（方法与复现）

判据是**「第几个请求发没发出」「工具副作用有没有发生」**，所以模型必须可编程：

- `scripts/lib/mock-provider.mjs` —— 假 provider（OpenAI chat-completions 兼容）。
  第 1 次请求回一个 `bash` 工具调用（写 `s1-marker.txt`），之后回文本；
  每个到达的请求都追加进 `requests.jsonl`（含消息数、角色、工具表）。
- `scripts/lib/hook-probe-ext.mjs` —— 探针扩展，除指定那一件事外不改行为，逐条记录钩子时序。
- `scripts/hook-probe.mjs <mode>` —— 编排：建隔离 `PI_CODING_AGENT_DIR`（`models.json` + 假
  `auth.json`）→ 起假 provider → 跑 `pi --print` → 打印请求清单 / 钩子时序 / 会话 JSONL / marker。

```bash
node scripts/hook-probe.mjs plain     # 对照
node scripts/hook-probe.mjs block     # tool_call 返回 {block:true}
node scripts/hook-probe.mjs abort     # 第 2 次 before_provider_request 调 ctx.abort()
node scripts/hook-probe.mjs compact   # tool_call 里调 ctx.compact()
node scripts/hook-probe.mjs payload   # before_provider_request 返回改过的 payload
```

## 2. 实验 1（`block`）：`tool_call` 是真门禁，但拒绝文案不可定制

| 观测 | `plain`（对照） | `block` |
|---|---|---|
| 假 provider 收到的请求 | 1 次 | **2 次**（第 2 次带 1 条 tool 消息） |
| `bash` 副作用（marker 文件） | 不存在（本来就没调工具） | **不存在** |
| 会话 JSONL 里的工具结果 | — | `content: "Tool execution was blocked"`、`isError: true`、`details: {}` |

两条硬结论：

1. **返回 `{block:true}` 的工具真的不执行** —— 只读门禁可以靠它兜底
   （反向对照：`abort` 模式不 block 时，同一个命令**真的写了** marker 文件）。
2. **我返回的 `content` / `isError` 被忽略**：pi 固定写 `Tool execution was blocked` +
   `isError: true`。所以**不能用它给模型解释为什么被拒**；要让模型知道「澄清档只允许只读」，
   只能靠提示词 + **把工具从表里移除**（`--tools` / `setActiveTools`）。
3. block **不终止循环**：第 2 个请求照常发出，模型看到拒绝结果后继续。

**对 S3 的直接影响**：澄清档的只读门禁**以工具表（`setActiveTools`）为主**——
被移除的工具模型根本看不见，连「试图调用再被拒」都不会发生；
`tool_call` block 作为**兜底**（比如工具表刷新失败、或第三方/MCP 工具不在白名单里）。

## 3. 实验 2（`abort`）：能阻止下一请求，但是「整轮结束」而不是「暂停」

| 观测 | 结果 |
|---|---|
| 假 provider 收到的请求 | **1 次**（第 2 次**没有发出**） |
| 工具副作用 | 第 1 轮的工具**执行了**（marker 文件存在） |
| pi 退出 | `exit=1`，stderr：`Request aborted` |
| 会话 JSONL | 完整：user → assistant(toolCall) → toolResult → **一条空内容的 assistant**（usage 全 0） |

- `ctx.abort()` 在**请求前**调用是立即返回的（日志里 `abort_call` → `abort_returned` 相邻），
  不会死锁；效果是**这一轮 agent 直接结束**。
- 所以它是「**已知装不下就不发**」的可用硬止损，但**不能当成安全暂停**：
  想「停下来做点事再继续」，得先结束这一轮，再由宿主决定下一步。
- 空 assistant 消息会落进会话文件 —— 界面侧要能容忍（砚的历史以 JSONL 为准）。

## 4. 实验 3（`compact`）：钩子里不能压缩，安全点在宿主侧

| 观测 | 结果 |
|---|---|
| `ctx.compact()` 返回值 | `undefined`（日志 `compact_result raw:"null"`） |
| 当前 run | **被打断**：工具结果变成 `Operation aborted` + `isError: true`，`exit=1` |
| `session_before_compact` 钩子 | 没有触发（压缩根本没走到那一步） |

即：在工具调用窗口里主动压缩不是「忙时安全拒绝」，而是**把这次运行弄坏**。
这与 §6 的禁令一致（不得在 `before_provider_request` 内递归 compact），并且把原因说清了。

**安全点在哪**：宿主侧 **RPC `compact`**（`session.compact(customInstructions)`）。
砚已经在用这条路径（`src/main/agent.ts` 的手动压缩，pi 侧一律记为 `reason: 'manual'`），
所以 §6「完整落盘并进入 compact」是**已具备的能力**，不需要新接口——
需要新增的是**什么时候**发起（预算门判定），那是 S4 的活。

## 5. 实验 4（`payload`）：请求体可以当场改写

| 观测 | 结果 |
|---|---|
| 钩子看到的 payload | 2 条消息（`system,user`） |
| 假 provider 实际收到 | **3 条**（`system,user,system`，多出的那条是钩子注入的） |

`before_provider_request` 的返回约定是**替换**：返回 `undefined` 保持原样，返回对象则整体替换。
抛错**不会**阻止请求（只记一条扩展错误）。

**对 S4 的直接影响**：物理风险命中时可以在**同一个钩子里**裁剪历史（丢大工具结果 / 截短消息）
再发出去 —— 这比 `ctx.abort()` 温和得多，是「不发送已知装不下的请求」的首选实现。

## 6. 对实施-05 其余切片的影响

- **S3**：只读门禁顺序改为「工具表（主）→ `tool_call` block（兜底）→ 提示词（说明）」；
  门禁必须在**真实执行入口**施加（§6 已有的口径不变）。
- **S4**：软预算 → 改写 payload（实验 4）；物理风险 → `ctx.abort()`（实验 2）；
  安全压缩 → 宿主侧 RPC `compact`（§4）。**没有「安静暂停」可用**，所以
  「等待安全压缩」这个界面状态只能表示「这一轮已结束，正在压缩」。
- **S6**：`payload` 之外，观测点在**假 provider 的请求清单**上 ——
  「诊断与真实请求相符」可以用它做成**确定性**断言（不依赖真实 provider 用量）。
- 钩子时序（本次实测，与 01-S1 一致）：
  `input → before_agent_start → message_end(user) → context → before_provider_request
  → after_provider_response → message_end(assistant) → tool_call → message_end(toolResult)
  → context → before_provider_request → …`

## 7. 未覆盖 / 剩余限制

1. **只在 Windows + 内置 pi 0.85.1 上实测**；pi 升级后要重跑（`node scripts/hook-probe.mjs …`）。
2. 假 provider 只覆盖「一轮里两次请求」。**多轮连续 block / 连续 abort** 没测 ——
   S3 真做门禁时应在 live 场景里覆盖。
3. `ctx.compact()` 在**空闲时**能不能用没测（不需要：宿主侧走 RPC，已实现）。
4. 真实模型在 `block` 后的行为（会不会反复重试同一个被拒工具）没测 —— 这正是
   「以工具表为主、不要靠 block 反复拒绝」的理由之一。
5. 实验用的 `bash` 命令必须写**相对路径**：命令会被拼进 JS 字符串字面量，
   绝对路径的反斜杠会被当转义吃掉（踩过一次，文件写到了别处）。

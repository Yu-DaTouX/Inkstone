`yan tasks apply` 往 `~/.pi/agent/yan/ops/` 写了一个操作回执（已确认内容、已删除）。
`test-live.mjs` 与 `test-packaged.mjs` 现在都会剥掉这几个变量（§7.1）。

## 1. 这一片在验什么

S3/S4 已经分别验过「写入链」与「界面接线」，但它们都有一个共同的自证弱点：
**请求是预置的、或只看了界面**。S5 补的是两端：

| 场景 | 驱动方 | 证明了什么 |
|---|---|---|
| `taskcli`（S3） | Node 侧的预置 request 文件 | 模型照用法敲命令 → 宿主写入 → 界面读回。**写入链**不受模型随机性干扰 |
| `taskplan`（本片） | **全部由模型决定** | 模型自己写 JSON、自己登记、自己做、自己勾选 —— 真实使用下的整条链 |

「三处一致」的具体落点（`taskplan` 里三条同时断言）：

1. **工具调用** —— 界面上的 `yan tasks apply` 工具行（且带 `data-origin="yan-task-plan"` 来源标记）；
2. **原生任务清单** —— 渲染端 `store.todos`（探针打进 `taskplan.todos=…` 取证行）；
3. **实际落盘** —— `YAN_DATA_DIR/task-plans/<sessionId>.jsonl` 的最后一行。

② 与 ③ 由退出后的 `afterExit: taskPlanMultiStep` **逐条比对文字与勾选状态**；
另外核会话 JSONL 里没有任务条目（宿主日志不寄在会话文件上）。

## 3. 证据 · 真实运行

### 3.1 `taskplan`（cost 1，**新场景**，`YAN_TEST_MODEL=deepseek/deepseek-v4.1-flash`）一次全绿

任务（提示词里给死形状、内容由模型自己写）：在 fixture 项目里建 `tasks/step-1/2/3.txt`，
每建完一个就用任务计划标完成。

实测：

| 观察 | 值 |
|---|---|
| 工具调用序列 | `bash → write → bash → write → …`（16 次：8 次 `write`、5 次 `bash`） |
| `yan tasks apply` 调用 | **5 次**（1 次 `add` 三条 + 3 次 `complete` + 1 次后续调用） |
| 界面清单 | 3 条，文字是模型自己写的（「第 1 步：创建 tasks/step-1.txt 并写入说明」…），**3/3 完成** |
| 来源标记 | 5 条工具行标为「任务计划 · 砚内置」，全部仍是 `bash` 卡，摘要里就是 `tasks apply` |
| 磁盘日志 | 4 行，`revision` **1 → 2 → 3 → 4**，每行 `schemaVersion=1`，坏行 0 条 |
| 三处一致 | 界面 3 条 vs 日志最后一行 3 条 —— **文字与勾选逐条相同** |
| 会话语义 | 会话 JSONL 里**没有** `yan-task-plan` / `left-panel-tasks` 条目 |
| 真实产物 | `tasks/step-1/2/3.txt` 三个文件都建出来了、都非空（不是嘴上说完成） |

模型自己写了请求文件 `tasks/yan-plan.json`（探针没有预置任何 request）。
**「模型会不会真的照这个用法做」这件事第一次有了正面证据** —— S3 的预置文件绕过了它。

### 3.2 `taskcli`（cost 1，回归 + 新增「取消」一节）全绿

原有 28 条断言不变（写入 → 界面 → `complete` → 切走清空 → 切回读回 → 退出后磁盘核对），
**新增 4 条「取消」断言**：

- 回合真的跑起来（取消的前提）→ 同一个按钮文案从「发送」变成**「中止」** →
  点它 → `isAgentRunning` 变 false；
- 取消**没有改动任务清单**（前后 JSON 完全相同）；
- 没有卡在 `running` 的工具行；输入框仍可用。

退出后那半边的保护也在：日志仍然是 **2 行**（`valid.length === 2`）——
如果取消导致多写/写坏，这条会红。

### 3.3 cost 0 的共存与命令面

- `taskext` **扩成两个扩展**（旧任务扩展 + **与任务无关**的 `notes-panel.ts`），新断言 4 条全绿：
  来源诊断数的是**全部**用户扩展（2 项）、无关扩展也在清单里、它的 `session_start` 通知真的进日志、
  它注册的 `/notes` 照常出现（`source=extension`）；
  同时第 3 节的 4 条任务清单仍只来自 fixture 会话（无关扩展没有干扰来源判定）。
- `slashcmd` 20 节全绿（含手打 `/panel` 草稿与附件都不丢，S4 那条不变）。

### 3.4 回归

`todos` / `todonew` / `slashcmd` / `sessions` / `historyswitch`（cost 0）**全部通过**。
其中 `todos` 是历史上那条「陈旧失败」—— 现在跑的是修好后的断言（不是跳过、不是放宽）：
`fs` 那条既有的焦点/roving-tabindex 红与本片无关。

## 4. 证据 · 应用与包

`npm run dist:dir`（build + electron-builder）→ 安装目录 `resources/` 下
`app.asar` / `pi-extensions` / `pi-runtime` / **`yan-cli`** 四件齐全；
`npm run test:packaged` 通过，新断言 11 条：

| 组 | 断言 |
|---|---|
| 静态落位 | `extraResources` 里 `yan-cli/yan.mjs` 真的在安装目录（electron-builder.yml 漏一行就会失败） |
| 运行时启动器 | `YAN_DIR/bin/yan.cmd` 与 `bin/yan` 都被生成；内容指向**解包目录**里的 `yan.mjs`（不是开发态仓库路径）；用的是应用自带运行时（`ELECTRON_RUN_AS_NODE=1`） |
| CLI 真跑 | 用**解包里的 exe** 以纯 Node 模式跑解包里的 `yan.mjs --help`：退出码 0、打出用法、用法里含 `tasks apply` |
| 错误可读 | 无宿主环境下 `yan tasks apply` 退出码 **3**（`unavailable`），报「宿主能力服务不可用」并列出缺哪些环境变量 |

最后一条是本轮补的洞：**「文件在不在」不等于「程序能不能跑」** ——
S4 那次 `yan.mjs` 语法错就是靠「真跑一次」才暴露的（证据-02-S4 §2）。

**没有做**（如实记录，见 §7.2）：在解包实例里由**模型**触发一次 `yan tasks apply`。
它需要把真实凭证复制进隔离 piDir，且新增覆盖主要在「模型侧」，与打包无关。

## 5. 失败恢复逐项对照

S5 列的五个情形，逐条给出**实际拿到的是什么证据**：

| 情形 | 证据 | 强度 |
|---|---|---|
| 扩展冲突（旧任务扩展 + 无关扩展 + 砚同时存在） | `taskext`：诊断 2 项、`/panel` 两条并存、任务清单只读旧会话、退出后会话文件前缀逐字节不变 | **live（cost 0）** |
| RPC / 实例重启 | `taskcli` 第 3 节：切走再切回，清单从磁盘读回（含完成状态）、会话 id 稳定在原值 | **live（cost 1）** |
| 取消 | `taskcli` 第 4 节：取消后清单不变、无卡住的运行行、输入框可用；退出后日志仍是 2 行 | **live（cost 1）** |
| 磁盘错误 | 单测 `test-task-plan-store.mjs`：`write_failed` / `read_failed` 都报错不报成功、失败后文件逐字节不变；对日志路径换成目录也要报错，**不退化成空清单** | 单测 |
| 两个快速 add | 单测 `test-task-plan-store.mjs`：并发两次提交都成功、清单是 2 项（漏了串行会只剩 1 项）、写了两行 | 单测 |

后两条没有 live 场景：它们要构造的真实条件是「磁盘不可写」与「同一会话两条并发写」，
在 Electron 里只能靠模型凑巧并发触发，**不可复现的场景比没有场景更糟**（会变成偶发假红）。
落盘层的保护（只追加、按会话串行、失败即不动）已经在单测里逐条钉住，这里不重复造。

## 7. 剩余限制

1. **测试工具自身会污染真实数据（已修，但值得记住）**：`YAN_CLI_*` 是环境变量，会被子进程继承；
   从砚自己的 pi 子进程里跑任何测试时，它们都指向**真实实例**。现在两个测试入口都会剥掉。
   如果你在别的地方 spawn 子进程跑 `yan`，也要注意同一件事。
2. **包里的「模型触发任务工具」没验**：需要真实凭证进隔离 piDir。
   等价覆盖是开发态 `taskcli`/`taskplan`（同一条链），而「打包带来的差异」已经单独验过
   （启动器指向解包目录 + CLI 在解包目录里真跑 + 资源清单齐全）。
3. **`taskplan` 依赖模型照做**：提示词给死了任务形状与请求格式，但**没有任何机制强制**模型用任务计划。
   实测 deepseek-v4.1-flash 一次通过（5 次 apply）；换模型（尤其小模型）可能只登记不勾选、
   或者干脆不登记。这条红的时候**先看诊断输出里「工具调用序列」**——
   它把「没调工具」「调了但 yan 报错」「界面没刷新」三种原因分开写出来了。
4. **免费模型不保证把摘要贴回正文**：`taskplan` 实测助手最后一条回复是空白，
   所以判据全部落在工具调用 / 界面状态 / 磁盘上，**不拿模型的自然语言当证据**。
5. **取消只验了「取消不损坏已有数据」**：没有验「取消时正好在写盘」那一瞬间的行为
   （同步追加写完整行，理论上是原子的；单测覆盖了失败即不动）。
6. **`todos` 场景的既有红（`fs`）与本片无关**：HANDOFF 里始终登记为两条待修的遗留缺陷。
7. **应用与包栏的边界**：`dist:dir` + `test:packaged` 验的是**解包目录**，
   不是 NSIS 安装包 / portable 单文件（那两条属于实施-09）。

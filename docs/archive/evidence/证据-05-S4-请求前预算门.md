# 证据 · 实施-05 S4：请求前预算诊断与硬闸门

> 2026-09-19。对应 [实施-05](实施-05-工作模式与长任务续接-已完成.md) §6 的
> 「每次模型请求前的预算诊断」「soft 命中先清旧工具结果」「物理风险不发送已知装不下的请求」。
> S1 已经证明**手段可用**（`before_provider_request` 能改写请求体、`ctx.abort()` 能让下一个请求真的不发）；
> 这篇记录**落地之后**的行为证据。
> 复现命令见文末。

## 0. 结论（先看这里）

| # | 问题 | 结论 | 依据 |
|---|---|---|---|
| 1 | 装不下的请求真的没发出去吗 | **是** | 假 provider 只收到 **1** 个请求（正常应是 2），第 2 个被钩子挡在门外（实验 1） |
| 2 | 挡下之后有痕迹可查吗 | **有** | 会话 JSONL 里一条 `custom: yan-budget-abort`（估算 / 预测 / 窗口 / 原因）+ 诊断 `budget-abort{aborted:true}` |
| 3 | soft 会不会误伤（把正常请求也挡掉） | **不会** | 同一份消息、同一个大工具结果，`budget-soft` 组 **2 个请求全部发出**、0 次 abort（实验 2） |
| 4 | 估算准不准 | **同量级（~1%）** | 估算 13621 token ↔ 真实请求体 55054 字符（4 字符/token 口径偏差 570 字符）（实验 2） |
| 5 | soft 命中会先清旧工具结果吗 | **会**（产品接线，单测） | 同一份消息、把收益门槛设到永远不可能达标：窗口未知时**一条不清**；预算知道窗口且过线时**清出墓碑**（实验 3） |
| 6 | 真实链路会不会误拦 | **不会** | `budgetgate`（cost 1）：`request-budget-soft` 记到了，`physical` / `budget-abort` **都是 0**（实验 4） |
| 7 | 公式会不会两边漂移 | **有可执行检查** | 6 个窗口 + 一组覆盖值：扩展侧 JS 与 `shared/context-policy.ts` 的 `workingSet` / `emergency` / `reserve` / 三条触发线**逐项相等**（单测） |

一句话：**估算到了工作集线就清扫，到了「估算 + 输出预留 > 窗口」就不发** ——
两条线都由同一份预算公式算出来，且「不发」这条只有在假 provider 上才能确定性取证（真实窗口 1M 构造不出）。

## 1. 方法与复现

判定用的仍然是 S1 留下的设施（**不联网、不花钱**）：

- `scripts/lib/mock-provider.mjs` —— 假 provider；每个到达的请求追加进 `requests.jsonl`，
  本轮新增 `bodyChars`（请求体真实字符数，用来校准估算）。
- `scripts/hook-probe.mjs <mode>` —— 编排：隔离 `PI_CODING_AGENT_DIR` → 起假 provider →
  跑 `pi --print` → 打印请求清单 / 钩子时序 / 会话 JSONL / 预算诊断。

```bash
node scripts/hook-probe.mjs budget        # physical：第 2 个请求应当不发
node scripts/hook-probe.mjs budget-soft   # 对照：同一个大结果，soft 但照发
node scripts/hook-probe.mjs abort         # S1 回归（原样）
node scripts/hook-probe.mjs workmode      # S3 回归（原样）
```

两个新模式都加载**真正随包**的 `resources/pi-extensions/context.js`，
预算覆盖走的是产品的 `YAN_CONTEXT_POLICY` 通道（`workingSetCap` / `responseReserve*` / `safetyMarginMin`）：

| 模式 | 策略覆盖 | 期望 |
|---|---|---|
| `budget` | `responseReservePreferred/Min = 195000`、`safetyMarginMin = 1000` | 装不下的线降到 5k → 大工具结果必然超过 → **不发** |
| `budget-soft` | `workingSetCap = 1000`（输出预留走默认 32k） | 过线但离窗口很远 → **照发**，只标 soft |

模型窗口由 `models.json` 固定为 200000，最大输出 4096（与假 provider 一致）。

## 2. 实验 1（`budget`）：物理风险 → 请求真的没发出去

假 provider 收到的请求：

```
n=1  messageCount=2  roles=["system","user"]  bodyChars=3456  toolNames=["bash","read"]
（n=2 不存在）
```

钩子时序（关键几行）：

```
before_provider_request  n=1  messageCount=2
tool_call                n=1  name=bash  command=node -e "process.stdout.write('x'.repeat(400000))"
context                  count=3  roles=["user","assistant","toolResult"]
sweep-forced-by-budget   transcriptTokens=12890  applied=false  reason=no-candidates
before_provider_request  n=2  messageCount=4      ← 只到钩子，没有 after_provider_response
message_end              role=assistant  textLen=0
```

预算诊断：

```json
{"hook":"request-budget-normal",  "estimatedTokens":776,   "window":200000, "workingSet":1000, "responseReserve":195000}
{"hook":"request-budget-physical","estimatedTokens":13621, "projectedTokens":208621,
 "reason":"估算 13621 + 输出预留 195000 = 208621 超过窗口 200000：不发送这个请求"}
{"hook":"budget-abort", "aborted":true, "estimatedTokens":13621, "projectedTokens":208621}
```

会话 JSONL 里留下了那条留痕（不进模型上下文）：

```json
{"type":"custom","customType":"yan-budget-abort",
 "data":{"estimatedTokens":13621,"projectedTokens":208621,"contextWindow":200000,
         "reason":"估算 13621 + 输出预留 195000 = 208621 超过窗口 200000：不发送这个请求"}}
```

三条硬事实：

1. **第 2 个请求没有发出** —— 假 provider 的请求清单里根本没有 `n=2`，
   而 `before_provider_request` 的时序里有（说明钩子跑到了、判定也下了）。
2. **代价是这一轮空转**：会话里多一条空内容的 assistant（与 S1 的 `ctx.abort()` 结论一致）。
   所以留痕必须存在 —— 用户/排障者要能区分「被预算挡下」与「崩了」。
3. `sweep-forced-by-budget` 也触发了，但 `applied:false / no-candidates`：
   在这次实验里整个对话是**一个原子单元**（只有一条 user 消息，assistant/toolResult 都挂在它下面），
   按「不得从单元中间切」的硬约束，它没有可清的东西。**这不是缺陷**，
   而是这一片最难在假 provider 里覆盖的点（见实验 3 与剩余限制②）。

## 3. 实验 2（`budget-soft`）：同一份消息、同一个大结果，照发

| 观测 | `budget`（physical） | `budget-soft`（对照） |
|---|---|---|
| 假 provider 收到的请求 | **1** | **2** |
| 第 2 个请求 | 没有 | `bodyChars=55054`、`toolResultCount=1` |
| 预算 abort | 1 | **0** |
| 第 2 个请求的诊断 | `request-budget-physical` | `request-budget-soft`（`projectedTokens=45621`，离窗口还远） |

**估算 vs 真实**：诊断里的 `estimatedTokens = 13621`，
第 2 个请求的真实体积 `bodyChars = 55054`。按估算口径（ASCII 4 字符/token）
`13621 × 4 ≈ 54484` —— 与实际相差 570 字符（**约 1%**）。
也就是说这条线不是拍脑袋的：它量的确实是那个要发出去的请求。

## 4. 实验 3（单测）：预算驱动的清扫，成对对照

物理闸门在假 provider 里验得了；**「soft 命中先清旧工具结果」验不了** ——
单次 `pi --print` 只有一个 user 消息，按原子单元规则没有可清的旧回合。
所以这一条用产品代码的直接调用取证（`scripts/test-context-transform.mjs` 的 L 节）：

| 条件 | 结果 |
|---|---|
| 收益门槛设成永远不可能达标（`minReclaimTokens = 1e9`）+ **窗口未知** | **一条都不清**（高门槛仍然有效） |
| 同样的消息、同样的高门槛 + 窗口 200k + `workingSetCap = 100` | **墓碑 1 条**（过线 → 门槛归零 → 真的清了） |

两组的**唯一差别**就是「预算知不知道窗口、有没有过线」，
所以那次清扫只能来自 S4 的接线。同一节还钉住两条：
`requestBudgetFor({contextWindow: 0}) === null`（回落原生压缩）、
`requestBudgetFor({contextWindow: 64000}).workingSet === 40000`（读到窗口并算对）。

## 5. 实验 4（真实模型）：`budgetgate`（cost 1）——不误拦

- 场景：`YAN_CONTEXT_POLICY={"workingSetCap":3000}`，只发一句「1+1 等于几」。
- 结果：这一轮正常跑完；磁盘上的预算诊断只有**1 行**：

```json
{"hook":"request-budget-soft","messages":4897,"tools":960,"system":0,
 "estimatedTokens":5857,"workingSet":3000,"window":1000000,
 "workingSet":3000,"responseReserve":32000}
```

四点：

1. **`ctx.model.contextWindow` 在 `before_provider_request` 里可用**（读到 1048576）——
   这是 06-S4 的结论在这一处的复用，之前只在 `context` 钩子里验过。
2. **soft 命中**（5857 ≥ 3000），说明钩子在真实链路上是活的。
3. **`physical` 与 `budget-abort` 都是 0**：真实窗口 1M 下不该拦，也确实没拦。
4. 本轮模型返回了空文本 —— **与预算无关**：手动 `--print` + 同一扩展 + 同一策略 + 同一模型
   同提示正常回答「1+1 等于 2。」；诊断里也没有 abort。场景因此**不拿模型文本判红**
   （判据是那三条磁盘断言）。

**同批回归**：

- `contexttakeover`（cost 1）**全绿** —— 真实压缩链路照常：`beforeTokens=31158 → afterTokens=98`、
  `triggeredBy: policy` / `policyStage: compact`、`session_before_compact` 钩子被调到。
  这条同时证明新钩子没有干扰既有的工作集压缩。
- `hook-probe abort` / `workmode`（cost 0）行为与 S1 / S3 记录一致。
- `test:live -- contextbudget context`（cost 0）全绿。

## 7. 已知限制

1. **physical 只在假 provider 下取证**：真实模型窗口 1M，构造不出「估算 + 输出预留 > 窗口」；
   这与 S1 的四组对照同一取舍（判据是「请求发没发出」，真实模型看不见网络层）。
2. **soft 的清扫没能在真实链路取到「真清了」的证据**：单次 `--print` 只有一个原子单元，
   而真实多轮会话要花模型额度才能造；产品接线的成对对照在单测里（实验 3）。
3. **估算没有缓存 / 增量**：每轮遍历一遍 messages 与工具表（O(体积) 的字符串拼接）。
   大上下文下的 CPU 成本**没实测**；真成为问题时再按「只算变化段」优化。
4. **界面看不到档位**：`normal / soft / physical` 只写进诊断日志与那条 `yan-budget-abort` 留痕，
   界面上没有「预算」指示（S6 的联调范围）。
5. **默认测试模型已退役**：`commandcode/longcat-2.0:free` 现在返回
   `403 permission_error`（免费层下线）—— 与本片无关，但会让不带 `YAN_TEST_MODEL` 的 cost 1 场景变红；
   本片的 `budgetgate` 固定用 `deepseek/deepseek-v4.1-flash` 绕开它。
6. 判定用的是**估算**：口径偏差在纯 ASCII 上约 1%，但图片、超长单行、非 ASCII 混合
   未逐一标定；physical 线留了完整的输出预留就是给这个误差当缓冲。

## 1. `pi install` 的真实能力面

`pi install --help`（原文）：

```
pi install <source> [-l] [--approve|--no-approve]
  -l, --local       Install project-locally (.pi/settings.json)
  -a, --approve     Trust project-local files for this command
  -na, --no-approve Ignore project-local files for this command

Examples:
  pi install npm:@foo/bar
  pi install git:github.com/user/repo
  pi install https://github.com/user/repo
  pi install ./local/path
```

结论：

1. **可以装 npm 包**（`npm:@foo/bar`）—— 与 S5 的 npm 候选路径对得上。
2. **`-l` 装到项目级 `.pi/settings.json`** —— 正好是 §8 `AcquisitionPlan.scope: 'project-managed'` 的落点。
   非 `-l` 是用户级；自动接入应默认**项目级**（影响面小、可随项目回滚）。
3. `pi list` 可以列出已装包（用于「接入后核验」与「禁用后缓存失效」）。
4. 除此之外 pi **没有**包搜索、也没有「静默安装」开关（`pi --help` 只有 install / remove / update / list / config / auth）。
5. **技能可走显式启动参数，不必登记成 pi 包**：当前随包 CLI 的 `pi --help` 列出
   `--skill <path>`（可多次传入；支持 Skill 文件或目录），并明确 `--no-skills`
   只关闭自动发现、不会关闭显式 `--skill`。因此受管 Skill 可以按 projectId 从
   `YAN_DIR` 解析出已核验目录，并在目标 runner 启动时显式加载；无需写入项目
   `.pi/settings.json`，也无需增加 pi 扩展。此项只确认了 CLI 能力，宿主的受管目录、
   启动接线、安装与真实 runner 验收仍未实现。

## 2. ⚠️ 项目资源信任：安装不能靠命令行标记绕过

`--approve` / `--no-approve` 控制的是**本次命令是否信任项目本地资源**，不是安装确认。
当前 pi 对未信任项目执行 `pi install <local-path> -l` 会拒绝修改 `.pi/settings.json`；
`--no-approve` 不会让安装成功，而 `--approve` 是一次命令级项目资源信任覆盖，
不应由自动接入器静默追加。项目持久信任保存在 pi 的 `trust.json`，其范围覆盖该项目
当前及后续的 `.pi` 设置、扩展与技能，明显宽于「批准这一个候选包」。

**2026-09-20 隔离实测**（仅临时目录与内置 pi CLI）：未信任项目的本地目录安装无 `--approve`
时失败并提示项目不受信任；加 `--approve` 后成功改写临时项目 `.pi/settings.json`。
安装过程中，预先放置的项目扩展及已登记包扩展都没有执行；本地路径登记也没有执行包的
`prepare` 脚本。该结果只证明 CLI 安装命令本身，不代表后续 runner 加载资源时安全，也不代表
依赖安装阶段不会执行生命周期脚本。

S6 的实施口径：先查询项目是否已有**持久信任**；不可信时必须在用户授权对话框明确展示
「信任整个项目资源」的实际范围并由用户选择，随后仅用宿主固定参数执行
`pi install <verified-path> -l`，**不传 `--approve` 或 `--no-approve`**；
命令参数不得拼入模型提供的 shell 字符串（§8）。若持久信任无法确认或写入失败，拒绝安装。

## 4. 仍未决、必须在 S6 实施时实测的问题

这些**不能在预检里下结论**，避免凭空假设：

1. **装完是否需要重启 pi 实例**（§10.1）。若需要，就得走「激活 + 继续原任务」，
   而不是让用户手动重开 —— 这正是 S6 出口要证的东西。
2. **隔离验证怎么做**：装完在 staging 里先跑一次（不污染项目），
   验证点是「真的能加载出技能 / 工具」，而不是「文件存在」。
3. **`continueId` 的现有机制**：项目里已有工作模式与长任务续接（实施-05 S2–S3 已改
   `Composer.tsx` / `session-runtime.ts` / `store.ts`），S6 要**复用**它，
   不能另造一套「继续」概念 —— 且「仅消费一次」要有断言。
4. **并发安全**：接入期间正在跑的任务不能被重启（出口原文），
   其他 runner（子代理 / 其他会话）也不能被牵连。
5. **staging 落点**：放 `YAN_DIR` 下的受管目录，且**只清受管资源**（§13.3「缓存与卸载」）。

## 5. 与 S5 的衔接

S5 已交付：候选（`metadata-only`）、排名（不含下载量）、固定版本的接入计划、
`policyResult` 判定、`acquire` 明确 `not_implemented`。
S6 从那里接上：**下载 → 校验 → staging → 安装 → 隔离验证 → 激活 → 继续原任务**，
并且在每一步都能被取消、失败不留半登记状态。

# 证据 · 实施-04 S5（联网发现）真实目录检索记录

> 对应 [实施-04](../../plan/active/实施-04-能力自主选择-MCP与Skill.md) §7.2 / §8 / §12 S5。
> §12 S5 的出口原文：「**真实目录检索证据**（不能只用 fixture 断言排名）」——
> 这份文件就是那条证据：**真实请求、真实响应、真实候选**，附可复现的命令。
>
> 采集时间：**2026-09-19**（运行时 pi 0.85.1，Node v24.19.0，Windows）。
> 目录内容会随时间变化，所以本文只记录**当天实际返回了什么**，不声明永久排名或永久包名。

## 1. 为什么是这两个源（先做了可用性预检）

| 候选源 | 预检结论 | 依据 |
|---|---|---|
| **官方 MCP Registry** `registry.modelcontextprotocol.io/v0/servers` | ✅ 可用，免密钥，支持 `search` + `limit` + `metadata.nextCursor` 分页 | 实测 `?search=filesystem&limit=3` 返回 3 条，含 `server.name` / `description` / `version` / `remotes[]` |
| **npm registry 搜索** `registry.npmjs.org/-/v1/search` | ✅ 可用，免密钥，支持 `text` + `size` + `from` | 实测返回 `objects[].package`（name / version / description / links / publisher） |
| pi 官方包目录 | ❌ **不存在** | `pi --help` 只有 `install / remove / uninstall / update / list / config / auth`，**没有**包搜索命令。这一条如实写进候选说明（`未核实包内是否含 SKILL.md`），没有假装有 |

§7.2 的硬要求「至少一条 Skill 路径和一条 MCP 路径、密钥缺失时仍能做目录检索」由此满足：
两个适配器都是**砚随包提供**的内置实现，不依赖先装搜索插件，也不需要任何 API key。

## 2. 真实检索记录

命令（宿主链路，场景 `discnet`）：

```bash
yan capabilities discover --query-text "filesystem"
```

回执摘录（真实输出，字段未改）：

```json
{
  "query": "filesystem",
  "sources": [
    { "sourceId": "npm-registry", "kind": "npm-registry", "ok": true, "pages": 2, "candidateCount": 40 },
    { "sourceId": "mcp-registry", "kind": "mcp-registry", "ok": true, "pages": 2, "candidateCount": 40 }
  ],
  "candidates": ["…共 8 条（已按 §7.2 截断）…"]
}
```

要点：

- **两个源都真的返回了候选**（各 40 条 = 2 页 × 20），不是「源可达但 0 条」。
- **分页被真的跟随**：`pages: 2` 说明 `nextCursor` / `from` 生效（§7.2「每源最多两页」）。
- 候选经排名后**截断到 8 条**（§7.2「候选最多八项」）。
- 排在最前的真实候选样例：`npm:@capacitor/filesystem@8.1.3`。
- 每条候选都带 `sourceUrls`（可回溯到 npm 页面 / 仓库 / registry 查询地址）。

**一个实测教训**：第一版检索词用的是 `"filesystem storage tools"`，
结果 npm 返回 40 条而 **MCP Registry 返回 0 条** —— 它的 `search` 偏精确匹配，长句搜不到。
改成单个通用词后两边都有结果。这也说明「源 ok」**不等于**「这个源查到了东西」，
所以场景里的断言是分两条写的（源可达 + 该源 `candidateCount > 0`）。

## 3. 可信度标注（§8「`metadata-only` 不得声称已验证」）

目录返回的一切都被标为 `verification: "metadata-only"`，并附一句能力边界说明：

> 候选来自公开目录的元数据（verification=metadata-only）：只证明发布来源存在，
> 不等于代码已审计，也不等于已验证可用。

具体到两类候选：

| 类型 | 目录能证明的 | 目录**不能**证明的（如实写进 `requirements`） |
|---|---|---|
| npm 包 | 包存在、确切版本、发布者、仓库 | 是不是 pi 技能包、包内有没有 `SKILL.md` |
| MCP server | server 名、版本、描述、`remotes` 端点或 `packages` 运行时 | 认证方式（一律 `unknown`，**不猜成 `none`**）、能不能在本机跑 |

MCP 远程端点的 `installKind` 是 `remote` —— **不伪造下载步骤**（§9）。

## 4. 接入计划（S5 只生成，不执行）

```bash
yan capabilities prepare --candidate "npm:@capacitor/filesystem@8.1.3"
```

真实回执：

```json
{
  "planId": "1ebd218793ef80c2",
  "revision": 1,
  "candidateId": "npm:@capacitor/filesystem@8.1.3",
  "pinnedSource": "npm:@capacitor/filesystem@8.1.3",
  "scope": "project-managed",
  "policyResult": "needs-authorization",
  "executable": false
}
```

- 固定到**确切版本**（§8：不因搜索结果第一名就自动执行）。
- `planId` 由 `候选 + 目标 + 项目` 稳定派生：**抓取时间不进指纹**，
  否则每次 discover 都会让计划「刚生成就失效」。
- `executable: false` 是本片的边界：真正下载 / 安装 / 登记是 **S6**。
- 候选只由宿主持有（10 分钟），模型只能回传 ID —— 不能让模型自己拼装「要装什么」。

## 5. 失败路径（不编造）

| 情形 | 行为 | 证据 |
|---|---|---|
| 两个源都不可用 | 返回**空候选** + 「暂时无法搜索」+ 每个源的具体错误 | 单测（注入必失败的 fetch）；live 场景离线时走同一条路径并**跳过** |
| 只有一个源可用 | 仍返回该源候选，两个源状态**分开记录** | 单测 |
| 检索词脱敏后为空 | **不发请求**，直接说明「只剩本地路径 / 密钥 / 文件名」 | 单测 |
| 未知候选 ID（prepare） | 可读错误 `candidate_unknown`，不吐堆栈 | live 场景 |
| `acquire` | 明确 `not_implemented`（不假装成功） | live 场景 |

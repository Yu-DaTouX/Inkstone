## 0. 一句话结论

宿主任务服务落地为 `src/main/task-plan-store.ts`：**一个会话一个 append-only JSONL**，
写前从磁盘读回 `revision` / `operationId` 做 CAS 与幂等，同一会话串行，
写完 `fsync` 并回读校验（**落盘失败不得报成功**）。
`yan tasks apply` 经既有能力端点进入 `AgentController`，会话身份由宿主自取、不由模型自报。
界面把**宿主日志 + 会话里的旧条目**按同一套规则归并（同轮宿主优先）。
真实模型链路（`taskcli`，cost 1）全绿：模型敲 `yan tasks apply` → 清单出现在界面 →
切走清空 → 切回从磁盘读回；退出后核对：日志两行、`revision` 1→2、会话 JSONL 里**没有**任务条目。

## 1. 一个必须先讲清的设计决定：宿主日志**不写进**会话 JSONL

方案里「宿主日志」只规定了字段（`sessionId + branchHead + revision + operationId`），
没写物理落点。核实之后只能落在**砚自己的目录**：

| 事实 | 怎么核的 | 结论 |
|---|---|---|
| pi 的 RPC **没有**「追加 custom entry」命令 | 从 `resources/pi-runtime/dist/bundle/chunks` 里提 RPC 命令表：`steer`/`prompt`/`switch_session`/`fork`/`get_entries`/`compact`… 共 30 条，**没有写 entry 的那条** | 宿主没有官方通道写会话条目 |
| 协议层**不许**外部写正在用的 JSONL | 01 §5 的迁移要求：「新数据由宿主保存」「不能直接编辑正在使用的 pi JSONL」；pi 的 SessionManager 在内存里维护 parentId 链与 leaf，外部追加会让文件与内存分叉 | 不能自己 append JSONL |
| 用扩展 `appendEntry` 代写也不行 | 02 §0「`resources/pi-extensions/task-plan.js` **不再新建**」；01 §5「不能再要求 pi `appendEntry` 写新数据」 | 唯一合规落点是宿主自己的文件 |

所以：`YAN_DATA_DIR/task-plans/<sessionId>.jsonl`，一行 = 一次提交；
界面把这份日志按**与会话条目完全相同的形状**喂给
[`todoSnapshotsFromEntries`](../../../src/main/todo-snapshots.ts)（`taskPlanLogEntry()`）。
好处是归并规则只有一份（同轮宿主优先、相邻轮合并、按轮次排序），
不会出现「旧条目一套规则、宿主日志另一套」的不一致。

**代价如实登记**：用户拿 pi 终端打开同一会话时看不到这些任务（它不在会话文件里）。

## 2. 契约定稿（本片往 S2 的契约上补的部分）

| 项 | 定稿 |
|---|---|
| 日志文件 | `YAN_DATA_DIR/task-plans/<sessionId>.jsonl`，**只追加**；文件名就是 pi 会话 id |
| 行形状 | `{ id, round, at, data: { schemaVersion, revision, operationId, todos } }` —— `data` 与写进会话文件的载荷同形（`TaskPlanEntryData`） |
| `round` | **写入时**记下当时的用户轮次（数会话里的 user 消息），读回时直接采信 —— 日志文件在异地，条目的位置推不出轮次 |
| 幂等键 | `operationId`：缺省由宿主生成（`randomUUID`）；调用方显式传则以它为准（重试同一次提交的唯一表达方式）。它**不做身份判定**，身份永远来自端点绑定 |
| 失败语义 | 校验失败 → `ok:false + code`，`state` 一个字段不动；落盘失败 → `write_failed`（**不报成功**）；读不了 → `read_failed`（**不退化成空清单**，否则下一次写入会基于空清单，等于悄悄清空） |
| 错误附件 | 参数类失败把**当前清单**落进 `resultFile`（`{ revision, todos }`），模型据此自我纠正；错误码进响应 `code` 字段 |

「切走再切回读得回」是**重启后读取正确**的等价物：面板数据来自磁盘上的日志
（切走时清单清空，切回是从文件读回来的，不是内存里留着的）。

场景的两个前提写在这里，免得后来人以为是产品行为：

- request 文件由 **Node 侧**预置在 fixture 项目的 `tasks/` 下（`buildFixtureProject`），
  探针只让模型跑一条 bash 命令。**不让模型自己写 JSON**：那多一次工具往返，
  而模型可能换目录或改内容 —— 本场景验的是宿主写入链，不是 `write` 工具。
- 探针等「回合级 `session.isAgentRunning`」而不是 `.trow[data-running]`：
  两次工具调用之间后者会短暂消失，提前收工会把「还在跑」当失败。

### 6.1 顺手修掉：历史任务条目「一列一个字」（既有缺陷）

第一版截图里历史条目的任务文字是竖排单字（`确` / `实` / `真` 各一行）。测量结果：
行宽 293px、列宽 `13px 274.8px` 都正常，但 `.rp-text` 只有 **13px** 宽。
根因是 `.rp-box` 的**通用**规则里写了 `grid-column: 2`（那是为任务本体的 4 列网格写的），
而历史条目只有 2 列 —— 勾选框显式占掉第 2 列后，`.rp-text` 的自动放置只能退到 13px 的第 1 列。
修法是给历史条目补一条 `.rp-hist-todo .rp-box { grid-column: 1 }`（只补列号，不动布局），
重拍后深浅两张里的历史条目都正常。这不是本片的功能范围，但它是视觉验收该抓的东西。

## 8. 剩余限制（如实登记）

| 项 | 说明 |
|---|---|
| 宿主日志**不在会话 JSONL 里** | 见 §1。用户用 pi 终端打开同一会话看不到这些任务；将来若要可见，需要 pi 提供官方的写 entry 通道（或允许薄层做「追加条目」桥接，那要过一次薄层准入评审） |
| 真实链路只取证了**单会话** | 「两会话并行不串数据」有单测（两个 sessionId 各自文件）与端点身份绑定单测；**多 runner 真并行**没跑 |
| 分叉（fork）未取证 | pi 的 `fork` 会新建会话 id，所以数据天然按分支隔离；但「分叉出的新会话该不该继承父会话的清单」没定也没测（当前行为：不继承，清单为空，旧条目若被 fork 复制则照旧显示） |
| `branchHead` 未落地 | 方案里写的是 `sessionId + branchHead + revision + operationId`；当前只用了 `sessionId`（pi 的分叉＝新会话，所以分支维度由会话 id 承担） |
| 模型会不会**长期**主动用任务计划 | 本片只证明「给它指令它就用、写了就显示」；主动使用率属于 S5 的真实运行验收 |
| `round` 依赖 pi 的 `get_entries` | 每次提交多一次 RPC（几十毫秒）。没做缓存，因为轮次算错的代价（历史分组错位）比这点延迟大 |

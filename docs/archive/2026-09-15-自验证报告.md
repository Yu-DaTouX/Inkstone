## 四、发现的问题

### 4.1 【真实缺陷·已修】截图/审阅脚本的 preload 路径指向不存在的 `index.mjs`

- **症状**：`npm run shots` 跑完打印 4 个 `✓`，但产出的 PNG 全是**空白**（每张 8459B，1802×1128 纯背景），
  并附带报错 `汉字格宽 = 12.50px ⚠️ 字体未生效`。
- **根因**：构建产物是 `out/preload/index.cjs`（`electron.vite.config.ts` 明确注释：sandboxed preload 不支持 ESM），
  但三个脚本仍写 `out/preload/index.mjs`：`scripts/shot.mjs:40`、`scripts/shots.mjs:96`、`scripts/live-preview.mjs:16`。
  preload 加载失败 → `window.yan` 不存在 → 渲染端白屏 → `capturePage` 只能拿到背景色。
- **影响**：README 预览图 / UI 审阅图的整条生成链路失效，而 `✓` 输出会让人以为成功。
- **修复**：三处改为 `out/preload/index.cjs`（并注明原因）。修完字体断言立即变回 `15.00px (Maple 已生效)`；
  紧接着又暴露出 §4.2。
- **证据**：`%TEMP%\yan-verify\shots3`（空白）→ 修复后 `shots5`（275–387KB 有内容）。

### 4.2 【真实缺陷·已修】`shot-fixture.js` 缺 `settings.projects` 让 React 整棵树卸载

- **症状**：preload 修好后截图仍空白，`#root` 子元素数 = 0，DOM 只剩 10 个节点。
- **根因**：注入 fixture 后渲染进程抛
  `Uncaught TypeError: Cannot read properties of undefined (reading 'find')`（`out/renderer/assets/index-*.js:51595`，
  对应源码 `Composer.tsx:71` 一类 `s.settings?.projects.find(...)` —— `settings` 存在但 `projects` 缺失）。
  fixture 的 `settings` 对象没有 `projects` / `projectGroups` 字段（`scripts/shot-fixture.js:29`），
  于是任何一个读它的组件抛错，**没有 ErrorBoundary 兜底** → React 卸载整棵树 → 白屏。
- **修复**：fixture 补 `projects: []` / `projectGroups: []`。修完 4 张图正常（275–387KB）。
- **产品侧观察（未改，供决策）**：
  1. 应用**没有 ErrorBoundary**：任意渲染异常都是整屏白屏，用户看不到任何提示，也不会有"重新加载"出口。
  2. `Composer.tsx:71`、`FileTree.tsx:57`、`store.ts:1332` 用 `settings?.projects.find(...)` 而不是
     `settings?.projects?.find(...)`。真实路径下 `settings.projects` 一定存在（实测：真实实例 `hasProjects: true`），
     所以这不是线上 bug；但它让"状态缺一个数组"直接升级为白屏。**建议**：加 ErrorBoundary，或在这几处补一级可选链。
- **证据**：`%TEMP%\yan-verify\diag.log`（含 console 错误与 `nodes:10` dump）。

### 4.3 【探针失效·已修】3 个场景的断言与当前实现契约不符

| 探针 | 失效原因 | 修法 |
|---|---|---|
| `tokens` | 期望 `pct.toFixed(1)` / `≥99.5% → ≈100%`，而 `shared/turns.ts` 的 `formatHitRate` 是"**截断**到两位小数、只有原始比例 == 100% 才显示 100%"（用户明确要求"不要显示约等于"） | 期望值改成与 `formatHitRate` 同规则 |
| `projectlimit` | 探针用 `store.setState({session:{...cwd}})` 指定"当前项目"，但 `Rail.tsx:247` 的判定是 `activeProjectId ?? currentSummary?.projectId` —— 隔离环境里真实 runner 自带 `projectId`，改 `cwd` 根本不动"当前项目"（于是 11 条断言全红，`实际 11` 个项目全展开） | 新增 `pinCurrentProject()`：清空 `runners` + 给 `sessions` 挂目标 `projectId`，再设 `cwd` |
| `railmini` | 同上，另外断言文案"（不是第一个）"与实现相反 —— 实现**故意把当前项目置顶**（`Rail.tsx:364`） | 用同一个 `pinCurrentProject()`；文案改为"当前项目会被置顶" |
| `ask` | 探针等 `.modal` / `.modal-option`，而 `select/confirm/input/editor` 已改成输入区上方的**非模态面板**（`QuestionPanel`，`data-testid="question-panel"`）；`.modal` 只留给需要用户接管的场景 | 改用面板契约（`question-panel` / `qpanel-option` / `qpanel-title`），并同时断言**模态**不出现 |

> 这类"探针与实现脱节"在 HANDOFF 里已有先例（曾一轮修好 6 个）。判定原则：
> **先读实现、再改断言**，不要为了让测试变绿而弱化语义 —— 本次每组断言都保持了原有强度（甚至更准）。

### 4.4 【探针误判·已修】`queue` 把"撤回被正确拒绝"误判成"撤回成功但文本丢失"

这是本轮最值得记录的一处，因为它一开始像**严重产品缺陷**（用户排队的文本消失）。

- **表面症状**：`✗ 撤回文本回到输入草稿`、`✗ 排队文本被放回输入框`，`queueRestore=null`、草稿为空。
- **排查过程**（每一步都留下了日志）：
  1. 怀疑探针读的是 stale DOM → 改成每次重新查 `[data-testid="composer"]`：
     `{text:"",count:1,same:true,connected:true}` → **节点没换、就是空的**，排除 stale。
  2. 怀疑会话身份迁移触发 Composer 重新 hydrate 草稿（`activeRuntimeKey` = `sessionId ?? run:<id>`）→
     采 `sessionId` / `runnerSessionId` / `activeRunnerId`：撤回前后**完全一致**，排除。
  3. 采样时间线（每 60ms 记录 `queueRestore` 与草稿值）：只有 `t=0 qr=null v=""`，之后 1.2s 内**零变化**
     → 结论：`queueRestore` **从未被设置**，不是"设置了又被覆盖"。
  4. 回到主进程代码：`removeQueued` 用 `clear_queue` 拿回剩余文本重建队列；若目标 `queueId` 已不在返回队列里，
     返回 `{ok:false, error:'消息已被 pi 接收，无法撤回'}`。store 侧失败路径**只弹提示、不设草稿**。
- **真相**：免费模型回得很快，**在探针点击"撤回"之前就把第一条 follow-up 收走了** → pi 侧已无这条 →
  撤回被明确拒绝（UI 提示"消息已被 pi 接收，无法撤回"）→ 草稿当然为空。**产品行为是正确的。**
- **探针真正的错误**：用**旧 queueId** 判断"移除了"（恢复队列后 id 是新生成的），于是把"拒绝"误判成"成功"，
  再拿空草稿报红。修法：按 **notice 文案**判定两种合法结果（`已撤回排队内容` / `已被 pi 接收`），
  各自断言各自的契约；Esc 回收断言只在"pi 侧仍有排队"时才要求文本回收。
- **副产品**：修好后连续两次通过，并证明**中止回收本身完全正常**（Esc 后草稿 =
  `"插话一：这段再短一点\n插话二：最后加一句总结"`，队列清空、光标消失、助手消息保留）。
- **对 N09 的提示**：真实模型下"撤回单条"经常落到"已被接收"分支。产品已给明确提示 ✓，
  但 UI 仍把这类消息显示在"排队中"列表里（主进程队列快照落后于 pi 的真实消费）——
  建议 N09 收敛时用"已被接收 → 立刻从队列行移除并标明已发送"的展示。

### 4.5 【外部能力边界】`image` 场景：前端链路全绿，免费模型不认图

- 通过 12 项：生成图 → 附件就绪 → 缩略图 → 发送后清空 → 新增消息 → 用户消息渲染缩略图 →
  data URI → 会话历史带图 → `mimeType` → base64 完整 → …
- 唯一失败：`★ 模型认出了红色`。LongCat-2.0:free 回答"抱歉，你发的图片我这边看不到（当前环境不支持接收图片）"。
- **定性**：模型能力边界，不是产品缺陷。要完成这项验收需要视觉模型
  （`TESTING.md` 写的默认是 `commandcode/deepseek/deepseek-v4.1-flash`，本轮未获授权使用）。
- **未验证项**：图片经 pi 真实传给视觉模型并被正确理解 —— **仍待视觉模型下复验**。

### 4.6 【已核查·不是问题】三处初判为 UI 错误的地方

为避免后人重复误报，这里把"看着像 bug、实测不是"的结论留下：

| 初判 | 实测证据 | 结论 |
|---|---|---|
| 深色主题下用户消息有"蓝色描边"，浅色没有 | `borderWidth: "0.8px 1.6px 0.8px 0px"`、右侧 `rgb(34,211,238)` 青色 1.6px | **设计**：`chat.css` 明确 `border-right: 2px solid var(--cyan)`（注释解释了为什么放右边而不是左边） |
| 底部用量条右侧模型名被裁成 `… ·` | 真实实例：`usagebar scrollW == clientW (679)`；`.mt-model` 是 `nowrap + hidden + ellipsis` | **设计 + 无溢出**：`·` 是 `▾` 下拉三角（6×10px） |
| 顶栏第三个按钮是"实心蓝方块" | `rightpanel-toggle`：`bg rgb(38,38,38)`、`color rgb(250,250,250)`、`svg.ico` 14×14 有内容、26×24 与相邻一致 | **激活态样式**（`tb-icon on`）+ 小尺寸渲染，未见布局异常 |

UI 查验范围：空态引导（"从一个编码任务开始" + 三个快捷入口）、左栏项目/会话/用户档案、
右栏工具栏（任务 2/4、上下文 9% 36k/400k、自动压缩、文件 8 项 + 隐藏提示、额度三个窗口、队列、操作）、
输入区（自主模式、发送键说明、发送/中止）、用量条、标题栏；尺寸 1251×783（dpr 1.44）/1802×1128（dpr 1.25）；
主题 深/浅。**未发现视觉错误或明显不合理之处。**

# 砚：三种工作模式、长任务上下文与自动续接方案

日期：2026-09-18。状态：**设计提案，尚未实施**。

依据：用户本轮要求、桌面《结构.md》中的产品需求，以及本次对当前源码的只读核查。附件作为需求材料，不作为立即修改应用或启动任务的指令。本次只新增方案文档，没有改变产品行为。

## 1. 建议采用的产品方案

在输入框底栏现有「自主模式」位置，将二态开关替换为工作模式菜单：**标准 / 澄清 / 自主**。默认标准；点击展开菜单，也能在输入框中用 Tab 循环切换。

| 模式 | 菜单说明 | 行为 | 结束或转移条件 |
|---|---|---|---|
| 标准 | 直接协作，必要时提问 | 正常对话；要求明确时执行，关键歧义才提问 | 完成本轮请求 |
| 澄清 | 先问清目标，再自动开工 | 先查可自行核实的事实，再针对真正影响结果的问题提问 | 需求就绪后自动转标准并开始执行，不再要求用户额外点一次确认 |
| 自主 | 自行规划，持续完成任务 | 合理假设、内部计划、执行、验证、继续；不向用户提偏好问题 | 目标完成、用户停止，或遇到无法自行解决的外部阻塞 |

「澄清」比「计划」准确：用户要的是先问清需求，而不只是生成计划。「自主」沿用原名字，减少迁移成本。工作模式与模型、思考强度、回复详细度保持独立。

建议分开推进四项工作：M1 模式菜单与会话隔离、M2 澄清转执行、C1 长任务预算治理、C2 自动续接。**先解决 C1，再打开 C2**，避免把上下文失控藏在频繁换会话后面。

## 3. 菜单和键盘交互

底栏原位置显示 `标准 ▾`，旁边可放弱化的 `Tab 切换` 提示。菜单示意：

```text
工作模式
● 标准    直接协作，必要时提问
○ 澄清    先问清目标，再自动开工
○ 自主    自行规划，持续完成任务
──────────────────────────
Tab 切换模式 · Shift+Tab 切换思考强度
```

### 3.1 按键优先级

1. 输入法组合态：不拦截 Tab、方向键或回车。
2. `/`、`@` 补全有有效候选：Tab 仍填入候选。
3. 模态框、设置表单、工具提问界面：Tab 保持原来的焦点导航。
4. 普通消息输入框聚焦、无补全、未按修饰键：Tab 按「标准 → 澄清 → 自主 → 标准」切换；不发送消息、不改变草稿与选择区。
5. 长文编辑模式默认保留编辑/焦点行为，不抢 Tab；可点击底栏菜单切换。
6. 模式菜单打开时，方向键移动、Enter/Space 选择、Esc 关闭并返回触发按钮；Tab 离开菜单，避免困住焦点。

快捷键设置提供「Tab 切换工作模式」开关，默认开启；关闭后恢复原焦点行为。输入框另提供明确的键盘离开方式，例如 Esc 将焦点移至模式按钮（先让补全菜单处理 Esc）。菜单使用可访问的单选菜单语义，并以 `aria-live` 宣告模式改变。Shift+Tab 原功能不变。

运行中切换显示「下一轮生效」，不撤销已开始的工具调用。待发送消息保存模式快照；已经入队的消息不被后续 Tab 偷改。必要的模式立即中止由用户停止任务完成，不用模式切换冒充取消。

颜色、间距、焦点样式沿用现有令牌。只有自主且任务实际运行时呈现运行光带；澄清等待回答不能显示成持续执行。新增令牌必须先写 [DESIGN.md](../design/DESIGN.md)。

## 4. 模式状态与数据设计

建议引入 `WorkMode = 'standard' | 'clarify' | 'autonomous'`，主进程管理真值，渲染端只显示和发送意图。

| 状态 | 作用域 | 建议内容 |
|---|---|---|
| 新会话默认模式 | desktop.json | `defaultWorkMode`，与现有全局布尔迁移关联 |
| 当前模式 | 稳定会话 ID；首条消息前用临时 runner ID | `workMode`、`revision`、`pendingMode` |
| 单次工作目标 | `goalId`，不等于每条消息 | 用户目标、约束、验收标准、已答问题、当前阶段、停止状态 |
| 续接控制 | `goalId + segmentId` | 成功自动压缩计数、交接事务、前后会话引用、续接次数 |

旧数据迁移：`autonomous:true → autonomous`，其余 → standard；新字段存在时优先新字段。完成迁移后内置扩展不再各自以全局 `autonomous` 决策，旧字段仅保留兼容读取入口，避免双真源。

建议为每个 runner 提供隔离的控制文件路径，由主进程原子写入，扩展按请求读取；复用现有设置文件机制的实现经验，但不能让 A 会话更改 B 会话。确切传输选型需先验证 pi 扩展与主进程已有桥接能力；如用本地桥接，必须校验 runner 身份和 revision。不要假定 RPC 已支持自定义模式命令。

新会话继承默认值；恢复会话读取自己的模式；澄清自动转标准只改当前会话。跨会话续接保持 goalId、自主模式和授权范围；切换项目、分叉、远程发消息均须携带明确目标身份。用户停止优先于所有自动继续，迟到回调不得复活任务。

## 5. 澄清模式：如何落实「95% 把握」

95% 只能是模型对需求理解的自评，**不代表 95% 的成功概率**。不在界面做虚假的精确成功率进度条。开工门槛采用「自评 ≥0.95 + 必填项齐全 + 无关键冲突」。

必填检查项：目标与交付物、范围与明确不做的内容、关键输入、约束、验收方式。可从代码/文件核实的信息先自行查；用户已经说过的信息不重复问。低影响细节可列为明确假设，不为凑 95% 反复提问。

每次通常问一个关键问题，提供 2–4 个具体选项并允许自由回答；相互独立的问题可在同一轮展示。问题要说明为什么影响结果。沿用 `question` 与 `UiBridge` 交互，不重做任务面板。

状态流：`收集事实 → 提出关键问题 → 等待回答 → 校验就绪 → 切换标准 → 执行`。

建议新增受控工具 `clarification_ready`（名称为提案），提交：`goalId / modeRevision / confidence / objective / deliverables / constraints / acceptance / assumptions / unresolvedCritical`。主进程做 schema、身份、过期版本及待答问题校验；字段齐全不能证明语义理解正确，因此验收还需真实模糊需求场景。

校验通过后落盘并显示「需求已明确，已切换标准，开始执行」，自动继续一次，不再问“是否开始”。若当前 pi 工具循环无法刷新模式提示，则在安全回合边界结束澄清轮，再由宿主发送一次有幂等键的内部续行请求；不能假设修改设置就会重跑当前轮的 `before_agent_start`。

澄清阶段允许读文件、查代码等事实核实；不执行实现类修改。不能只禁用 write/edit 就宣称只读：bash 和第三方扩展也能写。第一阶段必须使用明确的只读工具白名单，未经审查的终端/扩展工具不在澄清阶段开放。

现有 `question.js` 在取消/失败时返回「自行假设并继续」：标准模式可保留；澄清模式中关键问题取消应保持未就绪，不能自动执行。无界面、网络失败、用户迟迟不答也不视为回答。用户主动改成标准/自主则结束澄清门槛，按新模式继续。

## 6. 自主模式：从「不提问」到持续交付

现有提示词只要求自行假设并完成任务，不等于宿主已实现「直到目标完成」。建议增加轻量 goal 状态：`planning / executing / verifying / completed / blocked / stopped`。

模型先建立内部步骤和验收条件，执行后检查遗漏；若未完成且可推进，继续下一步。不要改用户扩展任务清单的格式或现有任务面板。建议受控结果工具上报完成证据或阻塞原因，宿主禁止仅凭普通回复末尾“完成了”把 goal 标为 completed。

不向用户提偏好问题；遇到选择就采用合理、可逆方案并简短说明假设。不扩大用户授权范围；缺凭证、外部服务不可用或必须依赖用户才能解决时，保留进度并报告阻塞，不编造答案、不无限重试。此类阻塞汇报不是再抛一串澄清问题。

建议默认连续两次同类失败转 blocked，避免空转；有明确的新输入或可验证的新策略才重试。继续请求必须绑定 goalId、最后消费的会话条目和幂等键。用户发新消息时先合并约束，停止/取消则废弃尚未提交的自动续行。

## 7. 长任务为何可能远超上下文限制

### 7.1 可以从源码确认的机制

默认工作集公式为：

```text
responseReserve = max(16k, min(32k, window × 25%))
safetyMargin    = max(8k, window × 2%)
workingSet      = min(240k, window × 70%, window − responseReserve − safetyMargin)
```

240k 是默认 cap，用户/模型级覆盖会改变生效值。`evaluateContextPolicy` 在 `agent_settled` 后判定，且 busy 时不触发；因此一条用户消息引发几十轮工具调用时，砚可能还没走到这道判定。清理历史工具结果并不保证本轮新产生的大结果足够小，状态生成器也在 settled 边界。

`src/main/compaction.ts`、agent.ts 的部分注释仍描述 pi 按窗口减 reserveTokens 兜底，而当前 HANDOFF 记载 pi 0.85.1 的旧回合结束触发前提已过期。**这两者不能同时当成已经验证的保证**：实施前必须按实际装载版本核对 pi 调用链和真实行为；本方案不把那条旧注释当可靠兜底。

### 7.2 还不能确认的个案原因

本轮没有用户出问题会话的逐请求日志，因此不能断定每次超限都是同一缺陷。还应区分：会话累计用量 vs 本次输入；供应商实际 input usage vs 本地估算；清理前 vs 变换后的工作集；缓存输入是否已经包含在供应商 input 里。重复累计缓存 token 会造成显示假超限，未计入系统提示、工具定义、图片则可能低估真实输入。以上是排查项，不是本轮证实的 bug。

### 7.3 建议的治理方案

增加请求前预算门，评估即将送出的系统提示、工具 schema、变换后消息、图片估算及输出预留。用最近一次供应商实际用量校准估算；估算不是精确 tokenizer，界面必须标注来源、时间与估算状态。

达到预警线时清理旧结果；仍越工作集线时，在完整工具调用/结果对的边界安排压缩或续接；接近物理窗口时阻止继续发送已知超预算请求。工具结果使用有界摘要和可召回原文，单个超大输入在发送前明确提示，而不是静默删掉用户关键要求。

不能在 `before_provider_request` 中递归调用 compact、等待自身结束而形成死锁。先验证当前 pi 的 hook 是否允许取消请求、在哪个工具循环边界允许压缩。若当前 RPC 不具备安全暂停点，需通过受支持的 pi 升级/扩展能力补齐，再实现硬门；不得修改生成目录 resources/pi-runtime。过渡版只能如实称「预警与软预算」，不能声称硬封顶。

诊断至少记录：requestId、runner/session/goal、模型窗口、生效预算及来源、估算构成、供应商用量、是否 busy、清理前后数值、压缩触发/跳过原因。默认不写完整正文与凭证。界面分别显示「当前工作集」「目标预算」「模型窗口」，超限但等安全边界时明确显示正在等待，而不是假装压缩已完成。

## 8. 第三次自动压缩前移交新会话：评估与方案

### 8.1 是否有用

**有条件地有用，建议作为自主长任务的可配置续接策略。** 它能让新片段只携带当前目标、约束、证据和下一步，减少旧摘要反复叠加。但不能保证模型更聪明，也不能解决单轮巨量工具输出；反复交接反而可能遗漏细节、增加模型调用与缓存重建成本。

推荐遵循用户提出的默认节奏：当前自主片段内成功自动压缩两次后，下一次正常策略压缩需求出现时，优先交接。不是“压缩完第三次再交接”，也不是“累计三次任何清理就换”。

计数只包含**成功的自动完整压缩**，包括去重后的 policy/原生自动事件；手动压缩、清理、状态刷新、失败、取消和重复事件不计。计数按 goal 的 session segment 持久化，重启不归零；成功移交的新片段从零开始。原生自动事件若无法在开始前拦截，就让该次压缩安全完成后安排交接，并显示实际次序，不能谎称已提前接管。

### 8.2 触发条件

自主模式、goal 未完成、两次成功自动压缩、下次正常压缩待触发、完整工具对已落盘、没有待答交互/未完成外部写动作，且源水位未变化。后台子代理/长命令尚未结束时先等待或有证据地登记接管；第一阶段建议等待，不把它们遗弃。

物理窗口紧急保护优先于交接。摘要预算不足时先安全压缩，不能为了严格凑“第三次之前”把当前任务弄崩。默认自动续接最多连续 3 次作为防循环建议值，达到后停在可恢复状态并报告原因；可在高级设置调整，不代表任务完成。

### 8.3 交接包

结构化保存：原始用户目标与相关原话、有效约束与授权范围、已完成及验证证据、未完成步骤、失败尝试及原因、当前文件/分支/工作树状态、运行进程状态、最近用户补充、模型/工作模式、来源会话与条目水位、可召回引用和附件引用。

建议摘要目标 4k–8k tokens，并按目标模型窗口动态缩小；硬约束和用户最近要求不能静默裁掉。超预算时抽取可核对的引用，必要时判交接不可用并保留原会话。TaskState 只能作为有水位与 freshness 的材料，不是已经验证的新事实。继续工作前重新核对文件、Git 和命令状态，避免照着过时摘要重复执行。

现有 `ctx://` 引用可能绑定原会话，不能直接复制字符串就假设新会话可读。新增受限来源解析：由主进程按同一 goal 的显式来源关系授权只读召回，绑定源会话和 entryId；测试删除/移动源文件及路径越界。不恢复旧 `get_tree` 浏览功能，也不恢复已移除的记忆模块。

### 8.4 可靠移交事务

```text
pending → snapshot → validate → destination-created → committed → resumed
                           ↘ failed：保留源会话，按条件恢复或回退压缩
```

1. 主进程锁定当前 goal 的调度，停止派发新工作，等待在途工具落盘。
2. 保存 sourceHead、生成交接包并做 schema/引用/预算校验；源有新消息则作废重建。
3. 创建同项目、同 cwd 的新会话，写来源关系和交接包；新 runner 此时不执行。
4. 原子提交 activeSegment；旧 runner 释放 cwd 写入占用，新 runner 才获得执行权。不能绕过 RunnerRegistry 的同 cwd 并发防线。
5. 用唯一 resumeId 自动发送一次继续请求；收到实际消费确认后记为 resumed。
6. 任一步失败不删旧会话，不清用户工作区；以事务日志在重启后恢复，禁止两侧同时继续。

停止指令使事务失效。用户在交接期间发消息必须按主进程序号转入最终生效片段并只消费一次；附件副本和权限需重新绑定验证，不继承不明权限。断电发生在“发送成功、确认未落盘”之间时，通过 JSONL 的 resumeId/消费证据去重，不能盲目再发。

### 8.5 用户看到的结果

保留旧会话并显示「已续接至 ××」，新会话显示「接续自 ×× · 第 2 段」与简短交接摘要。只在用户正在看源会话时自动跟随；用户已切到别处则只标记未读，不抢窗口。历史仍读取各自 JSONL，不伪装成所有旧消息都仍在模型上下文中。

## 9. 当前 agent 提示词清单

这是**源码层可确认的构成**，不是本轮某个实际 provider 请求的完整抓包。没有读取私人配置或枚举用户安装的所有包，因此外部自定义提示词只列加载来源，不声称已穷尽。主对话并不是只有一份固定提示词。

### 9.1 普通对话与自主模式（现有原文）

来源：[question.js](../../resources/pi-extensions/question.js)，`before_agent_start` 追加。

```text
Interactive questions:
- If a request is genuinely ambiguous, or you are about to guess at a choice that materially changes the result, call the `question` tool and ask BEFORE doing the work.
- Ask only when the answer changes what you build; do not ask about trivia or things you can verify yourself.
- Give 2-4 concrete options. The user can also pick the custom/typed answer.
- Keep it to one question at a time unless several are truly independent.
```

自主模式时替换为：

```text
Autonomous mode is ON:
- Do NOT ask the user questions, and do NOT call the `question` tool.
- Make a sensible assumption, state it in one line, and carry the task through to completion.
- Prefer reversible choices when several options are plausible.
```

即使模型仍调用 question，工具也返回自行决定并继续的说明。因此已有“不弹提问框”的代码兜底；自然语言回复是否夹带问题仍是模型遵循问题。

### 9.2 语言与回复详细度

来源：[language.js](../../resources/pi-extensions/language.js)：

```text
zh-CN: 推理（思考过程）与回复一律使用简体中文，即使用户用其他语言提问也不要切换。
en-US: Think (reason) and reply in English, even if the user writes in another language.
```

同一句在 `before_agent_start` 追加到系统提示，并在 `before_provider_request` 放到最后一条 user 前；不是两套语言要求，也不使用主会话启动参数 append-system-prompt。保留模型返回原文。

来源：[response-detail.js](../../resources/pi-extensions/response-detail.js)：

| 档位 | 当前提示内容摘要 |
|---|---|
| standard | 不追加提示 |
| brief | 先给结果和改动；解释仅保留建立信任所需内容；仍报告错误、阻塞和用户决策；简短不缩减任务范围 |
| detailed | 补充关键取舍、步骤、适用例子和边界；仍报告错误、阻塞和用户决策；详细不扩大任务范围 |

### 9.3 子代理

来源：[index.ts](../../src/main/index.ts) 的 `SUBAGENT_SYSTEM_PROMPT`，由 [subagents.ts](../../src/main/subagents.ts) 以 `--append-system-prompt` 传给子进程：

```text
You are a subagent working on one focused task inside a larger project.
- Work autonomously: do not ask the user questions; make reasonable assumptions and state them.
- Keep the scope to the task you were given.
- Finish with a concise report: what you changed or found, and how you verified it.
```

它属于子代理，不应和主会话自主模式开关混为一谈。

### 9.4 上下文专用调用与注入

| 来源 | 当前要求/作用 | 是否是主对话常驻提示 |
|---|---|---|
| [context-producer.js](../../resources/pi-extensions/context-producer.js) `PRODUCER_SYSTEM_PROMPT` | 只输出 JSON 工作状态；目标、阶段、约束、决策、完成项、失败、未解决、下一步；只引用 citable_entries；不编造文件/命令/测试；约束来自用户；值使用用户语言；完成的旧片段可产 episode | 否，独立状态生成调用；结果经校验后可能注入主上下文 |
| [context-deep.js](../../resources/pi-extensions/context-deep.js) `DEEP_SYSTEM_PROMPT` | 中文最多 12 行，每行 `- `；保留目标进度、事实决定、文件命令、未解决和下一步；不确定标未确认；无内容回复“无” | 否，Deep Context 的独立调用，默认关闭 |
| [context-transform.js](../../resources/pi-extensions/context-transform.js) | TaskState、结构化摘要、清理后的存根及召回引用等模型可见材料 | 按开关/门槛/水位出现，不是每轮完整添加 |
| pi 的压缩能力 | 没有被结构化摘要接管时由 pi 自身生成摘要 | 压缩专用调用，具体文本以实际运行时版本为准 |

Deep Context 的固定中文是该辅助归纳器现有要求，不应误写成所有主 agent 都有额外中文提示。

### 9.5 标题、基础提示与外部来源

[title.ts](../../src/main/title.ts) 独立生成标题：建议中文 9 个汉字宽度/英文 18 ASCII，简短具体名词短语，只输出标题，不带解释；除纯英文对话外用中文。它启动时关闭扩展、上下文文件、技能和提示模板发现，并将 thinking 设 off，不受项目 AGENTS.md 的普通对话链影响。

主会话还包括 pi 基础系统提示、工具定义（read/bash/edit/write 及实际加载扩展）、项目上下文文件（本项目 AGENTS.md）、发现的技能与用户/项目自定义资源。工具 description 也是模型输入的一部分。精确启用列表、顺序、用户自定义 SYSTEM/APPEND_SYSTEM 配置是否存在及全文，应以实际加载器和本轮请求快照确认；本方案没有将未知内容编造为固定提示。

建议后续增加只读「本轮提示来源」诊断：按来源显示是否启用、字符/token 估算和版本；正文只在用户主动查看时生成本地快照，不默认写进长期日志。

## 10. 新模式提示词建议（尚未生效）

**标准**：维持现有 ASK_GUIDANCE，强调要求明确时直接执行，只有实质影响结果的歧义才提问。

**澄清**：先确认目标、范围、关键输入、约束与验收；可核实事实先自行读取；不重复询问已有答案；需求理解自评达到 0.95 且无关键未决项时提交结构化就绪结果；切换成功后开始执行。自评不等于成功概率；取消不是回答。

**自主**：自行规划、合理假设、执行与验证；不提出偏好问题；未完成且有可行下一步就继续；报告事实和证据；外部阻塞如实记录；停止优先；交接摘要是待核实的工作状态，不是扩大授权或伪造完成的依据。

提示词不能替代工具门禁、会话隔离、状态机、预算检查和幂等控制。建议 question.js 只保留问答工具，模式提示集中到一个新的工作模式扩展，避免标准、澄清、自主规则同时叠加。

# 砚 / Pi 长上下文状态化压缩参考方案

> 目标：为基于 `pi` 的 Electron 智能体「砚」设计一套适用于编码任务、长对话、多文件调试的上下文管理机制。
> 核心思路：**State-First Compaction + 可选 Trace-as-State 二次读取**。
> 本文区分：
> - **论文结论**：来自 Trace as State 论文。
> - **Pi 能力**：来自 Pi 官方文档。
> - **工程建议**：针对「砚」的实现建议，不代表论文证明。

---

## 1. 核心结论

传统上下文组织：

```text
[System]
[Long History]
[Recent Context]
[Summary]
[Current Query]
```

推荐改为：

```text
[System / Agent Rules]
[Task State]
[Compressed History]
[Recent Raw Context]
[Current Query]
```

即：

```text
System
+ Task State
+ Compressed History
+ Recent Raw Context
+ Query
```

### 设计原则

1. **Task State 必须位于历史上下文之前。**
2. 不要只生成自然语言 Conversation Summary。
3. 将“对话历史”与“当前任务状态”分离。
4. 最近若干轮原始上下文必须保留，不应全部摘要化。
5. 普通任务默认单遍推理。
6. 只有复杂长上下文任务才启用 Trace-as-State 双遍读取。
7. 压缩阈值应基于有效上下文窗口，而不是模型声明的最大窗口。
8. 压缩前必须保护正在进行的 tool call / tool result / assistant turn 边界。

---

# 2. 为什么需要 Task State

长上下文问题不只有“信息太多”。

另一个关键问题是：

```text
模型第一次读到某段信息时，
可能还不知道后面的任务要求会让这段信息变得重要。
```

在 causal Transformer 中：

```text
token1 -> token2 -> token3 -> ... -> tokenN
```

前面的 token representation 不会因为后面出现的新任务条件而被重新编码。

因此：

```text
Data -> Condition
```

可能明显差于：

```text
Condition -> Data
```

Trace as State 的核心思路是：

```text
Pass 1:
Long Context + Query
    ↓
Reasoning Trace / State

Pass 2:
State + Long Context + Query
    ↓
Final Answer
```

也就是：

```text
[T, X, Q]
```

而不是：

```text
[X, T, Q]
```

论文实验显示，在多个模型和长上下文任务上，将 reasoning trace 前置通常显著优于将 trace 追加到末尾。

# 3. 推荐上下文结构

最终送入模型的上下文建议固定为：

```text
┌──────────────────────────────────────┐
│ 1. System Prompt / Agent Rules       │
├──────────────────────────────────────┤
│ 2. Task State                        │
├──────────────────────────────────────┤
│ 3. Compacted Historical Context      │
├──────────────────────────────────────┤
│ 4. Recent Raw Context                │
├──────────────────────────────────────┤
│ 5. Current User Request              │
└──────────────────────────────────────┘
```

推荐顺序：

```text
SYSTEM
TASK_STATE
HISTORICAL_CONTEXT
RECENT_RAW_CONTEXT
CURRENT_QUERY
```

禁止默认使用：

```text
SYSTEM
HISTORY
RECENT
SUMMARY
QUERY
```

# 4. Task State 数据模型

建议将 Task State 作为独立结构维护，而不是单纯拼接自然语言摘要。

```ts
interface TaskState {
  version: number;

  objective: string;

  constraints: string[];

  userDecisions: string[];

  confirmedFacts: string[];

  architecture: Record<string, string>;

  activeFiles: {
    path: string;
    status: "read" | "modified" | "created";
    purpose?: string;
  }[];

  completed: string[];

  inProgress: string[];

  unresolved: string[];

  hypotheses: string[];

  errors: {
    message: string;
    suspectedCause?: string;
    status?: "open" | "resolved" | "unknown";
  }[];

  nextActions: string[];

  criticalContext: string[];
}
```

## 示例

```yaml
task_state:
  version: 12

  objective:
    实现基于 pi 的 Electron Agent 长上下文管理

  constraints:
    - 保持 pi 插件兼容
    - 不破坏现有 JSON-RPC
    - 最近工具调用必须保留原文
    - 压缩不能切断 tool call / result 对

  user_decisions:
    - Task State 位于历史上下文之前
    - 普通模式不做完整二次读取
    - 复杂任务允许增加推理时计算量

  architecture:
    runtime: pi
    frontend: Electron
    transport: JSON-RPC
    context_engine: state-first-compaction

  active_files:
    - path: src/main/agent.ts
      status: modified
      purpose: Agent runtime

    - path: src/main/context-manager.ts
      status: created
      purpose: Context management

  completed:
    - 确认 State-First 上下文结构

  in_progress:
    - 实现 compaction hook

  unresolved:
    - 每个模型的有效上下文阈值
    - Deep Context Mode 自动触发条件

  hypotheses:
    - 状态前置可以减少长上下文中的条件顺序问题

  next_actions:
    - 实现 TaskStateStore
    - 接入 session_before_compact
    - 加入 context hook
    - 建立 A/B benchmark
```

# 5. Task State 与 Summary 的区别

## 不推荐

```text
用户正在开发一个 Electron 应用。
之前讨论了 Pi、上下文压缩以及浏览器控制。
用户希望优化长上下文能力。
```

这种摘要存在的问题：

- 缺乏当前执行状态
- 缺乏明确约束
- 缺乏文件状态
- 丢失决策来源
- 丢失未解决问题
- Agent 很难直接继续执行

## 推荐

Task State 应回答：

```text
现在要做什么？
已经完成什么？
当前做到哪里？
哪些决策已经确定？
哪些内容不能改变？
有哪些文件正在工作？
当前错误是什么？
有哪些未验证假设？
下一步应该做什么？
```

# 6. 推荐的上下文生命周期

建议采用多阶段管理，而不是达到某个 token 数后突然压缩。

```text
0% -------------------- 60%
Normal

60% ------------------- 75%
State Refresh

75% ------------------- 85%
Soft Compaction

85% ------------------- 93%
Hard Compaction

93%+ ---------------------
Emergency Compaction
```

> 上述百分比属于工程建议，不是论文结论。

---

# 7. 有效上下文窗口

不要直接使用模型声明的最大 context window。

例如：

```text
Model Context Window = 1,000,000 tokens
```

不建议：

```text
980K 才开始压缩
```

推荐引入：

```ts
effectiveContextWindow
```

例如：

```ts
effectiveContextWindow = Math.min(
  model.contextWindow * safetyRatio,
  userConfiguredCap
);
```

推荐初始配置：

```ts
const safetyRatio = 0.75;
const userConfiguredCap = 300_000;
```

对于 1M 上下文模型：

```text
Model Max          1,000K
Effective Window     300K

State Refresh        180K
Soft Compact         225K
Hard Compact         255K
Emergency            280K
```

注意：

**300K 是工程策略，不是论文证明的临界值。**

应该允许模型级 override。

# 8. 压缩流程

推荐：

```text
Old Context
     │
     ├── Extract / Update Task State
     │
     ├── Create Historical Summary
     │
     └── Preserve Recent Raw Context
```

形成：

```text
Task State
+
Historical Summary
+
Recent Raw Context
+
Current Query
```

## 推荐 token 分配

可作为初始值：

```text
Task State:
5K ~ 15K

Historical Summary:
10K ~ 30K

Recent Raw Context:
20K ~ 50K

Current Query + Working Space:
动态保留
```

Coding Agent 可提高 Recent Raw Context：

```text
普通任务:
20K ~ 30K

Coding:
30K ~ 50K

复杂 Debug:
40K ~ 64K
```

原因：

- 最近 tool call 很重要
- diff 很重要
- 编译器 / runtime 错误不能过度摘要
- 最近文件读取内容通常与当前修改强相关

# 9. Pi 的默认压缩能力

Pi 官方 compaction 已经提供类似基础设施。

Pi 默认配置示例：

```json
{
  "compaction": {
    "enabled": true,
    "reserveTokens": 16384,
    "keepRecentTokens": 20000
  }
}
```

Pi 默认压缩思想：

```text
旧上下文
    ↓
Structured Summary
    +
Recent Messages
```

其结构化摘要包含类似：

```text
Goal
Constraints & Preferences
Progress
  Done
  In Progress
  Blocked
Key Decisions
Next Steps
Critical Context
Read Files
Modified Files
```

因此推荐：

**不要推翻 Pi 的 compaction，而是在它之上实现 State-First。**

# 10. 使用 `session_before_compact`

Pi 提供：

```ts
pi.on("session_before_compact", async (event, ctx) => {
  // custom compaction
});
```

可访问类似：

```text
messagesToSummarize
turnPrefixMessages
previousSummary
fileOps
tokensBefore
firstKeptEntryId
settings
```

推荐在这里实现：

```text
messagesToSummarize
        │
        ├── Task State Update
        │
        └── Historical Compression
```

伪代码：

```ts
pi.on("session_before_compact", async (event, ctx) => {
  const { preparation } = event;

  const result = await buildStateAwareCompaction({
    messages: preparation.messagesToSummarize,
    previousSummary: preparation.previousSummary,
    fileOps: preparation.fileOps,
  });

  return {
    compaction: {
      summary: renderCompactionContext({
        taskState: result.taskState,
        history: result.historySummary,
      }),

      firstKeptEntryId:
        preparation.firstKeptEntryId,

      tokensBefore:
        preparation.tokensBefore,

      details: {
        taskState: result.taskState,
        stateVersion: result.taskState.version,
        readFiles: result.readFiles,
        modifiedFiles: result.modifiedFiles,
      },
    },
  };
});
```

推荐输出：

```xml
<TASK_STATE>
...
</TASK_STATE>

<HISTORICAL_CONTEXT>
...
</HISTORICAL_CONTEXT>
```

而不是只输出：

```text
Conversation summary: ...
```

# 11. 使用 `context` hook 保证 State 前置

Pi 支持在 LLM 调用前修改最终上下文。

推荐逻辑：

```ts
pi.on("context", async (event, ctx) => {
  const state = taskStateStore.getCurrent();

  return {
    messages: injectTaskState({
      messages: event.messages,
      state,
      position: "before-history"
    })
  };
});
```

Session 内部可以继续保存：

```text
history
history
compaction
recent
query
```

但真正发送给模型时改为：

```text
SYSTEM
TASK_STATE
COMPACTED_HISTORY
RECENT_RAW
QUERY
```

Task State 不必反复复制进 Session History。

# 12. State 更新策略

不要每轮完整重新生成 Task State。

建议使用：

```text
Existing State
+
State Delta
=
New State
```

模型每完成关键动作后，可以输出结构化 delta：

```json
{
  "completed": [
    "implemented context hook"
  ],

  "newDecisions": [
    "keep recent 40k tokens for coding mode"
  ],

  "newFiles": [
    {
      "path": "src/main/context-manager.ts",
      "status": "modified"
    }
  ],

  "resolved": [
    "how state is injected"
  ],

  "newUnresolved": [
    "benchmark threshold"
  ]
}
```

State Store 负责 merge。

推荐触发更新的事件：

```text
用户明确改变要求
架构决策确定
文件被修改
工具调用失败
测试结果变化
Bug 被定位
任务阶段完成
即将 compaction
```

# 13. Deep Context Mode

默认模式：

```text
Task State
+
Compressed History
+
Recent Raw
+
Query
        ↓
Single Inference
```

成本最低。

## Deep Context Mode

仅在复杂任务使用：

```text
PASS 1

Long Context
+
Query
        ↓
Reasoning Trace / Working State
```

然后：

```text
PASS 2

Working State
+
Long Context
+
Query
        ↓
Final Answer
```

即 Trace as State：

```text
[T, X, Q]
```

---

# 14. Deep Context Mode 触发条件

建议满足任一条件时考虑启用：

```text
context > 200K

需要跨大量文件推理

需要在几十万 token 中建立依赖关系

全仓库 debugging

architecture review

大型日志分析

第一次推理置信度低

模型多次来回读取旧文件

多个远距离证据需要组合

用户选择 High / Max Reasoning
```

不要对普通问答强制启用，因为它会：

- 增加延迟
- 增加 token 消耗
- 可能破坏 KV Cache 复用
- 增加模型调用次数

# 15. Reasoning Effort 映射

可以设计：

```text
Low
单次推理
仅使用已有 Task State

Medium
刷新 Task State
单次推理

High
1 次 Trace 生成
1 次 State-First reread

Max
多 Trace
Merge State
Final reread
```

例如：

```text
Max:

Trace A
Trace B
Trace C
   ↓
State Merge
   ↓
Merged State + Context + Query
   ↓
Final
```

Trace as State 论文中，多 trace 场景总体表现会继续改善，因此可以将其作为高推理预算模式参考。

# 16. Compaction 安全规则

必须保证：

```text
禁止从 tool call 中间切割
禁止将 tool call 与 tool result 分开
禁止从 assistant reasoning / output 中间切割
禁止删除当前正在使用的 diff
禁止摘要掉尚未解决的错误
禁止将用户明确约束降级为普通历史信息
```

优先保留：

```text
System / developer rules
Current Task State
User constraints
Recent user messages
Recent tool results
Active file contents
Current diff
Latest error logs
Pending plan
```

优先压缩：

```text
已完成且稳定的历史讨论
重复的工具输出
已解决的错误
旧版设计方案
重复文件读取
已经被新的决策覆盖的历史内容
```

# 20. 推荐的 Context Assembler

```ts
function assembleContext({
  system,
  taskState,
  historySummary,
  recentMessages,
  currentQuery
}) {
  return [
    system,

    {
      role: "system",
      content:
        `<TASK_STATE>\n${serialize(taskState)}\n</TASK_STATE>`
    },

    {
      role: "system",
      content:
        `<HISTORICAL_CONTEXT>\n${historySummary}\n</HISTORICAL_CONTEXT>`
    },

    ...recentMessages,

    currentQuery
  ];
}
```

实际实现需根据 Pi Message 类型调整。

# 21. 不要将 Task State 当永久事实

Task State 是：

```text
当前任务的工作状态
```

不是：

```text
用户长期记忆
```

它必须支持：

```text
新增
覆盖
修正
失效
删除
版本化
```

推荐：

```ts
interface StateEntry {
  value: unknown;
  status: "active" | "resolved" | "superseded";
  updatedAt: number;
}
```

防止旧决策污染后续推理。

---

# 22. 防止 State Hallucination

Task State 本身也可能产生错误。

建议重要字段附带 provenance：

```ts
interface StateFact {
  value: string;

  source:
    | "user"
    | "tool"
    | "file"
    | "model";

  confidence:
    | "confirmed"
    | "inferred"
    | "hypothesis";

  sourceId?: string;
}
```

例如：

```json
{
  "value": "RPC 使用 JSON-RPC",
  "source": "user",
  "confidence": "confirmed"
}
```

而：

```json
{
  "value": "EPIPE 可能由 child process 提前退出导致",
  "source": "model",
  "confidence": "hypothesis"
}
```

两者不能混为一谈。

建议 Coding 模式额外维护：

```ts
interface CodingState {

  activeBranch?: string;

  filesRead: string[];

  filesModified: string[];

  symbolsTouched: string[];

  commandsRun: string[];
```

这样 compaction 后 Agent 不需要重新猜：

```text

```

# 24. A/B 测试方案

不要只凭主观体验判断。

至少测试四种策略：

```text
A. Raw Long Context

B. Traditional Summary

C. State-First Compaction

D. State-First + Trace-as-State
```

测试任务：

```text
跨文件 Bug 定位
大型 refactor
多轮需求修改
旧决策召回
错误日志定位
架构一致性
长 session 继续开发
```

指标：

```text
Task Success Rate
Exact Match / Unit Test Pass Rate
错误修改率
重复读取文件次数
错误回滚次数
Token Usage
Latency
Compaction Frequency
State Accuracy
Lost Constraint Rate
```

尤其建议加入：

```text
Lost Constraint Rate
```

用于检测 compaction 后是否遗失用户要求。

# 27. 最重要的实现原则

如果只做一个改动：

> **不要再把 compaction 当成“生成聊天摘要”，而要把它升级成“恢复 Agent 可继续工作的任务状态”。**

即：

```text
Conversation Summary
        ↓
Task State
+
Historical Evidence
+
Recent Raw Context
```

对于编码 Agent 来说，目标不是：

```text
模型记得我们聊过什么
```

而是：

```text
模型在压缩之后仍然知道：
现在正在做什么、
为什么这么做、
已经改了什么、
什么不能改、
```

# 29. 结论

推荐「砚」采用：

```text
State-First Compaction
+
Recent Raw Preservation
+
Adaptive Effective Context Window
+
Optional Trace-as-State Deep Context Mode
```

默认路径：

```text
Task State
+ Compressed History
+ Recent Raw
+ Query
```

复杂任务路径：

```text
Pass 1:
Context + Query
→ Trace / State

Pass 2:
State + Context + Query
→ Final
```

这套设计兼顾：

```text
上下文连续性
长文推理能力
编码 Agent 状态恢复
Token 成本
延迟
Pi 兼容性
```

并且可以在不重写 Pi 核心的情况下，通过扩展层逐步实现。

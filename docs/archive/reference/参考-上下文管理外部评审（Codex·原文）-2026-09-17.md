## 二、Codex 的回答（原文）

## 1. 对外部评审的总体判断

- **同意** TaskState 是可重建视图、精确水位会造成可用性悬崖、应采用 Hybrid Producer，以及优先补
  State Producer + Freshness Protocol；这些直接解决当前"状态永远不生成、压缩永远降级"的闭环缺口。
- **同意**扩展内可用 `agent_settled + ctx.modelRegistry.complete()` 生成状态；这已被 pi 0.85.1
  的真实实现核实，不需要 sidecar。
- **部分同意**状态事务、权限分离、富墓碑和结构化预算下界；方向正确，但必须经过真实消息序列、
  失败注入和压力测试。
- **不完全同意**"stale 字段可以直接照用"、固定 `32k`、固定触发数字/语义权重，以及无条件默认开启
  Sweep；过期状态必须标记或剔除，数值只能是可调初始值。

## 2. 对 a–i 的判断

- **a 同意且必须做**：JSONL 是事实源，状态和归档是可丢弃派生物；判据是任何快照都能由
  `sourceRange + watermark` 追溯并重建。
- **b 同意但需收紧**：objective/用户约束仅在没有显式否决时长期有效，hypothesis/nextActions 过期就
  标 stale 或不注入；空数组也要能表示"已确认为空"，不能当作缺字段。
- **c 同意且优先**：要求 session/branch ancestry 正确，再按 delta overlay；首版可默认最多陈旧
  2 个 settled turn，换分支或越界立即丢弃。
- **d 同意**：reducer 持续维护 files/commands/tests，模型只在 settled 且 dirty 时无工具调用一次；
  必须单飞、超时降级、输出完整快照而非 patch。
- **e 同意原则、必须实测**：system 只放权威级别协议，状态作为 data；验收应检查真实序列为
  `SYSTEM→HISTORICAL→TASK_STATE→RECENT_RAW→QUERY` 且状态文本不能获得 system 权限。
- **f 基本同意**：allowlist、富墓碑、归档成功后再替换消息都值得做；checksum 可先用轻量原文 hash，
  重复 recall 的 pin 先做简单 3-turn 去抖。
- **g 部分同意**：需要结构性质量门，但不应把 `32k` 写成永恒常数；默认按
  `systemFloor+taskStateMax+recentRawMin+queryReserve` 判定，不满足则结构化 disabled、回退 pi。
- **h 部分同意**：内容 hash、显式语义失效和 65%/82% 检查点有价值；8k/12k 及权重先作可调启发式，
  `tool result=0` 只适用于语义刷新，不适用于证据归档和确定性 reducer。
- **i 同意但有前提**：自动管理和安全版 Sweep 可默认开，额外语义刷新默认 off 或 unconfigured，
  因为它会消耗订阅额度。

## 3. 可后置与必须补充

- **可后置**：Deep Context、项目备注新字段、三层继承设置、详细成本面板、model profile、复杂 pin，
  以及精确触发数字；它们不阻塞首个闭环。
- **必须补**：TaskState 自身的最大 token/字段优先级与超限裁剪；生成器的重入、取消、迟到结果 CAS，
  不能覆盖更新快照；归档与墓碑提交失败时的原子回退；真实模型对"状态顺序、约束优先级、分支切换"
  的验收。

## 4. 只能先做一件事

先做 **State Producer + Freshness Protocol**：确定性 reducer、`agent_settled` 单次无工具 completion、
宿主 schema 校验/原子 CAS、字段 freshness 与 ancestry overlay，并用真实模型证明 `<TASK_STATE>`
已注入且压缩接管不再永远降级。

## 二、它的回答（原文）

### Q1：删掉 60% workingSet / compactionIsImminent 后还有什么明显漏洞？

有两个，其中一个值得现在修；都不需要新增主进程 → 扩展通道。

第一，固定 48_000 对小上下文模型存在真实盲区。按你主进程现有 workingSet 公式，假设模型窗口是 64k：

```
workingSet = min(44.8k, 64k - 16k - 8k) = 40k
```

也就是说可能已经进入 compact，而 episode-fold 的 48k token gate 还没资格命中。如果之前也没有发生
Tool Sweep，这个会话会直接错过 fold。这个不是单纯"策略不够优雅"，而是确定存在的可达路径。

但我不认为值得为此新增 IPC。如果你支持这类较小窗口，优先用扩展已经拥有的信息解决；哪怕最终只是
给低窗口模型一个扩展侧 clamp，也比把 workingSet 变成跨进程同步状态好。若你实际支持的模型最低就是
128k 左右，这个问题可以降级为非 P0。

第二个漏洞是：

```
(settledTurns >= 4 && transcriptTokens >= 48k)
OR
toolSweepActuallyRemovedSomething
```

意味着 Sweep 分支完全绕过 settledTurns 下限。一个早期回合只要产生一个巨大 tool result，Sweep 就可能
在第 1～2 回合触发，然后 sticky=true，episode-fold 从此永久 eligible。它不会破坏正确性，但会把
"有足够历史值得提炼"误等价成"出现过一个肥工具输出"。

我会把最低 settled turn 数当全局 floor，而不是只约束 token 分支。比如逻辑语义至少应是：

```
settledTurns >= minimum
&&
(transcriptTokens >= threshold || sweepActuallyEffective)
```

至于 minimum 是 2 还是 4，你现有 4 没明显问题。

除此之外，我没看到需要靠 workingSet IPC 才能补的 P0 洞。你现在失去的主要是跨模型窗口的自适应性，
不是 authority/correctness 保证。

### Q2：state.generate / state.inject 而不是拆两个 kind，有问题吗？

这个选择我认可，不建议拆 kind。

你的 kinds 实际承担的是"哪个上下文管理阶段由砚接管"，而 generate / inject 是"这个阶段内部以什么
运行模式工作"。这是两个不同维度。把 episode-fold-generate、episode-fold-inject 拆成两个 kind，
反而会污染你主进程 UI 的阶段所有权语义。

你现在这个状态空间也是合理的：

| generate | inject | 语义 |
|---|---|---|
| true | true | 正常模式 |
| true | false | shadow / 观测模式 |
| false | true | 冻结生成，只消费已有状态 |
| false | false | episode-fold 实质停用 |
| kinds 不含 episode-fold | 任意 | 总闸关闭 |

而且你把 compaction handoff 也纳入 inject 是正确修复。否则所谓 inject:false 实际只是"context hook
不注入"，而不是"TaskState 不影响模型"，语义就是假的。

唯一需要锁死的是一个契约命名问题：inject 现在实际上不是狭义的"插入 `<TASK_STATE>`"，而是
**allow TaskState to participate in any model-visible context**，包括正常 context injection 和
compaction handoff。这个语义最好直接写进 schema/comment。否则半年以后很容易有人看到：

```js
if (policy.state.inject) {
  injectTaskState()
}
```

然后在 compaction 新增一个 consumer，觉得"这里又不是 inject"，再次绕过去。

另外两个组合只需要保持现在这种行为即可：`generate:false + inject:true` 在没有合法已有状态时 no-op，
不能临时生成；`generate:true + inject:false` 允许落盘和诊断，但任何模型可见路径都不能消费它。

结论：字段分路优于拆 kind。你这次的实现方向是对的。

### Q3：天然落后 1 个用户回合，要不要视为 fresh？

**要。明确建议：把"只落后当前这 1 条新 user turn"视为 fresh。不要采用"只给 hypothesis 标 stale"。**

你现在实际上有两个不同概念混在一起：snapshot 是否覆盖了所有已 settled 的历史；snapshot 是否已经吸收
当前正在开始的新 turn。在你的执行时序里：

```
Turn N settled
    ↓
生成 TaskState，sourceHead=N
    ↓
User N+1 到达
    ↓
context hook 注入 TaskState
```

TaskState 对**所有已经完成的历史**都是最新的。它只是理所当然地还没有吸收当前正在处理的用户消息。
把这种状态称为 stale，会产生一个结构性问题：episode-fold 永远不可能在正常消费时达到 fresh。
那么 fresh 这个状态在 steady state 下几乎成了不可达状态，这说明 freshness 定义和生命周期错位了。

而且你已经有 authority：新用户指令 > 真实工具结果 > reducer 事实 > 原始转录 > TaskState。
当前 user N+1 就在 TaskState 上面，所以发生 pivot 时已有明确覆盖关系。

为什么不选"只 hypothesis stale"：因为 volatility 不是 hypothesis 独有 —— hypothesis 会被新用户信息
推翻；nextActions 同样非常容易被新用户消息直接改写；currentPhase 也可能瞬间变化；甚至 objective
都可能被用户一句"不要做 A 了，改做 B"推翻。所以只给 hypothesis 特判，本质上是在字段层猜"哪个最可能
失效"，并没有解决时序定义问题。

更干净的判断应该是：**sourceHead 后面如果唯一新增的是当前尚未 settled 的 user turn，则仍算 fresh。**
一旦 sourceHead 后已经出现真正的新证据，例如新的 tool result、assistant / tool execution、额外
settled turn 等，再进入 partial / stale-soft。

**你会牺牲什么**：会牺牲一点保守性。极端例子：

```
TaskState.nextActions = "继续实现 SQLite cache"
用户下一句："停止 SQLite 方案，全部改成内存缓存"
```

此时 header 仍显示 fresh，虽然 nextActions 已经语义过期。但这个风险有三层缓冲：用户消息就在上下文里，
而且比 TaskState 新；你已经明确声明 authority 是用户指令优先；sourceHead 仍然保留真实水位，没有伪造
provenance。

换来的收益则很实在：正常运行路径不会永久把 hypothesis / nextActions / assumptions 污染成
`[stale: verify…]`。否则模型每一轮都会被告知"你收到的工作状态不可靠"，等于主动削弱 episode-fold 的价值。

所以我的取舍是："落后当前一个、尚未 settled 的 user turn" = fresh。不要只 special-case hypothesis。
只有出现当前 user turn 之外的新执行事实 / 已完成回合，才降为 partial/stale。

**你这轮六项改动里，真正还值得马上动的，我认为就是 Sweep 分支绕过 minimum turns 和这条
one-live-user-turn freshness 语义。其余没有看到需要重新翻设计的地方。**

### 三.1 一处它没预见、被实测抓到的细节

按它说的「唯一新增的是当前 user turn」写成 `tail.length === 1 && tail[0] 是 user` 之后，
真实链路里**仍然判出 `partial`**。加上诊断字段（`tail`：水位之后新增条目的角色指纹）后一次成功的
真实回合给出了答案：

```json
{"hook":"task-state-injected","freshness":"partial","sourceHead":6,
 "gap":2,"turnsGap":1,"pendingOnly":false,"tail":["session_info","user"]}
```

**pi 会在用户消息之前写一条 `session_info` 条目**（会话元信息变更记录），所以水位之后是两条。
于是把判据从「白名单枚举包装类型」改成**反向判据**：

> 新增条目里**恰好一条 user**，且其余条目**没有一条是 message 类**（即没有 assistant / toolResult
> 这类执行事实）。非 message 的条目（`session_info` / `custom_message` / `branch_summary` /
> `compaction`…）一律不构成执行事实。

枚举包装类型是必然会漏的（下一个新类型就漏），这也正是**为什么要有 `tailRolesOf` 这样的角色指纹诊断**
—— 只看 `gap: 2` 这个数字是排查不出来的。

### 三.2 端到端证据已取到（同夜第 7 次尝试）

```json
{"hook":"task-state-injected","freshness":"fresh","sourceHead":6,"tokens":141,
 "gap":0,"turnsGap":1,"pendingOnly":true,"tail":["session_info","user"]}
```

`pendingOnly: true` ↔ `freshness: fresh`，而 `turnsGap` 仍是 1 —— 真实水位差没被抹掉，
只是不再据此判陈旧。`test:live -- contextproduce` 全绿。

此前 6 次里 5 次是免费模型侧失败（`aborted` 超时 ×3、`not-json` 空文本 ×1、`error` ×1），
只有一次跑到成功、而那次恰好是修正前的版本（就是上面那条 `tail: ["session_info","user"]` 的诊断）。

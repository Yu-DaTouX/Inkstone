**反向验证（已实测）**：把 provider 与 model 两层顺序对调 → 「更具体的那层赢」变红；让 env 不参与解析 → 「env 优先于用户设置」变红（N21-7）。生成器侧的 CAS 与失败路径由单测直接构造（生成期间改文件 / 调用抛错 / 非 JSON 输出）。

### 1.12 状态生成开销量化 →「增量 delta」决策不做（2026-09-17 晚，已闭环）

| 应用与包 | 本轮**未重新打包**（只改了扩展诊断字段与测试脚本，不动打包结构；下一轮打包时自然带上） |

**顺带修好了一个静默失败的场景**（`contexttakeover`，见方案 §18.8）：它的三个症状都具有欺骗性 ——
① 探针只发一句 15 字符的消息，期望「越过工作集 1500」，而 pi 报的用量只有 4 → 永远到不了线，
失败输出却只有一行「主进程记录: null」；② 场景预算 180s 不够探针跑完，**进程在打印前就被 kill**，
`buf` 为空 → 被报成「应用可能启动失败」；③ pi 会拒压「太小」的会话
（`Compaction failed: Nothing to compact (session too small)`）。

最终修法：**单个足够大的回合（46k 字符）+ `keepRecentTokens: 1`**（不要用「预热回合」来绕 ——
在 1500 这种极低阈值下，预热回合结束本身就会触发一次压缩，反而干扰后面的回合），
场景预算提到 420s，并在等压缩前先断言「回合真的跑起来了」+ 打印 `pi 用量=n/window`。
实测（`deepseek/deepseek-v4.1-flash`）：`pi 用量=31019` → 压缩 `completed`、
`beforeTokens=31019` → `afterTokens=120`、`triggeredBy: policy`、
界面「最近一次工作集 · 已完成」✓。

**改用 `deepseek/deepseek-v4.1-flash` 后 `contextproduce` 也全绿**：生成器 1 次提交 / 0 错误、
注入 1 次且 `freshness="fresh"`（`pendingOnly:true`、`tail:["session_info","user"]`）、gate 当场激活、
状态文件 `revision=1` + `episodes 为空`、主进程校验 ok、`stateOverhead = 4.6%（low）`
（分母已改为**只算本场景会话** —— 之前把 8 份 fixture 会话也算进去，比值被稀释成 0.0%）。

同一次排查还确认 **pi 的用量口径不透明且非线性**（15 字符 → 4；7.8k → 1940；46k → 31019），
所以场景只能依赖「相对关系」（pi 原生线在工作集之上、用量真的过线），不能依赖这个绝对值。

### D11 详情（已修，高）

**现象**（用户截图）：模型菜单里“思考强度”显示“上游未提供思考档位信息”，但该模型在 pi 里
`reasoning=true`，档位实际存在。

**根因**（真实 pi 实测 + 代码）：

1. pi 的 `get_state` **不返回** `availableThinkingLevels`（它只给 model / thinkingLevel / isStreaming / …）；
   档位的权威来源是 `get_available_thinking_levels` 命令。
2. 但 `agent.ts` 的 `setStateFrom` 把它当作唯一来源：
   `hasOwnProperty(data,'availableThinkingLevels')` 恒为 `false` → `normalizeThinkingLevels(undefined, false)`
   → `{ values: [], status: 'unknown' }`。
3. state 推送非常频繁（流式增量、工具调用、状态变化），**每条都会把档位重置成 unknown**，

实测（直连内置 pi 的 RPC）：
```
set_model commandcode/deepseek/deepseek-v4.1-flash → success
数据源 get_available_thinking_levels → ["off","minimal","low","medium","high"]
```
→ **上游是有档位的，是砚把它丢了。**

**修复**：新增纯函数 `resolveThinkingLevels`（`shared/model-capabilities.ts`）——字段存在则以它为准；
缺失且模型未变则沿用上一次已知结果；模型变了才清空等回填。`setStateFrom` 改用它；
`model_change` 事件与首次连接（`setConn('ready')`）各补一次 `listThinkingLevels()`。

**验证**：单测 5 条（含“state 推送不得清空档位”回归）；live 探针 `thinking-levels` 实测
档位 = 关 / 轻度 / 中 / 高 / 极高，`thinkingLevelsStatus: known → known`（3.5s 多次推送后）。

### D13 详情（已修，中）

**现象**（用户）：人在**最新消息**，导航轨（左侧会话柄）的高亮却停在**第一格**。

3. 没有越顶的 → 视口里最靠上的一轮（不再回落到第一格）。

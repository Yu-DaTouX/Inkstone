# 并行代理编排（2026-09-19）

> **这不是主题文档。** 主题的范围、出口与六栏口径仍然只在各份 `实施-0X-*.md` 里，
> 主题的完成度只在 [HANDOFF](../../dev/HANDOFF.md) 里。本文只回答一个问题：
> **哪些片可以同时开工、每个代理占哪几个文件、做完往哪里交证据。**
>
> 起因：主题文档是按「一次会话一片」切的，但没有说**片与片之间能不能同时做**。
> 而本项目是**一个工作区、常年带大量未提交改动**，两个代理同时动同一个文件必然互相覆盖。
> 这个文件把「并行边界」显式写出来，避免每个代理各自去猜。
>
> 维护规则：只在**波次或文件域发生变化**时改；不改它去记录某片是否完成（那看 [README](../../plan/active/README.md) 状态列）。
>
> **当前状态（2026-09-22）**：本文保留为历史波次的文件域参考，不是独立待办，也不决定当前优先级。当前队列以实施-11 的 3.7 节、各主题正文和 HANDOFF 为准。

## 0. 开工前必须知道的三件事

### 0.1 同一个工作区，不能靠 git 回滚

2026-09-19 实测：`git status --short` 有 **116 项**改动（44 `M` / 13 `RM` / 2 `R` / 57 `??`），
`git diff` 累计 **+2494 行**。按 [AGENTS.md](../../../AGENTS.md) 第二节，这些是**在进行的工作**，
不许 reset / checkout / clean。

推论：

- **不能**用 `git worktree` 给代理做隔离（未提交改动不会跟着新工作树过去，代理会看到一个旧代码库）；
- **不能**靠「改坏了就 git 还原」兜底 —— 还原会连带抹掉别人的半成品；
- 所以并行只能靠**文件域所有权**：每个代理在自己的文件域里改，跨域的共享文件走**串行队列**。

### 0.2 五个共享热点（任何时刻只允许一个代理持有）

| 热点 | 谁会用 | 规则 |
|---|---|---|
| `src/main/agent.ts` | 01-S4b、05-S2 起、03-S4、04-S3 起 | 走**能力面队列**（§5），队列内串行 |
| `src/main/capability-server.ts` | 同上 | 同上 |
| `resources/yan-cli/yan.mjs` | 同上 | 同上 |
| `scripts/test-live.mjs`（4301 行 / 115 个 `CASES`） | **每个新增 live 场景** | 只在 `CASES` 表尾**追加自己一行**，不改别人的行；若同一波次有多个代理新增场景，**由编排者统一登记** |
| `docs/dev/HANDOFF.md` | 每片收尾 | 只在「本轮」区**追加自己一节**，不改别人的节；片末**一次写完** |

半热点（需要额外注意）：

- `src/main/paths.ts` —— 03-S2 / 09-S3 都会碰，两片不要同时开；
- `scripts/visual-matrix.mjs` + `docs/design/preview/` —— 新增视觉状态的片都要改；截图**另存新名**，不覆盖（AGENTS.md 第二节）；
- `src/main/index.ts` —— IPC / 服务接线处，改之前先 `git diff` 看当前未提交内容；
- `package.json` —— 新增脚本或依赖时改，改前打招呼。

### 0.3 三条工程环境约束（每张任务卡都适用）

1. 跑 Electron 前 `env -u ELECTRON_RUN_AS_NODE`（空串也算设置，见 AGENTS.md 命令表的坑 #2）；
2. 改 `src/` 后**必须先 `npm run build`** 再 `test:live`（坑 #1）；
3. cost 1 场景先设 `YAN_TEST_MODEL=deepseek/deepseek-v4.1-flash`（免费模型配额会让场景假红，见 HANDOFF「已知偶发」）。

## 5. 能力面串行队列（不得并行）

`src/main/agent.ts` + `src/main/capability-server.ts` + `resources/yan-cli/yan.mjs` 是同一个扩展点：
命令的实现点只有 `agent.ts` 的 `runCapabilityCommand` switch 一处，
注册点是 `capability-server.ts` 的 `KNOWN_COMMANDS`，CLI 侧是 `yan.mjs` 的用法表。
三处必须**成对登记**（02-S3 的教训：漏一处就是「命令已接通但会报错」）。

**队列顺序与理由**：

```
A1(01-S4b browser)  ← 硬阻塞，且要独占一段新桥接
  → B2(05-S2 模式服务)  ← 05 的其它片都建立在这份会话级状态上
  → C1(03-S4 knowledge) ← 03 的 buildin 登记是 04 的来源依赖
  → C2(04-S3 capabilities + mcp)
```

队列规则：

1. 进队列前先 `grep -n "runCapabilityCommand" -A 20 src/main/agent.ts`，确认**没有别人正在改这一段**；
2. 一片在队列里时，别的片**只能读不能写**这三个文件；
3. 队列片结束必须同时改三处，并在 `yan --help` 里能查到自己的子命令；
4. 新命令的**业务失败**用 `CapabilityCommandError`（带 `code`），协议 / 鉴权失败沿用端点级错误 —— 两者的区分见 `capability-server.ts` 的注释。

## 7. 登记与合流规则

1. **一个片一次收尾**：不写「本轮已落地」流水账（HANDOFF 末尾的明文要求）；做完一项就从「当前未完成」删掉。

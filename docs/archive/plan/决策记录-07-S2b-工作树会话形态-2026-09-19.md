# 决策记录 · 实施-07 S2b「带历史继续」的形态（2026-09-19）

> 背景：S2b 的四个重绑定本体（项目权限 / 相对文件路径 / 附件授权 / 上下文派生）**必须先定形态**才能动手 ——
> 否则「附件要不要带」「上下文怎么带」两个问题没有判据。这份记录把形态定下来，后续实现按 §4 的切片走。

## 1. 问题

用户在**主仓库目录**的会话里创建一个 Git 工作树（`git worktree`，独立目录 + 独立分支），
然后点「在工作树里开新会话」。当前实现是**降级路径**：只开一个干净的新会话（cwd = 工作树），
不带走历史、权限与附件授权，并在界面里如实写明「不带走这些」。

要升级成「带历史继续」，必须先回答：**新的那条会话与源会话是什么关系**。

候选形态：(a) 复用同一会话只换 cwd；(b) 新会话 + 注入摘要；(c) 新会话 + 拷贝全部历史；
(d) 新会话 + 引用源会话（可回看、默认不注入）；(e) 其他。

## 2. 咨询来源

按用户指示，用**砚内置浏览器**打开 ChatGPT 网页版（2026-09-19，会话标题「工作树会话形态建议」），
把上面这个问题连同四个重绑定的说明发过去。原文摘录（未改写的要点）：

- 推荐 **(e) Fork Session**：**新会话**（自己的 cwd / 权限 / 生命周期），与源会话建**不可变的 lineage**，
  创建时接收一份**经目标工作树校验过的交接包**；源历史**可回看 / 按需召回**，但**默认不整段注入**模型上下文。
- 理由：「会话绑定一个 execution environment」—— cwd、工具结果、Git HEAD、权限、安全边界共同构成环境；
  工作树已经是新环境，就该是新 session identity。但也不能退化成「完全干净」，否则刚讨论出的目标与约束全丢。
- **失败模式**（它点名最危险的一种）：拷贝全部历史时，「会话连续性 ≠ 文件系统连续性」——
  新会话会看到「我刚修改了 `src/foo.ts`」，而那个修改根本不在这里。**这正是复制历史最危险的地方**。
- 四个重绑定的优先级：
  - **项目权限 P0**：但**不是继承，是重新建立** —— 不许 `target.permission = source.permission`；
    要跑目标目录**自己的** trust policy（「同一个 Git 仓库含所有 linked worktree」可以是一条显式策略，
    但不能因为 remote/branch 相同就偷偷继承）。Windows 下要按 **canonical path** 判断（junction / symlink）。
  - **相对文件路径 P0**：源会话产生可迁移状态时就该存 **repo-relative** 路径；Fork 时用**目标仓库根**解析
    并**验证存在性**。**禁止** `text.replace("C:\\repo\\", "C:\\repo-worktree\\")` 这类前缀替换。
  - **上下文派生 P0**：区分「可迁移知识」（目标 / 约束 / 决策 / 假设 / 下一步）与
    **「环境派生状态」**（改过哪些文件 / `git status` / 测试结果 / 命令退出码 / 当前分支 / 文件是否存在）
    —— 后者必须**在新工作树重新计算**，绝不搬运。
  - **附件授权 P1（可延后）**：第一版可以不做迁移，但要**如实说明**「3 个源会话附件未带入，需要时可重新授权」；
    将来若做，产品语义必须是显式的「创建工作树会话时同时复制所选附件」；**用户本机文件系统路径**的授权绝不偷偷搬。
- **明确禁止的反模式**：同一 session 动态换 cwd；memcpy 式复制 session JSONL（尤其复制后只改 cwd）；
  自动继承目录权限；绝对路径前缀替换。

## 3. 裁决（采纳什么、为什么）

**采纳 Fork Session 形态**，并且它与项目现状几乎是对齐的 —— 不需要新造概念：

| GPT 说的 | 项目里已有的对应物 |
|---|---|
| 不可变 lineage | **实施-07 S2a 已完成**：`YAN_DIR/worktree-links.json` 记录新会话 ↔ 工作树 ↔ 源会话 ↔ 源目录 ↔ 分支（且**不参与历史拼接**，与「会话链」是两回事） |
| 「经校验的交接包」 | **实施-05 的交接包机制**（`handoff` 包：目标 / 约束 / 决策 / 下一步 + 三道闸门）—— S2b 复用它，不新造 |
| 「默认不注入、可回看」 | 现有「来源关系落盘 + 环境菜单显示『这个会话是从工作树 X 派生的』」正是这个位置 |

采纳的**优先级**（与咨询一致）：项目权限 P0、相对文件路径 P0、上下文派生 P0、附件 P1（第一版不迁移、如实说明）。
采纳全部四条反模式。

**不采纳的部分**：咨询里给的 `SessionForkManifest` 是一份**具名 TS 接口**，但项目里 lineage 已经落在
`worktree-links.json`（结构不同、已被 S2a 的证据覆盖）。**不为了对齐一份外部接口去重写已有存储** ——
需要的字段若缺失，就按现有 store 的风格加字段（那是 S2b 的实现细节，不是形态问题）。

**待定**：「信任整个 Git 仓库含所有 linked worktree」要不要成为**显式策略**（即：信任了主仓库就自动信任它的工作树）。
咨询说「可以作为显式策略，但不能偷偷继承」。我倾向**先不做自动策略**：S2b 只做「在目标目录重新走一次 trust 流程，
并把结果如实显示」；要不要加这条便利策略，等真实使用后再说（它属于放宽安全边界，默认不做）。

## 5. 顺带修掉的真缺陷：设置写入不是原子的（2026-09-19）

S2b-2 落地时拓到一个**既有并发缺陷**（不是本片引入的，但被本片的额外 IPC 暴露）：

`patchSettings()` 是「`invalidate()` → 读盘 → 合并 → 写盘」，不是原子操作。两个并发调用会各自读到同一份旧内容，
后写的那个把前一个的结果**整份盖掉**；更阴的是中间那次读盘会把旧内容写进 `cached`，
使后续 `getSettings()` 在**整段写入完成前**都返回旧值。

**症状**（真实复现）：工作树创建后要 `patchSettings({ projects: [...已有, 新工作树] })`，
同一时刻信任查询调用了 `getSettings()` —— 结果界面上**新建的工作树从项目列表里消失**，
而 git 侧工作树确实建好了（`git worktree list` 两条）。

**修法（两处）**：

1. `src/main/settings.ts` 加**写入串行队列**（`writeQueue`）：每个 patch 拿到的是上一个写完之后的磁盘内容；
   读（`getSettings`）不进队列（它不改文件，且界面高频读）。
2. `yan:trust:status` / `yan:trust:allow` **不再读 settings**（调用方必须把目录传进来）：
   少一个「顺手读一下设置」的调用方，就少一次与写入交错的机会。

**证据**：修前稳定复现（3/3 次运行失败），修后 `gitwrite` 连续两次全绿（含“新建的工作树已登记为项目”）；
探针里保留了失败时的诊断输出（打印 `projects` / `worktrees` 实际内容），下次再出问题不用再猜一轮。

## 3. 菜单与快捷键

- 原位显示「标准 / 澄清 / 自主 ▾」，菜单单选项带**一句说明**。
- **IME 组合态最高优先**；补全菜单打开且有候选时 `Tab` 保持填入。
- 无修饰键、普通输入框聚焦、无补全时 `Tab` 循环模式；长文模式保持原编辑 / 焦点行为。
- `Shift+Tab` **维持思考强度**；模态 / 表单不抢 `Tab`。
- 模式菜单用方向键、`Enter`/`Space`，`Esc` 关闭；`Tab` 离开菜单。
- 设置提供**关闭 Tab 快切**；输入框 `Esc` 在无补全时可把焦点移到模式按钮，避免键盘陷阱。
- 保留草稿、选区、附件；**切换不发送消息**。
- 自主运行才有运行光带；澄清等回答显示**真实等待状态**。使用现有 tokens，新增先改 `DESIGN.md`。
- 模式提交失败 → 恢复已确认值并显示错误，**不出现**「UI 已自主而扩展仍标准」。

## 4. 澄清门槛与自动开工

**「95%」是模型理解自评，不是成功概率。**

`ready` 条件（**全部**满足）：

1. `confidence >= 0.95`
2. 目标 / 交付物 / 范围 / 约束 / 验收**齐全**
3. 无关键未决
4. 无未回答的必要问题
5. `modeRevision`、`goalRevision` **未过期**

提问纪律：用户已给的信息**不重复问**；可从仓库查的**先查**；低影响事项**用假设**。
每次 **1 个**关键问题，独立问题可同组。

**结构化自评**：拟建 `clarification_ready` 提交通道（CLI 或受控工具），返回结构化理解；
**宿主验证字段、身份与状态** —— 模型自评不能替代这些校验。

**转移**

```text
clarifying → ready 校验 → 原子提交 mode=standard 且 goal=executing
           → 显示理解摘要 → 内部 resume 一次
```

- 内部继续使用**唯一** `operationId`；模型调用成功后**不能额外**向用户要「是否开始」。
- 就绪摘要**不是伪造用户消息**，应作为**宿主控制消息**留痕。

**模式切换的可行性（S1 已验 ✅）**：能否在同一工具循环里刷新有效模式与工具集？
不能只改 `desktop.json` 就假设 `before_agent_start` 会重跑。

> **已实测（2026-09-18 01-S1 + 2026-09-19 05-S1）**：`setActiveTools` 运行时可用且持续到后续请求；
> `tool_call` 返回 `{block:true}` 的工具**真的不执行**（但拒绝文案固定为
> `Tool execution was blocked`，不能自定义；循环也不会因此停下）。
> 所以澄清档的门禁顺序是 **工具表（主）→ `tool_call` block（兑底）→ 提示词（说明）**。
> 证据：[证据-05-S1](../evidence/证据-05-S1-钩子与安全点.md) 实验 1。

- 可安全切换 → 宿主提交后**确认新策略**再继续。
- 不可安全切换 → 在边界**结束澄清轮**、持久化续行记录，再启动标准轮。

两条路径都**不得**抢先执行实现工具或重复发用户目标。

**澄清的只读门禁**（三方结论：验收标准是「工具集真实受限」，跨轮续行可作**实现方式**）

- 覆盖**所有**工具调用入口；`write` / `edit` / `bash` / 脚本 / MCP / 第三方 `unknown` **不得仅靠提示词限制**。
- 允许经审查的**只读查询白名单**；**不对任意 shell 命令做脆弱的字符串「只读」判断**。
- **验收口径**（2026-09-18 三方一致，见 [决策记录 §2.3](决策记录-三方意见对照-2026-09-18.md)）：
  可以接受路径 B 作为实现方式，但**不能**把「没做到硬限制」当验收通过 ——
  **至少 allowlist 这一层必须真做**；若连 allowlist / 等效硬门禁都做不到，明确标为**未完成**，
  不退化成「提示词里写了不要写文件」。
  **已实测通过**（2026-09-18，见 [证据-01-S1 §3/§4](../evidence/证据-01-S1-可行性验证.md)）：
  `--tools read,ls` 后工具表里只剩 `read,ls`（真移除）；
  `setActiveTools` 运行时可用且持续到后续请求 —— 所以**不需要安全重建实例**，
  这也把[实施-05](实施-05-工作模式与长任务续接-已完成.md) 里「运行时不能改工具集」的前提取消了。
  ⚠️ 只读白名单必须**显式列全**：`grep` / `find` / `ls` 默认不在激活集里。

**跨轮续行（路径 B）的三个必做防护**（2026-09-18 外部咨询补全）

1. **唯一 `transitionId`**：一次就绪转移只允许一个 ID，重放返回**已提交结果**，不新建第二次转移。
2. **消费幂等**：`handoff` / `resumeId` 的消费点**持久化**；崩溃后按消费证据判断，**不盲发两次**。
3. **先持久化再启动**：readiness 记录必须先落盘（并校验 `revision`）**再**启动标准轮 ——
   禁止标准轮在落盘前抢跑；用户停止则废弃未消费的转移。

**问答失败语义**：`question` 取消 / 超时 / 无 UI / 失败 → **保持未就绪**，
**不沿用旧「猜一下继续」行为**。用户主动切标准或自主 → 以新模式更新，不再等待过期答案。

## 5. 自主持续执行与停止

阶段：`planning → executing → verifying → completed`。可推进但未完成就按条件继续；
**不能一次 assistant 文本结束便默认目标完成**。

拟建 `goal_report` 提交通道（宿主校验当前 goal / revision 与检查结果），提交剩余步骤、证据、阻塞。
**任务清单勾选仅是展示材料，不足以证明完成。**

- 默认同一无变化失败**连续两次** → `blocked`；有**新证据 / 新路径**才重试。
- 外部凭证或授权缺失**如实报告**，**不能**为了「不提问」扩大授权。
- **用户停止优先**：撤销未发续行、标 `stopped`、取消在途可取消调用；
  迟到工具结果可登记事实，**不能**再启动下一步。取消**不保证**外部操作回滚，状态未知要明说。
- 内部续行、用户队列、新消息由**同一调度器**排序；**用户消息优先**于尚未发送的内部续行。
- 持久化消费点防重复；后台会话完成**不抢**当前视图。

**S3c 落地（2026-09-19）**：上面这几条现在是**可执行的链路** —— 自主档下
`yan goal report` 成功后由宿主 `armContinue` 写一条 `kind=continue` 续行
（上限 `AUTONOMOUS_CONTINUE_LIMIT = 8`；用户发言归零、目标进终态 / 用户停止即清），
薄层在回合真的空闲时用 `yan-goal-continue` 把它叫起来 —— **不再需要用户再说一句话**。
到上限不再 arm，由 `goal.report` 的回执里告知模型「停下来把事情交代清楚」。

**S5c 落地（2026-09-19）**：上面管的是「模型主动报告之后接着干」；真实用起来更常见的中断是
**模型压根没回话**（上游 5xx、连接被掐、供应商抽风）。pi 自己会就地重试几次
（`auto_retry_start` / `auto_retry_end`），用尽后砚原先只留一条「模型返回错误」，等用户回来再敲一句。
现在这条路也自动化了，但**不是无脑重试**：

- **先分类再决定**（[`shared/auto-continue.ts`](../../../src/shared/auto-continue.ts)）：
  认出**额度 / 限流**（429、`quota`、`used all … free requests`）、**认证 / 权限**（401/403）、
  **上下文超限**、**用户取消**的四类**一律不自动继续**（前三类明说「重试没有意义」，
  取消按用户停止处理）；其余（网络 / 上游瞬态 / 认不出的）才算可重试 ——
  有上限与退避兜着时，这个方向的错判成本更低。
- **退避 + 上限**：可重试时按 **3s / 10s / 30s** 再起一轮，连续上限 **3 次**；
  用户发一句话、按停止、或一轮真的产出了 → **归零**；计数落 `YAN_DIR/auto-continue.json`，
  **重启不忘记**（否则重启一次就等于重新给满额度）。到上限停手并说明「连续 3 次都没成功」。
- **续行走同一条通道**：宿主写 `goal-resume/<runnerId>.json` 快照（`kind=retry`），
  薄层在回合真的空闲时发一条 **`custom` 角色**消息（`yan-auto-continue`）并 `triggerTurn` ——
  **不伪造用户消息**；正文必须提醒「上一轮可能已经产生副作用，先检查再动手」。
- **触发源是结构化事件**（IPC 推送新通道 `agent-error`，来自 `auto_retry_end {success:false}` 的
  `finalError` 与 assistant 的 `stopReason === 'error'`），**不靠匹配提示文案**（改一句文案就静默失效）；
  同一错误在 2 秒窗口内重复到达只算一次（两个来源会同时报同一件事）。

**取到的证据**：`autocontinue`（**cost 0** —— 模型名故意写坏，上游回 400，请求被拒**不产生用量**）：
一条用户消息 → 3 条错误助手 → 2 次自动继续 → 到上限停下；磁盘 `auto-continue.json` 计数停在上限、
会话里有 2 条 `yan-auto-continue`（角色不是 user）、扩展日志有 `kind=retry` 的 `resume_sent`。
回归 `goal`（S3b）/ `goalloop`（S3c）/ `workmode` / `live` / `sessions` 全绿。

## 6. 长任务预算门（先于续接）

- 保留 `shared/context-policy` 作为预算**唯一公式源**；默认 240k，受窗口 / 输出预留 / 余量 / 用户覆盖限制。
- 新增**每次模型请求前的预算诊断**：系统提示、工具 schema、Skill、项目知识、变换后历史、图片估算、输出预留。
  实际 input usage 用作**校准**；**不重复累计 cache token**。
- `soft budget` 命中：先清理旧工具结果，仍高则安排安全压缩。
  **物理风险**命中：不发送已知装不下的请求。
- 工具调用与结果必须**成对保留**；大结果「摘要 + 可召回原文」，**不静默丢约束**。
- 单条用户输入本身超预算 → 明确提示，**不循环压缩**无效历史。

**S1 已在隔离 pi 中证明安全点 ✅（[证据-05-S1](../evidence/证据-05-S1-钩子与安全点.md)，2026-09-19）**

1. 一条用户消息引发多次工具循环，记录 `context` / provider 请求与 `settled` 时序。
2. 验证当前 hook 能否**阻止下一请求**、能否完整落盘并进入 `compact`。
   → **能阻止，但不是暂停**：`ctx.abort()` 让下一个请求真的不发，代价是整轮以
   `Request aborted` 结束（会话完整落盘，多一条空 assistant 消息）。
   → **压缩不能在钩子里做**：`ctx.compact()` 在 `tool_call` 里返回 `undefined` 并打断当前 run；
   安全点是**宿主侧 RPC `compact`**（砚已在用，见 `src/main/agent.ts`）。
3. **禁止**在 `before_provider_request` 内递归 `compact` 或等待自己完成。
   —— 实测进一步说明：不是「忙时安全拒绝」，而是**会把这次运行弄坏**。
4. 无可用安全暂停 API 时，走支持的 pi 升级 / 适配；**不修改 vendor 生成物**。
   未补齐前只能交付「**软预算 / 预警**」，该**硬门工程项仍未完成**。
   → **现可用两条硬手段**：`before_provider_request` 返回新 payload（**实测真能改写发出去的请求**，
   适合丢大工具结果）、以及 `ctx.abort()`（适合物理风险止损）。**没有安静的暂停**，
   所以界面的「等待安全压缩」只能表示「这一轮已结束、正在压缩」。

**S4 已落地 ✅（[证据-05-S4](../evidence/证据-05-S4-请求前预算门.md)，2026-09-19）**：
`before_provider_request` 里估算**真正要发**的请求体（messages + 工具表 + 顶层 system），
三档判定：`normal` / `soft`（过工作集线 → `context` 钩子跳过收益门槛再清一次旧工具结果）/
`physical`（估算 + 输出预留 > 窗口 → `ctx.abort()` **不发送** + 会话留痕 `yan-budget-abort`）。
公式与 `shared/context-policy.ts` 交叉校验（同一组窗口逐项相等），
扩展侧实现在 `resources/pi-extensions/context-budget.js`。
**仍属 S4 的尾巴**：界面无预算档位指示；估算未做缓存 / 增量；
`physical` 的确定性证据来自假 provider（真实窗口 1M 构造不出）。

界面明确区分工作集、目标预算、模型窗口、估算 / 真实来源；超限等边界显示「等待安全压缩」。
**不得**把过去请求 usage 当当前未来请求的精确值。

## 7. 自动压缩计数与续接资格

- 当前 goal 的 segment 中，**成功自动完整压缩**累计到 **2**；下一次**正常策略**压缩需求触发 handoff。
- **不计**：手动压缩、tool sweep、state refresh、失败 / 取消。
- policy / native 自动事件用**唯一 `compactionId` 去重**；重启后还原计数，**不能重置躲开阈值**。
- 原生自动压缩没有事前拦截能力时，允许**安全压完后接续**，记录实际次序；
  **不能宣称总是第三次之前**。
- 紧急物理保护优先压缩；goal 已完成不续接；有未完成子代理 / 长命令先等待，**不遗弃**后台工作。
- 默认连续自动续接上限建议 **3**，可配置；到上限保留任务并报告需介入原因，**不标 `completed`**。
- 本策略只对**自主模式**默认候选；先完成真实长任务验证后再开启默认值，
  **不能用「压缩次数」证明移交有益**。

## 8. 交接包与事务

**交接包内容**：用户目标 / 最近补充、约束与授权、验收标准、已完成证据、未完成与失败原因、
文件 / Git / 长进程状态、项目与 `cwd`、模式 / 模型、`sourceSession` / `sourceHead`、附件与召回来源。

- `TaskState` 仅是**带 freshness 的材料**；**不能把旧总结升级成事实**。
- 摘要建议 **4k–8k tokens**，按目标窗口收缩；约束超预算时**失败降级**，**不静默裁掉**。
- **不**在交接包复制凭证；**不**把全部历史重新灌进新会话。

**事务状态机**

```text
pending → snapshot → validated → destination-created → committed → resumed
```

1. 锁定 goal 调度，工具**完整结束后**截 `sourceHead`；用户新消息进入有序日志。
2. 生成并校验交接包；水位变化则**重建**。
3. 同项目 / `cwd` 创建目的会话，写关系与交接包，**尚不执行**。
4. 提交 `activeSegment`，旧 runner 释放 `cwd` 执行租约，新 runner 获取；**不得绕过**同 `cwd` 防线。
5. 用 `resumeId` **发送一次**，JSONL 消费证据确认 `resumed`。
6. 每一步写**可恢复日志**；崩溃在「发送后确认前」时，通过消费证据判断，**不盲发两遍**。
7. 失败保留源会话；未提交回源，已提交按日志恢复目的；**任何时候只允许一侧执行**。

**重绑定**：附件、相对路径、模型能力与权限重新绑定验证；
源 `ctx://` 引用需通过**同 goal 授权的只读来源**解析，**不复制字符串**就宣称可召回。
源文件被删 / 移动则**明确缺失**；**不得**恢复 `get_tree` 或全局任意会话访问。
交接中用户停止 → 废弃自动 `resume`；新消息按提交后的 `activeSegment` **只消费一次**；
**没有消费去重支持不允许开启默认自动续接**。

**S5b-2 落地（2026-09-19）**：交接包真的由**模型**写了（用户拍板）。分工严格按「能落地到宿主的一律不留扩展」：

- **宿主**：判资格（§7 四条 + 可覆盖的阈值）→ 用 `renderHandoffPrompt` 渲染提示词（TS，扩展用不了）
  → 写请求文件 `YAN_DIR/handoff-request/<runnerId>.json` → 轮询结果 → **三道闸门**（id 对得上 / 能解析 / 清洗过）
  → 落盘 `handoffs.json`。任何一道不过就丢掉这份并告知用户，**不把半份包写进事务**。
- **薄层** [`handoffs.js`](../../../resources/pi-extensions/handoffs.js)：在 `agent_settled`（一轮真的结束）时读请求，
  调一次 `ctx.modelRegistry.complete(...)`（无工具、60s 上限），把**原文**写回结果文件 ——
  无论成败都写，否则宿主分不清「压根没跑」与「跑了没结果」。

三个实现细节值得记住：

1. **触发时机有两处**：压缩完成之后（`observeCompaction`）与**回合结束之后**（`state` 推送里 `isAgentRunning === false`）。
   只靠前者会让「先报告、后压缩」的顺序漏掉 —— `goal report` 发生在回合**中途**，那一刻实例是忙的，资格会正确地拒掉。
2. **解析要括号平衡扫描**：早期写法是「第一个 `{` 到最后一个 `}`」，模型在 JSON 后面再接一句话就会把两份内容连起来、
   整份解析失败 —— 明明第一份是好的。现在只取**第一个完整对象**。
3. **写包失败就是失败**：解析不过 / 缺两栏必填 → 丢掉并提示，**不重试、不降级成半份包**（§8：「失败降级，不静默裁掉」）。

**取到的证据**：新场景 `handoffpack`（cost 1，`YAN_HANDOFF_THRESHOLD=0` 让「够数」先成立）全绿 ——
探针经只读 `yan:getHandoff` 看到两栏必填、来源字段由宿主填；退出后核对包已落盘、计数仍为 0、
请求 / 结果目录**已清空**；扩展日志的时间线（`check hasRequest:false → true` → `produced ms=4753 chars=1203 error=null`）
证明薄层真的调了一次 completion。**仍属 S5b 的尾巴**：事务（建目的会话 / 同 cwd 租约 / `resumeId` 消费去重 / `link`）未做，
界面也还没有入口（`yan:getHandoff` 只给探针与 S5b-4 用）。

**S5b-3a 落地（2026-09-19）**：§8 那七个阶段现在是**可执行的状态机**（[`shared/handoff-transaction.ts`](../../../src/shared/handoff-transaction.ts)）：

```text
pending → snapshot → validated → destination-created → committed → resumed
                                                            │
                                      任何非终态 ─────────→ failed（保留源会话）
```

- **不许跳步**：没有包不能 `validated`，没有目的会话不能 `destination-created`/`committed`。
  跳步会在崩溃后制造「日志说已提交、可目的会话不存在」这种两边都回不去的状态。
- **目的会话锁定**：已提交之后不许改（那会把用户指向一个没有任务上下文的会话）。
- **`resumed` 只能由磁盘证据置位**（目的会话 JSONL 里那条 resume），不是「发出即完成」——
  发送与确认之间正是进程可能死掉的窗口。`recoveryAction` 把这一格写成：
  `committed` + 有证据 → `complete`；无证据 → `resend`（消费去重挡住重复）；
  `destination-created` 及更早 → `abandon` 回源。这就是 §8 第 6/7 条「不盲发两遍」「未提交回源」。
- **日志先于动作**：每一步先落 `YAN_DIR/handoff-transactions.json`（按 `handoffId` 索引），
  再动外部状态；落盘失败**必须抛**（交接宁可停下，也不能「内存里提交了、磁盘没有」）。
  未终结的事务一条都不裁 —— 丢掉它们等于把「下次启动该恢复什么」一起丢了。

**取到的证据**：单测 **+59**（3506 全绿），含崩溃恢复的**全矩阵**与真目录上的事务日志（幂等 / 每步落盘 / 重启读回 /
`activeForSession` 源与目的两侧 / 脏文档丢弃 / 落盘失败抛）。**本片没有真实运行证据**：
状态机不含任何外部动作，真实链路要等接线（S5b-3b：建目的会话 / `runners.ts` 同 cwd 租约 / 发 resume / `link` 会话链）；
而 §7 明写「先完成真实长任务验证后再开启默认值」—— **默认是否自动交接需要用户拍板**。

**S5b-3b 落地（2026-09-19）**：事务接上了真动作（`shared/handoff-resume.ts` + `main/handoff-runner.ts` + `index.ts` 接线）。

```text
停止源实例（释放同 cwd 租约）→ 同 cwd 建目的会话 → setDestination / destination-created
      → 写会话链 → committed → 发 resume（发送前先记 attempt）→ 等**磁盘证据** → resumed
```

四条不可破的顺序（都有单测）：

- **先停源、再建目的**：两个忙实例不能共用一个物理 cwd（`runners.ts` 的同 cwd 防线）。
  交接走的是与界面切会话**同一条路**（`runners.select`），不绕过实例上限与 cwd 重建规则。
- **链只在目的会话真的建出来之后写**：链一写，侧栏就只显示代表段；写一个不存在的文件会让界面指向空气。
- **`resumed` 只认磁盘证据**（目的会话 JSONL 里那条 `[yan-handoff-resume:<id>]`），
  不是「发出即完成」——发送与确认之间正是进程可能死掉的窗口。
- **`resumeAttempts` 防「盲发两遍」**：发送**之前**记一次尝试（崩溃在发送途中也算发过）；
  恢复时 `>= 2` 次仍无证据就不再自动重发，改成停下等人（重复起一轮模型比停下来贵得多）。
  这也要求事务查询**归一化后比较**会话键（见下）。

**失败一律回源**（§8 第 7 条）：建会话失败 / 链写不成 / 落盘失败 → 记 `failed` 并把视图交还源会话；
发送失败或证据没到**不记 failed**（那样会把「其实已经发出去了」判死），留在 `committed` 等下次启动核对。
启动时 `recoverHandoffs()` 收尾所有未终结事务（`complete` / `resend` / `abandon` 三种处置）。

**默认开**（2026-09-19 用户拍板）：§7「先完成真实长任务验证再开默认值」的前置已满足
（`handoffcommit` cost 1 真跑通了建目的会话 / 写链 / 发 resume / 消费证据，崩溃恢复有单测全矩阵）。
显式关闭用 `YAN_HANDOFF_COMMIT=0`（`false` / `off` / `no` 同样认），解析在 `shared/handoff.ts` 的
`handoffCommitEnabled`（有单测钉住默认值 —— 它很容易被“顺手改成默认关”而无人发现）。
**打开只是允许交接**：实际发生仍要过四条资格（够数 + 目标在推进 + 自主档 + 不忙），
标准档会话不会被它带走。恢复**不受开关影响** —— 开关只决定要不要开始新交接，
磁盘上已有的未终结事务必须收尾，否则重启后会「日志说已提交、没人接着干」。

**真实链路抽到三个真问题（都已修）**：

1. 事务查询按**严格字符串**比较会话键 —— 事务里的 `destinationSession` 是 pi 给的原始路径
   （Windows 反斜杠），调用方的键来自 `workModeKeyFor`（已归一化）→ 刚交接完的会话查不到自己的事务，
   界面看不到进度、重启恢复也认不出它。改成归一化比较（`normalizeChainKey`）。
2. `yan:getHandoff` 只按**当前段**查计数与包 —— 交接后当前实例跑在目的段上，
   于是「已压 N 次 / 包写好了没有」当场归零（看上去像功能坏了）。改成**沿链回到首段**取。
3. `SessionChainStore.link` 在「目的已属于另一条链」时返回的是**那条链**（表示拒绝），
   只看返回值非空会把拒绝当成功 → 前端会出现两条会话。改成校验「这条链上真的有源与目的两段」。

**取到的证据**：单测 **+75**（**3581/3581** 全绿：resume 正文与证据 33 / 执行器顺序、失败与恢复 42）；
新场景 **`handoffcommit`**（cost 1，只把 `YAN_HANDOFF_THRESHOLD=0`，**不设** `YAN_HANDOFF_COMMIT` ——
「默认开真的生效」本身就是断言）+ `afterExit: handoffCommitPersisted` **全绿** ——

目的会话文件里真有那条标记、源会话与包都还在；回归 `workmode` / `live` 全绿。

## 12. 回滚与文档

- 模式功能可回落 `standard` / `autonomous` 兼容配置，保留会话元数据；
  关闭 handoff **仅停止新移交**，已提交事务仍需安全恢复。
- **不得**删除旧 / 新会话来「回滚」；goal `stopped` **不重启**。
- 更新 PROJECT、CODE-MAP、TESTING、HANDOFF 和用户快捷键说明；
  旧设计提案（已归档）**不再维护一份竞争的实现状态表**。
- **不保证**模型自评准确或摘要无损；交付重点是**状态可信、失败可恢复、能力受控、用量可核查**。

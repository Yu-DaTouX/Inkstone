## 1. 目标

在砚已有的会话级持续目标、自动续接、预算、暂停和证据基础上，明确“模型报告完成”与“宿主核验通过”的差别，并让用户能为持续目标给出足够具体的范围与验收条件。

本方案只吸收外部产品中适合砚的部分：

- **Codex Goal**：目标作为跨回合持续的结果契约；目标状态跟随任务保存；依据进展、预算和完成证据决定继续或结束。
- **Claude Code Plan Mode**：计划阶段只读探索；用户可以先审阅，再批准进入执行。

不照搬另一套自主循环、任务树、模型工具或权限系统。砚已有的自动续接、重试保护、预算、pause/pursue 与恢复回执继续作为唯一实现。

## 3. 产品语义

### 3.1 统一字段含义，不强迫用户填满五栏

持续目标入口保留现有必填项：

- **目标**：想改变什么。
- **达成判据**：如何判断结果符合预期；映射计划协议的 `acceptance`。

提供可选的“补充范围”区域，可填交付物、范围和约束；它们映射到已有计划协议字段。用户不展开时仍按当前两项目标创建流程工作。旧版 `PursuedBrief { goal, outcome }` 记录继续有效，升级读取时不要求补齐可选信息。

### 3.2 把完成声明和核验结果分开展示

目标 phase 继续表达执行阶段，不用它同时代表核验质量。目标进入 `completed` 表示模型已提交完成声明；宿主在独立的 verification 字段中记录核验状态：

| 状态 | 含义 |
|---|---|
| `not_checked` | 没有适用的机器核验条件。 |
| `passed` | 所有已声明且宿主支持的只读检查通过。 |
| `failed` | 至少一项可检查条件未通过。 |
| `manual_review` | 结果需要用户判断，宿主不能可靠地自动下结论。 |

界面明确写“模型报告完成”或“宿主核验通过”。没有可执行的确定性检查时，不显示“已核验”。文本 evidence 保留原样，作为解释和引用，不自动提升为核验事实。

### 3.3 计划批准是可选的人工关口

在澄清/计划模式设置“准备后先让我审阅”后，模型提交 ready 只生成待审计划，不立刻切到标准模式。用户选择“批准并开始”后，宿主再次核对 session、runner、goal revision 与 mode revision，再原子切模式并安排下一轮；“修改计划”则回到只读澄清阶段。

默认沿用现有 ready 后自动切换行为，避免改变现有会话习惯。批准关口只控制计划向执行的转换，不作为新的权限模式，也不改变 Standard / Autonomous。

## 5. 不可越过的边界

- 首期 verifier 不执行模型拼出的 shell、脚本、网络请求或任意命令；不把第三方 URL 可访问性当作事实。
- 文件核验只检查用户目标明确引用的本地路径，结果展示检查类型、时间与细节；它不能证明源代码语义正确或测试真实通过。
- 内容类、测试类验收须另行设计明确 allowlist、超时、输出截断、工作区范围和用户授权；本提案不包含这些能力。
- 目标事实、状态转换和核验结果由宿主持有。`resources/pi-extensions/` 只做宿主无法经 CLI/RPC 表达的必要生命周期桥接；不新增模型工具、pi 命令或第二个任务服务。
- 不改任务面板、预算机制、续接次数、模型工具集、项目知识和历史会话 JSONL。

## 6. 验收要点与剩余限制

- **兼容**：旧 `goal.json` / `goals.json` 状态、两字段 brief 和无 verification 字段的记录能读；新字段不会清空现有 outcome、steps、links、预算或恢复信息。
- **可信**：模型报 `completed` 但核验失败时，界面同时保留完成声明和失败结果；不自动回滚文件或外部副作用。
- **并发安全**：过期 revision、会话切换、runner 更换和重复操作都不能把核验结果或批准动作写到别的目标。
- **模式边界**：审阅关口开启时，批准前写工具仍不可用；拒绝 / 修改 / 停止不会悄悄触发执行轮。
- **证据分层**：fixture / 单测、cost 0 宿主链路、真实模型多轮、真窗口视觉、应用与包分别报告；前一层不能替代后一层。
- **明确保留**：机器核验无法确认主观质量；不支持的条件必须显示“需人工审阅”，不能推断通过。

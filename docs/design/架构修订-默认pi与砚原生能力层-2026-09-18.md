# 架构修订：默认 pi + 砚原生能力层

> 2026-09-18；设计与实施约束，尚未实施。
> 用户新边界：砚不要内置 pi 插件，完成的版本只包含默认 pi。
> 本文先按严格口径设计：第三方及砚自有的 pi 扩展均不作为最终产品依赖；砚自身 UI、服务和 CLI 属于应用代码。是否允许保留砚自有薄适配层已另行询问，尚未收到确认；不得把严格口径写成用户对细分选项的明确答复。

## 1. 推荐决定

采用未经修改的官方 pi 运行时，继续通过正式 RPC 管理会话；新增能力由砚主进程服务与独立 CLI 提供。模型用 pi 原生 read/bash 等基础工具读短说明、调用命令并查看结果。

不预装 pi-mcp-adapter、pi-web-access、left-info-panel 等 pi 插件，不在首次启动暗中装回这些插件，也不把同一插件复制改名后称为原生。按需获取的 Skill、普通 CLI 或 MCP server 放用户数据目录，与安装包的默认内容分开。

能力使用优先顺序为：已有本地工具/脚本 → 合适的 Skill 流程 → 发布方 CLI/API → 确实需要的 MCP 服务。用户明确指定 MCP 或某能力时优先满足，不以此排序否定要求。

“默认 pi”不意味着应用没有业务代码或依赖。砚仍负责 UI、任务、项目知识、鉴权、能力搜索和结果管理；官方 MCP SDK 若需要，是砚服务的协议库，不是加载到 pi 的插件。不得用术语变化隐藏实际 pi 扩展依赖。

## 2. 阅读结论与来源

用户提供的 [文章](https://mariozechner.at/posts/2025-11-02-what-if-you-dont-need-mcp/) 以浏览器操作为例，说明短说明加脚本、按需阅读和本地组合结果的价值。本文采用这种组织方式；不把文章中的历史 token 数当作当前性能保证，也不照搬其关闭浏览器、复制个人配置等示例操作。MCP 是否合适取决于任务和服务，不能推导成所有 MCP 都应该删除。

[pi 包目录](https://pi.dev/packages) 是能力线索和设计参考，不是最终预装列表。核查两个相关条目：

| 条目 | 本次读取到的职责 | 采用方式 |
|---|---|---|
| [pi-mcp-adapter](https://pi.dev/packages/pi-mcp-adapter) | pi 扩展形式接入 MCP，按需发现工具并延迟连接 | 借鉴按需目录、配置来源和生命周期，不预装该扩展；其文档中的工具搜索不等于自动联网找未知服务 |
| [pi-web-access](https://pi.dev/packages/pi-web-access) | pi 扩展形式提供网页搜索和获取能力 | 作为检索能力参考，不作为砚的搜索前置依赖 |

以上是公开说明核查，不是对这些包做源代码审计或运行验收；未安装任何包。

## 3. 当前代码与新边界的差距

已检查 [agent.ts](../../src/main/agent.ts) 和 [electron-builder.yml](../../electron-builder.yml)：当前启动显式传入 browser/question/response-detail/language/context 扩展；打包复制 resources/pi-extensions。因此当前产品不是零扩展架构，不能只停止预装第三方包便标记完成。

本机官方 0.85.1 文档有 --no-extensions、--tools、read/bash、RPC prompt/compact 等基础能力。--no-extensions 关闭自动发现，不会自动取消显式 --extension；最终参数必须一起审计。实际版本按 [protocol.ts](../../src/main/protocol.ts) 的 resolvePi 确认，不能只查全局 PATH。

当前 AGENTS 对语言注入、任务数据和上下文有已确认约束。本文不直接改这些约束或删源码；实施时列出等价性证据与产品差异，不能借新边界静默丢失现有功能。

## 4. 目标结构

```text
砚 Electron UI / 会话与目标调度器
       ├── 官方 RPC ── 默认 pi
       │                 └── read / bash / 其它原生基础工具
       │                               │
       └── 砚能力服务 ← 本机 IPC ← yan CLI
              ├── 搜索源与候选目录
              ├── Skill/普通工具的接入管理
              ├── API/CLI 适配
              ├── 可选 MCP 客户端与服务器进程管理
              ├── 任务、项目知识、交互请求
              └── 产物/日志/结果文件
```

yan CLI 是随砚分发的普通可执行入口，不调用 registerTool、不注册 pi 命令、不 import pi 内部模块。向 pi 子进程注入会话专用 PATH 或明确绝对入口；不修改用户系统 PATH。Windows 下使用实际打包可执行文件/启动器，不假设用户有 node、bash 脚本解释器或可执行 .js 的关联。

拟议命令：

```text
yan capabilities search --query-file query.json --scope available
yan capabilities discover --query-file query.json
yan capabilities prepare --candidate ID
yan capabilities acquire --plan ID
yan operations status --id ID
yan skill read --id ID
yan mcp describe --server ID --tool NAME
yan mcp call --request-file request.json --output result.json
yan tasks apply --request-file task-update.json
yan knowledge search --query-file query.json
```

这些是拟建 CLI 接口，不是当前命令。参数文件采用 UTF-8 JSON，避免 shell 转义、命令注入和模型拼接凭证。stdin/输出文件可选，用法保持一致。

## 5. 能力发现与接入仍是必做

保留 C 方案的联网搜索、候选核实、固定版本、接入事务、验证和原任务续行；把 capability_*、mcp_* 从“拟注册的模型工具”改为 CLI 子命令。搜索服务随砚存在，不能为了找能力先要求装 pi-web-access。

下载规则重新分流：
- Skill：下载并验证 SKILL.md、必要脚本与资源，固定版本，按需读取；不自动启用同包内的 pi extensions。
- 普通 CLI/API 客户端：安装到项目受管目录，检查平台/依赖，按受信来源策略执行。
- MCP server：由砚连接或启动，不要求安装 pi-mcp-adapter。按需返回单个工具 schema，调用结果先落文件。
- 仅作为 pi 扩展工作的包：标记不适用于默认 pi 路线；可以寻找独立 CLI/API 实现，不能以完成任务为由偷偷装入 pi。

对于同时含 Skill 和扩展的包，只有当 Skill 不依赖该扩展注册工具、提问 UI 或生命周期钩子时才可单独取用。必须保留许可及来源，不能只改清单剥掉扩展就声称兼容。

搜索、自动接入和真实业务使用是不同阶段。缺认证就保存 needs-auth；已授权范围内自动接入后继续任务，不让用户重复目标。首次启动包目录应为空，不联网下载一套固定的“必备插件”。

## 6. 提示与上下文组织

给模型一段短的砚能力入口说明：何时读帮助、怎样查可用能力、能力不足怎样联网发现，以及文件结果的读取方式；完整命令用法按需读。模型只看到 pi 基础工具 schema，不增加一大组自定义工具定义。

入口说明必须走**已验证支持的官方提示配置**，且显示在砚的提示来源诊断中，不伪造用户发过的话。具体通过项目级上下文文件、会话专用提示文件或官方参数的选型在 P0 验证；不写用户 AGENTS、不恢复旧语言 append-system-prompt 方案来强行通过。

工具大结果由砚服务/脚本保存为文件，stdout 返回受限摘要、类型、路径、大小/条数、错误和操作 ID。模型可用文件工具筛选必要片段。JSON/二进制/图片分别处理，路径不是渲染成功证据。对图片需验证 pi 原生读取和砚附件显示链。

本地中间结果减少上下文传输是设计目标，必须测量真实请求 token；CLI 反复打印巨量输出仍会撑爆上下文，不能把 CLI 等同于天然省 token。

## 7. 现有扩展迁移矩阵

| 现有依赖 | 默认 pi 路线 | 迁移难点/门槛 |
|---|---|---|
| panel_todos / 左侧信息面板扩展 | yan tasks apply + 砚任务服务，原生任务 UI | 新数据由宿主保存；旧 left-panel-tasks 只读兼容，不能再要求 pi appendEntry 写新数据 |
| browser.js | yan browser 命令到已有浏览器服务 | 身份、页面范围、缩放、下载等边界保持；无须更换原生 WebContentsView |
| question.js | 砚问答请求服务 + CLI，或明确的澄清轮会话交互 | 等待/取消/回答必须对应同一请求；不能从自然语言猜用户点了什么 |
| response-detail.js | 宿主偏好与经验证的提示传递 | 当轮/下轮生效要明确，不能承诺修改设置会刷新正在执行的 system prompt |
| language.js | 待验证的宿主提示传递 | 当前唯一真源和近用户消息注入不能直接删除；严格零扩展与现有生效链有冲突，先验证替代再更新规范 |
| context.js / 状态归纳和 recall | 主进程状态生成、yan context read、官方 compact | context 变换与 session_before_compact 等钩子并非 CLI 等价物；默认 RPC 下能保留哪些必须逐项实测 |
| 新 capabilities.js/work-mode.js | 不创建；改 CLI + 宿主调度 | 不允许将 adapter 改名藏入 pi 启动链 |

任务新写入采用宿主日志（sessionId + branchHead + revision + operationId），UI 合并旧 custom entries 与新日志；保留分叉和历史快照语义。不能直接编辑正在使用的 pi JSONL，也不能伪造模型调用过 panel_todos。

现有历史工具卡继续按原工具显示；新调用真实底层是 bash/CLI，可依据宿主操作回执显示“砚任务计划”等业务卡，必须可展开到原始调用，不伪造原生独立工具事件。

## 8. 不可用 CLI 掩盖的约束

### 8.1 请求前上下文控制

本次读取的 RPC 文档提供 compact 与状态事件，未找到与 context/before_provider_request 钩子等价的通用请求重写入口。不能据此实现“每次模型请求前硬预算”承诺。
P0 必须用未修改的 pi 验证安全暂停/截断边界。若没有：保留原生自动压缩与宿主安全回合边界压缩，并如实标记软预算；严格请求前硬门作为未满足项。不能偷偷 patch pi、恢复 extension 或把进程中止当成安全暂停。

### 8.2 模式只读与 CLI 权限

yan 服务只允许当前身份和模式对应动作，但允许 pi 的原生 bash 就仍可绕开 yan 执行其它命令。CLI 服务校验不等于整个 agent 沙箱。
澄清阶段若要硬只读：通过官方 tools allowlist 禁用 bash/write/edit，只用 read/grep/find/ls 等已核实原生只读工具；联网检索由宿主完成，再以可追溯材料交给模型。转执行若运行时不能改工具集，需要安全重建同会话实例并验证历史/队列不丢。不可写“有 CLI 所以澄清全工具硬门禁已实现”。

### 8.3 会话身份与本机服务

CLI 会话身份由宿主传递，校验 runId/generation、项目和操作 ID；不能由模型随意传一个 projectId 就跨项目操作。权限针对宿主操作，不声称能防同用户恶意本地进程。认证不进入模型输出，不复用跨项目服务器凭证。

## 9. 对四份实施方案的变更

本文作为跨方案架构约束，不删除前版细节，冲突部分在重写完成前不得执行：
- A：保留任务功能与历史兼容；取消“随包 task-plan.js 注册 panel_todos”，改砚任务服务/CLI。
- B：保留清理矩阵、知识存储和检索；新知识工具以 CLI 接入，不新增 pi 扩展。
- C：保留搜索/接入/验证事务；取消 capabilities.js 与默认自动安装 pi 扩展路线。pi 包目录只作线索，最终安装目标按 §5 分流。
- D：模式/goal/交接留宿主；取消 work-mode.js 前提；语言、澄清工具白名单、预算硬门须先过 §8，不把旧扩展方案的验收结论带入。

若用户最终只禁止第三方预装而允许自有适配层，可以单独缩小迁移范围；在没有确认前，严格方案不以此较宽解释为前提。

## 10. 分阶段实施

P0 可行性：隔离干净 piDir，用官方 pi，无任何 --extension，确认加载清单、基础工具、CLI 调用、提示入口、模式切换及上下文边界。输出每项可实现/有限实现/缺官方接口的证据。
P1 能力基础：yan CLI、宿主服务、session/project 身份、结果文件、联网搜索源；不预装业务 Skill/MCP。
P2 动态能力：真实任务从零搜索、接入独立 Skill/CLI 或 MCP，并继续完成；固定版本和恢复机制复用 C。
P3 现有功能迁移：按 §7 逐项做对照，保留旧历史/用户数据，缺等价实现的项不删除原路径。
P4 发布切换：所有必需功能验收后，移除默认扩展装载与打包复制；生产默认关闭扩展自动发现，审计显式参数、包资源和设置，防止项目包间接载入。

开发期可保留旧路径做隔离对照，但不能在最终默认产品中暗中 fallback 到扩展实现。已有用户安装的扩展不删除；升级时说明默认路线不再加载它们，提供可读列表，不改用户独立 pi 终端配置。

用户后续安装的 Skill/MCP 是运行期资源；不要重新回收到 release 模板。打包从干净资源清单构建，不能复制开发者自己的 pi-agent/插件缓存或凭证。

## 11. 完成标准

1. 默认安装目录只含官方 pi 必需运行时与砚业务代码，第三方/砚自有 pi 扩展清单为空；官方 pi 自身必要依赖不误删。
2. 干净用户目录和带历史扩展的升级目录，实际默认加载链都无扩展；两个目录均保留原始数据。
3. 禁网首次启动可用基础对话；联网后在无预装 Skill/MCP 下完成一次真实发现 → 接入 → 验证 → 原目标完成。
4. Skill 与 MCP 各一条真实模型链路，结果既有产物证据也有调用来源；仅看到包文件存在不通过。
5. 任务、浏览器、语言、问答、模式、上下文迁移逐项登记六栏；缺少 RPC 能力时明确未完成，不以“纯净 pi”抵消功能损失。
6. 无后台自动安装固定插件，无伪装来源，无跨项目队列/凭证串用；Windows CLI、空格/中文路径、取消/重启通过。
7. 新旧实现对照中用户会话/附件/遗留数据不被破坏；移除打包项只在迁移验收后进行。

本轮只形成修订方案，不修改启动参数、生成运行时、当前扩展或用户配置。纯净默认 pi 是目标；现有功能能否全部无损迁移必须通过 P0/P3 的真实证据回答。

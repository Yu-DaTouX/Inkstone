## 1. 问题（同 v1）

右栏现状：

```
┌ 上下文 ──────────────────────────┐
│ 上下文  9%              36k / 400k│   ← 主值是物理窗口占用
│ ▬▬▬▬▬▬▬▬▬▬▭────────────────────── │   ← 一条触发线记号
│ > 详情                           │
│ 自动压缩        [开关]  [压缩上下文]│   ← 独立一行，看起来像第二个工具
└──────────────────────────────────┘
```

| # | 问题 |
|---|---|
| 1 | **看起来像另一个工具**：自动压缩被「详情」折叠区隔在主值之外，与「上下文」没有视觉隶属关系 |
| 2 | **主值语义**：显示物理窗口占用；换到 1M 模型时用户会以为"还早"，而编码模式该守的是远低于窗口的工作集 |
| 3 | **详情混三类**：策略参数 / 能力开关 / 花销 |
| 4 | **表达不了"会发生什么"**：只有单点阈值，没有阶段、没有"历史在哪" |

## 2. 目标（同 v1）

让「上下文」一屏回答：① 离"该管理"还有多远 ② 下一步自动发生什么 ③ 被移出的历史在哪、能不能取回。

原则：**压缩是上下文的一种行为，不是一个并列的工具。**

## 3. 技术事实核实（v2 新增，决定方案可行性）

我核对过内置 pi 0.85.1 的扩展 API 与 RPC 协议，结论如下（都有代码依据）：

### 3.1 可观测性：**RPC 事件已经存在，且砚已经在收**

| 事件 | 字段（实测） | 砚现状 |
|---|---|---|
| `compaction_start` | — | 已处理（只标记 streaming + 刷新状态） |
| `compaction_end` | `reason`（如 `threshold`）、`status`（`completed` / `declined`）、`entryId`、`lane`、`runId`、`endedAt` | 已处理（只标记结束 + 刷新） |

pi 侧还存在 `compaction_delta`、`compaction_cost`、`compaction_declined`、`session_compact_failed`、`before_compaction`、`autocompact` 等名字，需在实际运行时确认哪些会经 RPC 转发（这不是阻塞项）。

**结论**：批注第 2 点成立 —— 阶段 2 的"正在压缩 / 已完成 / 被拒绝 / 原因"**不需要 extension**，只要把已到达的事件字段用起来。

### 3.2 执行层：pi 扩展提供两个真正能改上下文的钩子

| 钩子 | 语义（源码行为） | 用途 |
|---|---|---|
| `context(messages)` | 扩展收到**发给模型的完整消息数组**，可返回 `{ messages }` 替换它 | **Tool Sweep / Episode Fold 的执行层** |
| `session_before_compact` | 可返回 `{ cancel }` 取消，或返回 `{ compaction }` 用自己的结果替换 pi 的摘要 | **结构化 Coding State 摘要**（替换对话式总结） |
| `before_agent_start` | 可改系统提示（已在用：自主模式、语言、回答档位） | 注入当前任务契约等 |

**结论**：批注第 3 点成立 —— 多阶段管理是**可实现的**，而且执行层能落在 pi 扩展里，砚负责决策。这也说明 v1 把阶段 3 写成"关掉 auto-compaction + 调 `compact()`"确实不够：那只是"更早/更晚做一次完整压缩"。

### 3.4 职责边界（已定）

| 侧 | 模块 | 负责什么 |
|---|---|---|
| **砚（桌面端）** | `ContextPolicy` / `ArchiveStore` / `Settings` / `UI State` | **什么时候做什么**：算工作集预算、决定触发哪一阶段、保存归档元数据、把状态反映到 UI |
| **pi Extension** | `ContextTransformer` / `CompactionAdapter` / `RecallTool` | **具体怎么改变送给模型的上下文**：`context` 钩子做 tool sweep / episode fold / recall 注入，`session_before_compact` 接管结构化压缩 |

边界：**原始 session/history 保持完整**，Extension 只改 active model context；不 fork pi core。

### 3.3 现有能力清单（砚已接）

`compact(customInstructions)`、`set_auto_compaction(enabled)`、`compactionInfo`（阈值/保留/预留）、模型 `contextWindow` 与 `maxOutputTokens` 能力表。

## 4. 目标信息架构（分两态）

### 阶段 1 态：**忠实显示 pi 当前真实状态**（不含未生效的工作集）

```
┌ 上下文 ─────────────────────────── 36k / 400k ─┐
│ 9%                              ╷ 触发线 384k    │   ← 主值仍是物理窗口
│ ▬▬▭──────────────────────────────────────────── │
│ 自动压缩  [开关]                       立即压缩   │   ← 归位：进上下文主体
│ 详情 ⌄                                          │
│   容量      窗口 400k · 保留最近 20k · 预留 16k   │
│   最近一次   阈值触发 · 已完成（或：未发生过）      │
│   本轮花费   $0.32                               │
└─────────────────────────────────────────────────┘
```

要点：**不出现**工作集数值、不出现三阶段记号、"详情"里加一行**最近一次压缩的事实**（来自 §3.1 的 `reason`/`status`）。

### 阶段 3 态：接管后切到工作集视角

```
┌ 上下文 ───────────────────────────── 36k / 240k ─┐
│ 15%   [清理]      [折叠]        [压缩]             │   ← 文字标记，不写 100%
│ ▬▬▭────────────────────────────────────────────── │
│ 下一步：清理旧工具输出（约 168k 时）                │
│ 自动压缩  [开关]                        立即压缩   │
│ 详情 ⌄  物理窗口 1M · 预留 32k · 余量 20k · 已归档 12 段 │
└──────────────────────────────────────────────────┘
```

三个记号写成「清理 / 折叠 / 压缩」，**百分比只放 hover 与详情**——避免"100% = 上下文满了"的误读（1M 模型下 100% 只等于物理窗口的 24%）。

## 5. 工作集与预算公式（v2 修订）

```
responseReserve = clamp(preferredReserve, 16_000, contextWindow × 0.25)   // preferred = 32k
safetyMargin    = max(8_000, contextWindow × 0.02)

workingSet      = min(
                    240_000,                                  // 编码模式天花板
                    contextWindow × 0.70,                     // 窗口比例
                    contextWindow - responseReserve - safetyMargin
                  )

triggers = { sweep: 0.70 × workingSet, fold: 0.85 × workingSet, compact: workingSet }
emergency = min(0.90 × contextWindow, contextWindow − responseReserve)
                                        // 物理兜底，防止策略自身出 bug 顶爆；
                                        // 但不能突破输出预留（§12.1 / D31）
```

验算（确认小窗口不会冲突）：

| 物理窗口 | 输出预留 | 安全余量 | 工作集 | 说明 |
|---|---|---|---|---|
| 64k | 16k | 8k | **40k** | 由 `窗口 - 预留 - 余量` 决定，不被 44.8k 卡住 |
| 128k | 32k | 8k | **88k** | 同上 |
| 256k | 32k | 8k | **179k** | 由窗口比例决定 |
| 1M | 32k | 20k | **240k** | 由绝对上限决定 |

## 10. 阶段 2 落地记录（2026-09-16）

### 10.1 接口落地：多了一个状态，并且拆成两份记录

| 决定 | 为什么 |
|---|---|
| `CompactionStatus` 加 **`cancelled`** | 实测中止给的是 `aborted: true`。把它归进 `failed` 会把“用户按了停止”说成“压缩崩了”；归进 `declined` 也错（那是上游主动不压）。 |
| `running` 与 `last` **分开两份**（`SessionState.compaction` / `.lastCompaction`） | 一条记录做不到：开始新一次压缩时要么擦掉上一次的结果（“正在压缩”时看不到上回压了多少），要么两个字段打架。分开后两者可以同时显示且永远不会矛盾。 |
| 多带 `beforeTokens` / `afterTokens` | `result.tokensBefore` / `estimatedTokensAfter` 本来就有。“上下文突然短了一截”的定量版本（`3.3k → 152`）；pi 不给就不显示。 |
| 自愈：pi 的 `get_state.isCompacting` 说“没在压”且本地还写着 running → 清掉 | 与 D19（文件树卡在“正在读取目录…”）同一类：少一条结束事件就会留下永久 spinner。 |
| 没有记录时**不渲染**“最近一次”这一行 | 从磁盘打开的历史会话可能早就压过，而砚不读会话文件里的 compaction 条目 —— 写“未发生过”是假陈述。 |

### 10.2 顺手发现的两个缺陷（已登记 D21 / D22）

它们都直接否定「界面上的数就是生效的数」这个前提，所以属于阶段 2 必须处理的东西：

- **D22**：用户级设置原来拼的是 `~/.pi/agent/settings.json`。pi 拿到的却是
  `PI_CODING_AGENT_DIR`（= 砚的 `PI_AGENT_DIR`）—— 便携版 / `YAN_PI_DIR` 下两份不是
  一个地方，界面会照另一份文件算触发线。已改为跟 `PI_AGENT_DIR`。
- **D21**：项目级 `.pi/settings.json` 只在 pi **信任该项目**时生效（该文件本身属于
  trust-requiring 资源），而 RPC 模式没有信任弹窗 —— 所以未在终端里 Trust 过的项目，
  其压缩设置会被 pi 整份忽略。实测三组对照：全局 → 第一轮就触发；只放项目级且无
  `trust.json` → 一轮都不触发；补上 `trust.json` → 又触发。已改为：**只把真会生效的那份
  当生效值**，并在详情里明说“项目的 .pi/settings.json 未生效”。

### 10.3 证据

| 项 | 证据 |
|---|---|
| 自动（阈值）压缩 | `npm run test:live -- compactionstatus`（cost 1）：真实压缩事件 `{reason:'threshold', result:{tokensBefore,estimatedTokensAfter}}` → 界面「已达阈值 · 已完成 · 3.3k → 152」 |
| 手动压缩**成功** | 同一场景：先关掉自动压缩（并断言行为真的被关住），再点「压缩上下文」→「手动 · 已完成」 |
| 手动压缩**失败不静默** | 同一场景：重复压缩 → pi 原文 `Compaction failed: Already compacted` 出现在详情里（不是一句“未知错误”） |
| reason × status 全表 | `declined` / `cancelled` / 未知原因（显示原文）/ 两行并存 → 探针第 4 节注入断言；分支逻辑单测 60+ 条 |
| 视觉 | `docs/design/preview/matrix-compaction-1440x900-100-{dark,light}-2026-09-16.png`（`npm run visual:matrix` 的 `compaction` 状态，带溢出与关键元素硬断言） |

### 10.4 剩余限制

- **`status` / `entryId` 那条 durable lane 形状没实测到**：归一化保留了分支，但没有真实
  场景能构造出来；目前所有实测事件都走 `result` / `errorMessage`。
- 会话文件里的 `compaction` 条目**仍未读**：切回旧会话时“最近一次”是空的（界面
  就不显示该行），压缩摘要也没进对话流。
- `declined` 只在 durable lane 出现，实测没碰到；“已跳过 + 解释行”目前只有注入证据。

## 附录 A · 阶段 0 接口草案

```ts
/** 上下文预算：由模型能力 + 策略参数推出 */
export interface ContextBudget {
  contextWindow: number          // 物理窗口（来自模型能力表）
  responseReserve: number        // 输出预留（§5）
  safetyMargin: number           // 安全余量（§5）
  workingSet: number             // 有效工作集上限
  triggers: { sweep: number; fold: number; compact: number }
  emergency: number              // min(0.90 × contextWindow, contextWindow − responseReserve)
}

/** 一次上下文变换：UI 状态与归档都从这里读。
 *  空闲态不是一种 operation —— 用 `currentOperation = null` 表示，不要加 `idle` 类型。 */
export interface ContextOperation {
  id: string
  kind: 'tool-sweep' | 'episode-fold' | 'compaction' | 'recall'
  status: 'running' | 'completed' | 'declined' | 'failed'
  reason: 'threshold' | 'manual' | 'overflow' | 'task-boundary'
  startedAt: number
  endedAt?: number
  beforeTokens: number
  afterTokens?: number
  archivedRefs: string[]         // 被移出 active context 的内容引用
  error?: string
}

/** 归档元数据（active context 之外的无损历史） */
export interface ArchiveEntry {
  ref: string                    // 例如 ctx://tool/8291
  kind: 'tool' | 'episode' | 'file' | 'diff'
  label: string
  createdAt: number
  tokens: number
  /**
   * 三态，而不是 boolean —— 「历史仍被保存」与「模型具备回溯能力」是两件事：
   *   none   不可恢复
   *   manual 仅砚/用户可恢复（历史已归档，模型取不回）
   *   agent  模型可通过 context_recall 主动取回
   * UI 只在 `agent` 时才能写「模型可回溯」。
   */
  recallable: 'none' | 'manual' | 'agent'
}

/** 策略参数（默认值取参考实践，可在设置里暴露） */
export interface ContextPolicy {
  enabled: boolean
  workingSetCap: number                                  // 240_000
  windowRatio: number                                    // 0.70
  recentTail: { target: number; max: number }             // 32_000 / 48_000（目标容量，切割按原子单元，§12.4）
  triggers: { sweep: number; fold: number; compact: number } // 0.70 / 0.85 / 1.00
}
```

事件映射（阶段 2 用 · **已按实测修正**，见 §10.1）：

|---|---|---|

**两处修订（审核意见）**

1. **兜底线不减安全余量**（提点修改 1 的"更保守"写法）。小窗口下工作集正好由
   `窗口 − 预留 − 余量` 决定，再减一次余量会让兜底线**等于**压缩线（64k 下都是 40k）；
   而"兜底不看是否上膛"是全系统唯一绕过上膛的路径 —— 两者相等就退化成
   "小窗口模型每轮都可以重试压缩"，正是修改 3 自己要防的事。取 `min(窗口×90%, 窗口−预留)` 后
   `emergency > triggers.compact` **恒成立**（余量 ≥ 8k > 0），兜底仍然是兜底。
2. **"低收益 → 不再频繁 Sweep"要限定为"本轮跳过 + 抬高门槛"，不是永久禁用**。
   工具输出是持续产生的：这次没有可回收的旧 tool result，下一轮可能就有一批。
   连续低收益该表达"现在不值得"，而不是"以后都不值得"。

**提点里没提、但阶段 4 必须一起定的两件事**

- **UI 文案随语义变**：水位线从"到线就做"变成"进入候选"之后，清理/折叠那两档
  **不能再写"下一步：清理旧工具输出"**（会被理解成承诺）。阶段 3 的「下一步」只报
  compaction，而它确实到线就压，所以现在不用改；等阶段 4 接上清理/折叠，这两档要改成
  「达到后会先看有没有可回收的旧工具输出」这类候选语义 —— "界面数字 ≠ 实际行为"
  是本项目最不能犯的错（D21/D22）。
- **降级路径**：每个变换都必须能在失败/超时后**退回 pi 原生行为**，不能把上下文留在半改状态
  （结构化压缩失败 → 交回 pi 自己的摘要；sweep 失败 → 一条消息都不动）。
  取证方式：探针里注入一个必然失败的结果，断言 active context 与原始 session 都没被破坏。

### 12.1 兜底公式（修改 1，已落地 · D31）

```
emergency = min(窗口 × 90%, 窗口 − 输出预留)      // 物理兜底不能突破输出预留
```

| 窗口 | 输出预留 | 工作集 | 压缩线 | 兜底线（新） | 兜底线（旧） | 旧值的问题 |
|---|---|---|---|---|---|---|
| 64k | 16k | 40k | 40k | **48k** | 57.6k | 只剩 6.4k 给回答（预留 16k） |
| 128k | 32k | 88k | 88k | **96k** | 115.2k | 只剩 12.8k 给回答 |
| 256k | 32k | 179.2k | 179.2k | **224k** | 230.4k | 越过预留 6.4k |
| 1M | 32k | 240k | 240k | 900k | 900k | 不变（90% 更小） |

三条必须对**所有**窗口成立的不变式（单测逐点扫过 1k–2048k 的窗口，见
`scripts/test-context-policy.mjs` 第 3b 节）：

1. `emergency ≤ 窗口 − 输出预留` —— 硬规则本身；
2. `emergency > triggers.compact` —— 兜底仍是兜底（不然会顶掉上膛与冷却）；
3. `emergency ≤ 窗口 × 90%` —— 用户调小 `emergencyRatio` 时仍然生效。

**与 pi 原生线的关系**：砚的预留（大窗口 32k）≥ pi 的 `reserveTokens`（默认 16.4k）时，
兜底线一定早于 pi 自己那条 `窗口 − reserveTokens` —— 砚先动、pi 最终兜底，层次不变。
反过来如果用户把 pi 的 `reserveTokens` 调得比砚的预留还大，pi 会先压：那是用户的显式选择，
砚不覆盖它（砚不写 pi 的设置文件）。

### 12.2 触发语义：水位决定"该关注"，可回收量决定"值不值得做"（修改 2）

```ts
interface ReclaimEstimate {
  reclaimableTokens: number   // 这次变换最多能腾出多少 token（上界估计）
  reclaimableRatio: number    // 相对当前用量
}
```

```ts
triggerReached && (reclaimableTokens >= minReclaimTokens || reclaimableRatio >= minReclaimRatio)
```

| 阶段 | 是否受收益门槛约束 | 为什么 |
|---|---|---|
| `tool-sweep` | ✅ 受 | 它是最便宜的一档，"收益太小就别动"代价很低 |
| `episode-fold` | ✅ 受 | 一次模型调用换 2k token 不值得 |
| `compaction` | ❌ **不受** | 它是"必须做点什么"的那条线：压不动也要压，否则接下来只剩兜底线与输出预留，没有第三个选项 |

估算从哪来（都不需要额外模型调用）：

- Sweep：候选集就是"已经不在最近 `recentTail` 窗口里的 tool result"，它们的 token 数**可以直接算**。
- Fold：候选集是"已关闭、且不在 recentTail 里的 Episode"，上界 = 这些 Episode 的 token 总和
  − 预计 `EpisodeState` 的 token；实际收益用 `beforeTokens − afterTokens` 校准（§12.10）。
- 估算只是**准入**，不是承诺：每次执行后都要记真实收益，下一轮的估算用实测值修正。

`minReclaimTokens` / `minReclaimRatio` 初值留待压力测试（§12.12 P2），但**必须有**：
没有它，170k 工作集只剩 2k 可回收时也会跑一次 sweep，界面与日志全是"整理了但没变化"。

### 12.3 每个阶段都有自己的运行状态（修改 3）

```ts
interface ContextStageRuntime {
  armed: boolean
  lastRunAt?: number
  cooldownUntil?: number
  lastBeforeTokens?: number
  lastAfterTokens?: number
  lastReclaimedTokens?: number
}

type ContextStageRuntimes = Record<'tool-sweep' | 'episode-fold' | 'compaction', ContextStageRuntime>
```

统一流程（阶段 4 照抄这一条，不要再各写一套）：

```
到线（候选）
  → armed?            否 → 记「待重新上膛」并退出
  → cooldown 到期?    否 → 退出
  → 估算可回收量       不足 → 跳过本轮（只记录：不改 armed、不重置冷却）
  → 执行
  → 记录 before/after/reclaimed、lastRunAt、cooldownUntil
  → disarm（armed = false）
  → 满足重新上膛条件（用量回落到 `线 × 0.9` 以下，或距上次超过重试窗口）后再 armed = true
```

**不许**"超过阈值 → 每轮都尝试执行"。阶段 3 已经踩过这个坑：`armed`/冷却/重试窗口
这三个参数就是为这件事存在的（`POLICY_COOLDOWN_MS` 30s、`POLICY_REARM_RATIO` 0.9、
`POLICY_REARM_MS` 5min，见 §11.2 与 D30）。阶段 4 落地时把这三条从"压缩专用"改成
**每阶段的默认值** —— `ContextPolicyState`（`src/shared/context-policy.ts`）就是这套机制
在单阶段（只有压缩）下的形态。

跳过（收益不足）与失败要分开记：跳过不改 `armed`（本来就还没动手），
失败要 disarm（否则会在同一轮里反复试）。

### 12.4 `recentTail` 与原子上下文单元（修改 4）

```ts
type ContextAtomicUnit =
  | { kind: 'user-turn'; entryId: string }
  | { kind: 'assistant-turn'; entryId: string }
  | { kind: 'tool-interaction'; callEntryId: string; resultEntryId: string }
  | { kind: 'agent-turn'; entryIds: string[] }   // user + assistant + 该轮所有 tool calls/results
```

- `recentTail.target = 32k`、`max = 48k` 是**容量目标**，不是切割位置：
  为了凑到 32k 而把一条 tool interaction 劈开是**禁止**的。
  实际尾部是 29k / 35k / 41k 都合法（语义完整优先于精确 token 数）。
- 最细粒度是 tool interaction：`assistant tool_call` 与它的 `tool_result` **不可分离**。
- 切割规则：从新往旧累加到 ≥ `target` 为止，然后对齐到 turn 边界；
  超过 `max` 也要继续往前退到最近的 turn 边界，而不是硬截。
- 硬约束（禁止产生）：
  - 留 `tool_call` 却清掉对应 `tool_result`；
  - `tool_result` 被截一半；
  - 系统提示 / 当前任务契约被当成可回收内容；
  - **（2026-09-17 补，N21-10）正在使用的 diff 不得删除**；
  - **（2026-09-17 补，N21-10）用户明确约束不得降级为普通历史信息**；
  - **（2026-09-17 补，N21-10）不得从 assistant 的 reasoning / output 中间切割**。
  唯一例外：Sweep 已经**显式**把该结果替换成 tombstone + `ctx://` 引用（§12.5）——
  那时剩下的不是"半条消息"，而是一条合法的、指向归档的占位。

**已落地为纯函数（N21-10，2026-09-17）**：`resources/pi-extensions/context-safety.js` +
单测 `scripts/test-context-safety.mjs`（42 条，进 `npm run test:unit`）。阶段 4 的扩展
在真正动 messages 之前调 `violations()`，非空就放弃这次压缩（宁可压不动，也不要发坏上下文）。
两条实现上的判断，别改回去：

- **"保护"分两档，强度不同**：
  · **硬留**（必须留在原始窗口里）：系统提示/契约、**正在使用的 diff**；
  · **可带走**（可以离开窗口，但必须进状态）：**用户约束**、未解决的错误。
  若把"用户约束"也当成硬留，cut 就永远退不到约束之后 —— 实际永远压不动；
  而"带走"这件事由 `carryOver()` 交出去、由 `violations()` 核对（忘了带会被抓）。
- **契约落在切片区里时，cut 选择"退到它之前"而不是"悄悄丢掉它"**：宁可这次不压，
  也不发一份少了任务契约的上下文。装配层（§12.5/N21-5）本来就会重新发出 system 与
  `<TASK_STATE>`，所以在真实链路上这种情况应当很少见；出现即说明该把契约提进状态。

与 pi 的关系：pi 自己也有 `compaction.keepRecentTokens`（保留最近多少 token），那是 pi 内部
压缩用的。阶段 4 的扩展自己决定 active context 的尾部，**不要两边都改**
（"砚不写 pi 的设置文件"这条界限不变）。

### 12.5 Tool Sweep 是确定性压缩，不是"再问一次模型"（修改 5）

默认**不调用模型**。旧工具结果 → 墓碑（tombstone）：

```text
[Archived tool result]
Tool: read
Target: src/foo.ts
Original tokens: 18,421
Ref: ctx://tool/8291
```

必要时保留**确定性元数据**（从结果里直接抄，不做推断）：退出码、错误行数、文件路径、
行区间、测试通过/失败数。

| 适合 Sweep | 不适合 |
|---|---|
| 旧文件整读（`read`）、目录列表 | 最近 `recentTail` 里的任何东西 |
| 长 stdout / build log / 测试日志 | 当前正在用的工具结果 |
| 网页全文、长 diff | 系统提示与任务契约 |
| 重复的 tool result、已失效的搜索结果 | 用户消息（任何情况下） |

原则：**快、便宜、可预测、信息损失边界清晰、原文可 Recall**。
sweep 必须**幂等**（同一份消息数组跑两次结果一致），否则界面上的"已归档 N 段"
会和真实 active context 对不上 —— 这一条可以直接单测。
真正需要语义理解的部分留给 Episode Fold。

### 12.6 Episode Fold 输出"工作状态"，不是"聊天摘要"（修改 6）

```ts
interface EpisodeState {
  id: string
  objective: string
  outcome: string
  decisions: { decision: string; reason?: string }[]   // 为什么这样做
  constraints: string[]                                // 什么不能改
  filesChanged: { path: string; summary?: string }[]
  failedAttempts: string[]                             // 试过但失败（含失败原因）
  unresolved: string[]
  importantRefs: string[]                              // ctx:// 引用
  sourceRange: { from: string; to: string }            // 指回**原始**条目 id（§12.7）
  tokensBefore: number
}
```

- 最重要的四栏是 `decisions` / `constraints` / `failedAttempts` / `unresolved` ——
  普通摘要把它们全丢掉，而它们正好是 coding agent 之后最容易重复踩坑的信息。
  字段可以为空，但**空必须在 schema 层面表示"确实没有"，而不是"忘了问"**：
  生成时按固定问题清单逐条填（要做什么 / 做成什么 / 为什么 / 什么不能改 /
  试过什么失败了 / 还差什么）。
- 关闭条件（何时可以 fold）：任务边界（用户换题目）、阶段完成、用户明确确认。
  没有关闭条件就不 fold —— 把"还在进行的活儿"折叠掉会直接误导下一步。
- 折叠结果要能被 Recall 取回原文（`ctx://episode/<id>`，对应 `ArchiveEntry.kind = 'episode'`）。

### 12.7 禁止递归摘要（修改 7，硬约束）

```
Episode 1 原始消息 → EpisodeState 1
Episode 2 原始消息 → EpisodeState 2
Episode 3 原始消息 → EpisodeState 3
active context = [EpisodeState 1..n] + recentTail        ← 允许
```

```
EpisodeState 1 + EpisodeState 2 → 新的自然语言摘要         ← 禁止
```

- **判据（怎么发现违反）**：`EpisodeState.sourceRange.from/to` 必须指回**原始条目**。
  某次 fold 的 sourceRange 落在另一份 EpisodeState 上，就是递归摘要 —— 单测直接断言。
- 结构化压缩需要全局状态时：**读结构化 EpisodeState + 仍然有效的原始状态 → 重建 CodingState**，
  而不是"摘要旧摘要"。
- 为什么：① 每层摘要都丢一点，且丢的偏偏是最不容易被模型注意到的约束类信息；
  ② 漂移不可追溯（无法回答"这条结论从哪来"）；③ 递归之后 `ctx://` 引用的可信度下降。

### 12.8 Structured Compaction 的 schema（修改 8）

`session_before_compact` 返回 `{ compaction }` 时用这份结构（替换 pi 自己的对话式摘要）：

```ts
interface CodingState {
  task: { objective: string; currentPhase: string }
  currentState: string[]
  decisions: string[]
  constraints: string[]
  files: { path: string; state: string }[]
  completed: string[]
  failedAttempts: string[]
  unresolved: string[]
  nextActions: string[]
  episodeRefs: string[]      // 被折叠的 EpisodeState id（不重新摘要它们）
  archiveRefs: string[]      // ctx:// 引用
}
```

它要回答的七个问题（写进生成清单里的固定提问）：

```
现在在做什么？已经做成什么？为什么这样做？什么不能改？
哪些方案试过但失败？还有什么没解决？下一步是什么？需要查历史时去哪里？
```

- 这是 **State Reconstruction**，不是 Conversation Summary：禁止"过去聊天主要讨论了……"这类句子。
- 与 §12.7 配合：`episodeRefs` 是引用不是内容 —— 不把 EpisodeState 再摘一遍。
- 降级：结构化生成失败/超时 → 交回 pi 自己的摘要（不 cancel），
  并在 UI 上标"结构化压缩失败，已退回 pi 原生摘要"，不静默。

### 12.9 Recall：独立预算与生命周期（修改 9）

```ts
interface RecallPolicy {
  maxTokensPerCall: number        // 单次召回上限
  maxActiveRecallTokens: number   // 同时驻留在 active context 的召回内容上限
  maxEntriesPerCall: number
  ttl: 'turn' | 'episode'         // 召回内容的保质期
}
```

反例（提点给的，必须用预算挡住）：

```
压缩后 240k → 100k
Recall A +50k → 150k
Recall B +60k → 210k
Recall C +70k → 280k        ← 绕过 ContextPolicy，直接顶穿工作集
```

- **召回是"读取历史"，不是"永久恢复历史"**：`ttl = 'turn'` 的召回内容在本次推理结束之后
  就可以再次被清理；只有新产生的**结论**值得留下，形式是"结论 + `ctx://` 引用"。
- 召回量**必须计入用量**（界面上的 tokens 会涨，这是对的）：于是它会推进下一次触发判定，
  而不是藏在预算之外。这条要写进 `context_recall` 工具自己的描述里。
- 三态 `ArchiveEntry.recallable` 不变：只有 `agent` 允许模型自己召回；`manual` 只能由
  用户/砚发起。每次召回留审计（时间、大小、发起方、命中的 ref）。
- 超预算的行为要明确：**拒绝并回一句可解释的话**（"这次召回 70k 超过单次上限 20k"），
  不要静默截断成半份内容 —— 半份历史比没有历史更危险。

### 12.10 每次变换都要有收益反馈（修改 10）

```ts
interface ContextOperationMetrics {
  beforeTokens: number
  afterTokens: number
  reclaimedTokens: number     // before - after
  reclaimedRatio: number      // reclaimed / before
  durationMs?: number
}
```

- 阶段 2 已经有 `beforeTokens` / `afterTokens`（`CompactionRun`），这一节把它升级成**反馈信号**。
- 反馈规则：
  - 连续 N 次（初值 3）`reclaimedRatio < 3%` → 该阶段**本轮跳过并抬高门槛**
    （不是永久禁用，见 §12.0 修订 2）；把机会让给下一档（Sweep 让给 Fold，Fold 让给 Compaction）。
  - 收益为**负**（`after > before`，例如折叠引入了 schema 开销却没压住）→ 记失败并回退本次变换。
- 观测落到可读的地方：详情里"最近一次"已经显示 `3.3k → 152`，阶段 4 追加阶段名与累计节省，
  并按阶段分开统计（一个阶段的坏结果不该污染另一个）。

### 13.0 一句话结论

### 13.2 数值冲突：为什么不照抄 300k / 0.75

| | 参考方案（§7/§18） | 我们（已实现，§11.1） |
|---|---|---|
| 有效窗口 | `min(窗口 × 0.75, cap 300k)` | `min(240k, 窗口 × 0.70, 窗口 − 预留 − 余量)` |
| 1M 模型 | 300k | 240k |
| 256k 模型 | 192k | 179.2k |
| 64k 模型 | 48k（可能吃掉输出预留） | 40k（**减去预留与余量**，避免与输出抢空间） |
| 阶段 | 5 档（60/75/85/93 + 100） | 3 档 + 兜底（70/85/100 + `min(90%, 窗口−预留)`） |

理由（三条，都是硬的）：
1. **小窗口下 `窗口 × 0.75` 会侵占输出预留** —— 这正是我们上一轮修掉的 D31（64k 窗口 48k > 40k）。
   参考方案的公式没有减 `responseReserve`，直接照抄会把 D31 重新引入。
2. 我们的数值**有真实触发证据**（`contexttakeover` 5652 → 108、`contextemergency`、四个窗口的参考值断言），
   换默认值等于把已验证的行为换成未验证的。
3. 数值本来就应该"工程策略 + 模型级 override"，参考方案自己也这么说（§7 末句）。

**处置**：数值进 N21-7 做成**可配 + 模型级 override**（含"想用 300k/0.75 就把这两个值改掉"），
默认保持现状；`State Refresh` 这一档（60%）**单独采纳**——它在我们的三阶段里没有对应物，
而且是纯收益（刷新状态比压缩便宜得多）。

### 13.4 两套状态的关系（必须一次说清，否则会并存两套）

```
Task State（= 我们的 CodingState，§12.8）   全局一份，随会话推进演化，**永远排在最前**
        ▲
        │ 由 EpisodeState 汇总 + 压缩时重建
EpisodeState（§12.6）                       每段一段，折叠后不重写（§12.7 禁止递归摘要）
```

- 参考方案的 `TaskState` ≈ 我们的 `CodingState`：**同一个东西**，合并字段，不新建第二张表。
- 我们**多**一层 `EpisodeState`：它是"证据层"，保证 Task State 可重建、可追溯（`sourceRange` 指回原始条目）。
- 参考方案的"增量 delta 更新"用在 **Task State** 上（便宜、稳定）；EpisodeState 不做增量（它是快照）。
- **删除/失效**：Task State 的条目可 `superseded`；EpisodeState 不删（归档保留，靠 §12.9 的 Recall 取回）。

### 13.5 需要用户拍板的三点（不定就不开工的部分）

   换来的是长上下文条件下更好的推理质量。默认关闭、按档位/阈值开启 —— 要不要做？
2. **默认数值**：保持我们已验证的 `240k / 0.7 / 三档`，还是切成参考方案的 `300k / 0.75 / 五档`？
   （我的建议：保持默认 + 暴露 override，`State Refresh` 那一档单独加。）

   会话删除时一并清理 —— 这属不属于"用户数据"，需不需要在设置里可见/可清空？

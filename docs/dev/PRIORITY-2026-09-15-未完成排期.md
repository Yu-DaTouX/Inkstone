## 优先级定义

| 级别 | 判断标准 | 处理方式 |
|---|---|---|
| **P0** | 会产生**错误结果**、**进程/目录残留**，或**阻塞发布结论** | 先修，再谈验收 |
| **P1** | 主链路能力已有实现但**零真实验收**，或功能闭环缺最后一环 | 紧接着做，与 P0 同批 |
| **P2** | 体验、视觉、文案、边界补充；不影响正确性 | 批量补齐 |
| **P3** | 需要证书、目标系统、上游接口或产品决策，代码侧无事可做 | 不排期，等条件 |

**当前只剩一个待拍板项**：`episode-fold`（Task State 生成 + 注入）要不要**进默认接管集**。
第四轮外部意见与源码核查已就绪（[方案 §17.5](../design/方案-上下文工具内的自动压缩-2026-09-15.md)）：
它主张「默认开 + 长会话条件激活」，选项 A/B/C 已写成可拍板的形式。
**2026-09-17 晚更新**：拍板不必再等实现 —— 与开关无关的硬化项已全部落地（包括它最在意的
输入自净与独立 kill switch），会话级 gate 也已实现并用 `contextgate` 在真实链路验过「短会话不花钱」；
它用的三个信号里「settled turn 计数」已补上（`turnsSince`），只有依赖于主进程工作集的两条
（`contextUsage ≥ 60%` / `compactionIsImminent`）仍未接。
另外，外部复核（第二问）指出**固定 48k 阈值对小窗口模型有盲区**：64k 窗口的 workingSet ≈ 40k，
可能已经进压缩、而 fold 门槛还没到。当前阈值可用 `state.gate.minTokens` 覆盖，**自适应 clamp 未做**
（外部也说为它新增主进程 → 扩展的通道不值得）。
生成器已经落地并可真实取证（方案 §17），但它**默认关** —— 打开意味着每轮结束多一次无工具 completion
（额度与延迟用户已拍板可接受）；形状上可以带智能闸门（`shouldRefresh`：纯只读不触发）。
在拍板之前，`session_before_compact` 只在本会话已有状态文件时接管（默认即降级回 pi 摘要，
**这是设计好的降级路径，不是故障**）。

**实施级契约已完成并落地**（方案 §16.6 + §17）：coordinator 单飞、CAS 发布协议（`revision`）、
freshness 分档与 overlay、TaskState 预算与裁剪、dirty 阈值、`partitionContext` 注入切分、
两段式压缩顺序、验收矩阵（单测 + `before_provider_request` 级探针 + 冲突 fixture）都已写到可照做的粒度；
落盘走扩展与主进程共享的 `YAN_DATA_DIR/context-state`，主进程读路径做 schema 校验与安全丢弃（不需要新造 IPC 通道）。

改 `src/` 后跑 live 前必须先 `npm run build`；跑 Electron 前要 `env -u ELECTRON_RUN_AS_NODE`；
`release/砚数据/` 全程只读，升级验证只用副本。

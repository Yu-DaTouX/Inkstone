### D11 详情（已修，高）

**现象**（用户截图）：模型菜单里“思考强度”显示“上游未提供思考档位信息”，但该模型在 pi 里
`reasoning=true`，档位实际存在。

**根因**（真实 pi 实测 + 代码）：

1. pi 的 `get_state` **不返回** `availableThinkingLevels`（它只给 model / thinkingLevel / isStreaming / …）；
   档位的权威来源是 `get_available_thinking_levels` 命令。
2. 但 `agent.ts` 的 `setStateFrom` 把它当作唯一来源：
   `hasOwnProperty(data,'availableThinkingLevels')` 恒为 `false` → `normalizeThinkingLevels(undefined, false)`
   → `{ values: [], status: 'unknown' }`。
3. state 推送非常频繁（流式增量、工具调用、状态变化），**每条都会把档位重置成 unknown**，
   覆盖 `listThinkingLevels()` 刚写入的正确值 → 界面一直显示“上游未提供…”。

实测（直连内置 pi 的 RPC）：
```
set_model commandcode/deepseek/deepseek-v4.1-flash → success
数据源 get_available_thinking_levels → ["off","minimal","low","medium","high"]
```
→ **上游是有档位的，是砚把它丢了。**

**修复**：新增纯函数 `resolveThinkingLevels`（`shared/model-capabilities.ts`）——字段存在则以它为准；
缺失且模型未变则沿用上一次已知结果；模型变了才清空等回填。`setStateFrom` 改用它；
`model_change` 事件与首次连接（`setConn('ready')`）各补一次 `listThinkingLevels()`。

**验证**：单测 5 条（含“state 推送不得清空档位”回归）；live 探针 `thinking-levels` 实测
档位 = 关 / 轻度 / 中 / 高 / 极高，`thinkingLevelsStatus: known → known`（3.5s 多次推送后）。

**UI 路径实测（第二次，完全按用户操作：开菜单 → 搜索 → 点行）**：

| 点的那一行（截图里两个同名模型） | 实际模型 | 档位 | status |
|---|---|---|---|
| DeepSeek V4.1 Flash（第 1 行） | `deepseek/deepseek-flash` | 关 / 中 / 极高 / Max | known |
| DeepSeek V4.1 Flash（第 2 行） | `commandcode/deepseek/deepseek-v4.1-flash` | 关 / 轻度 / 中 / 高 / 极高 | known |

两者都通过，且 3s 后复查未被后续推送清空、菜单里不再出现“上游未提供……”。

> ⚠️ **验证前先确认跑的是哪份代码**：修复只进了 `out/`（构建时间戳见文件），
> `release/win-unpacked/砚.exe`、`砚-0.2.0-portable.exe`、`砚-0.2.0-setup.exe`
> 都是修复**之前**的旧构建 —— 用它们验证会看到旧行为。

**对照实验（2026-09-15，同一台机器两份 agentDir）**——说明“没配 API”与这个 bug 的关系：

| 场景 | `set_model` | `get_available_thinking_levels` | 旧代码下的 UI |
|---|---|---|---|
| 空 agentDir（无 `auth.json`） | 失败 | `["off"]` | *旧代码仍显示“上游未提供思考档位信息”*（因为 unknown 分支被错误触发） |
| 真实 agentDir（有 `auth.json`） | 成功 | `["off","minimal","low","medium","high"]` | 旧：显示“上游未提供”（D11 bug）；新：显示 5 档 |

结论：**“没配 API”会让档位真的变少（只剩 `off`），但“上游未提供……”这句文案的
出现是 D11 造成的** —— 两者叠加时用户看到的就是截图里的样子。修完 D11 后：有凭证→显示真实档位；
无凭证→不再弹误导文案（但“模型不可用”本身还需要更明确的提示，已登记 D12）。

### D13 详情（已修，中）

**现象**（用户）：人在**最新消息**，导航轨（左侧会话柄）的高亮却停在**第一格**。

**根因**（`components/chat/ConversationOutline.tsx` 的 `activeFromGeometry`）：
原实现只在“顶边已越过视口顶部（`top <= 8`）”的回合里挑最靠下的那个；
若**一个都没有**（内容不满一屏，或滚到底后最后几轮均在视口内），`best` 就停在初始值 `0` → 高亮第一格。

**修复**（判定顺序）：
1. 已滚到底（`scrollHeight − scrollTop − clientHeight ≤ 32`，给虚拟列表估算高度留容差）→ **最后一格**；
2. 有回合越过顶部 → 最靠下的那个（原逻辑保留）；
3. 没有越顶的 → 视口里最靠上的一轮（不再回落到第一格）。

**验证**：`test:live -- outline` 新增两条断言，实测「滚到最新 → 第 10 / 10 格」「滚到最顶 → 第 1 / 10 格」。

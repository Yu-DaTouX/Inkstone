## 0. 一句话结论

项目知识落地为 `YAN_DIR/project-knowledge/<projectId>/`：**不可变 revision 文件 + 原子替换的
manifest 索引 + 跨进程排他锁**。写入必须 CAS（`expectedRevision`），冲突把磁盘上的最新版本
交回调用方去合并；正文写不进去或索引提交失败都**不改 manifest**；manifest 半写时退回
`manifest.json.bak`（连备份也没了就按 revision 文件重建索引）。
删除立刻从可检索集移除，永久删除只留**无正文墓碑**（指纹 + 长度），同一段文字再提一次被拒。
排他锁的过期**不等于可回收** —— 同机必须 `kill(pid, 0)` 核实那个进程真的不在了。
`projectId` 只认**项目登记**：模型自报、`cwd` 反推、未登记目录都进不来。
单测 **2667/2667**（本片 **+153**），其中五条出口判据全部用**真实文件**取证。

## 1. 本片定稿的规则（S3 / S4 照这个实现）

### 1.1 目录与文件

```text
YAN_DIR/project-knowledge/<projectId>/
  manifest.json            当前指针集合（原子替换；索引，可重建）
  manifest.json.bak        上一版 manifest（崩溃恢复兜底）
  lock.json                排他锁（pid + host + expiresAt + token）
  entries/<id>/r<rev>.json 不可变 revision（正文在这里；已发布的永不重写）
```

四条理由，都是踩过才会痛的那种：

| 决定 | 为什么 |
|---|---|
| 正文与索引分开 | manifest 每次提交整份替换。正文塞进去等于每次提交都在赌全部内容；现在的代价是「最多影响一条」 |
| **先写正文，后写 manifest** | 顺序反了，manifest 会先指向不存在的文件。按这个顺序崩溃，最坏是多一个没人引用的 revision 文件 |
| 临时文件与目标**同目录** | 原子替换靠 `rename`；跨卷在 Windows 上直接失败（或退化成复制）。所以不用系统临时目录 |
| 锁文件里的 `token` | 释放时只删自己那把：别人回收过再重建的锁不能被误删 |

### 1.2 项目身份（只认登记）

`resolveProjectIdentity(requested, registry)` 是唯一入口，存储层的每个函数只接受它产出的
`ProjectIdentity`（**不是**裸字符串）：

- 只接受 `settings.projects` 里的 id（`null` / 未登记 / 形状非法 → 拒绝）；
- 传 `{cwd}` **不是**身份，是越权尝试（`bad_project_id`）；
- `registeredProjectIdForCwd` 反方向也只在 **已登记** 的 cwd 上给 id —— 未登记目录不开启跨项目检索
  （实施-03 §4），也**不现场派生新 id**（那就是「信任任意 cwd」）；
- id 形状 `[A-Za-z0-9][A-Za-z0-9._-]{0,79}` 且不含 `..`，在**目录函数里**再挡一次路径穿越。

### 1.3 写入（CAS + 置信类）

| 规则 | 落点 |
|---|---|
| 更新必须 CAS | `expectedRevision` 与磁盘上的当前 revision 不等 → `stale_revision`，回执带 `latest` / `latestManifest` |
| 新建必须是新 id | `expectedRevision: 0` 且 id 已存在 → `entry_exists` |
| 模型**不能**写 `user-confirmed` | 没有宿主带原话的 `hostCheck.userConfirmed` → `unconfirmed_confidence` |
| `verified` 必须有证据 | 无 `evidence` → `missing_evidence`；`status` 升 `active` 另需 `hostCheck.evidenceVerified` |
| 已确认条目不能悄悄降级 | `downgrade_confirmed` |
| 文本指纹去重 | NFKC + 空白折叠 + FNV-1a 64（16 hex），同指纹 → `duplicate` + `existingId` |
| 替代必须显式 | `supersedes` 指向不存在的条目 / 已删除条目 / 自己 → 拒绝；被替代的条目**也写一份新 revision** |
| `revision` 只在成功提交时 +1 | 条目与 manifest 各自记账；失败不涨 |

### 1.4 删除语义

| 模式 | 落盘 | 可检索集 | 旧候选 |
|---|---|---|---|
| 逻辑删除 | 新 revision，`status: 'deleted'`，**保留正文**（数据层可恢复） | 立刻移除 | 同指纹再提 → `revives_deleted` |
| 永久删除 | 新 revision 是**无正文墓碑**（`text: ''`、`evidence: []`、`tombstone: {digest, textLength}`），旧正文 revision 被清掉 | 立刻移除 | 同上（墓碑指纹仍在） |

永久删除必须带 `userAction: { by: 'user' }`，否则 `not_user_action` —— 「永久」只按明确用户动作执行。

### 1.5 锁与恢复

- **锁**：`open(lock.json, 'wx')` 抢，TTL 30s，等待上限 5s，每 25ms 重试；等不到报 `locked`
  （不静默继续写 —— 两个写者同时提交正是「后写覆盖前写」的现场）。
- **回收判据**（`canReclaim`，顺序就是「先核实、后删」）：
  1. 同机：`kill(pid, 0)` 说进程不在了 → 回收。**还活着就绝不抢**，哪怕 TTL 过期
     （TTL 只说明「可能卡住了」，不说明「可以抢」）；
  2. 认不出的锁文件（另一个进程刚创建还没写内容）→ 等 5s 宽限期；
  3. 别的主机：`kill` 核实不了 → 只有超过「TTL + 10 分钟宽限」才回收（否则网络盘上的崩溃会永久锁死）。
- **恢复顺序**：`manifest.json` → `manifest.json.bak` → 按 revision 文件重建索引。
  恢复时**不改备份**（那一轮的「上一版」正是要扔掉的坏文件，拿它覆盖备份等于把唯一的好副本也弄坏）。
  重建时每个条目取**最高的、还能解析的** revision（崩溃可能留下半写的高 revision）。
  两边都坏且重建不出任何条目 → `unreadable`：写入直接 `read_failed`，
  **绝不**当空库（那等于用空库覆盖）。

## 2. 相对「拟定形态」收紧 / 明确的地方

| 项 | 拟定 | 现在 | 为什么 |
|---|---|---|---|
| 文本指针 | manifest 只提「不可变 revision + manifest」 | 指针**只存指纹，不存正文** | 去重与墓碑判定不必读正文文件；manifest 里也搜不到知识正文（单测钉住） |
| 指纹 | 「文本指纹去重」 | NFKC + 空白折叠 + FNV-1a 64（**不是**密码学哈希） | 平台中立（渲染端 / `yan` CLI / 单测都能直接 import，不拉 `node:crypto`）；碰撞方向偏保守（挡住重复，不会把两条知识混成一条） |
| `supersedes` 的状态 | `superseded` 是状态之一 | 被替代条目**也写一份新 revision**（状态变化也是历史） | 只改指针会让「谁在什么时候替代的」不可审计 |
| 永久删除 | 「保留无正文 tombstone」 | 墓碑里额外留 `textLength`，并**清掉旧正文 revision** | 不真删正文就等于「永久删除」没发生；长度只用于诊断 |
| 死进程留下的锁 | 「过期锁必须核实进程再回收」 | 进程已死时**即使 TTL 未到**也回收 | 死进程不可能还在写；等 TTL 只是白白卡住用户（单测明确覆盖） |
| 「需复核」 | 派生状态 | 只给判据（`knowledgeNeedsReview`），**不删**用户决定 | 实施-03 §3：文件 / 分支变化把条目标记为需复核，而不是当作失效清掉 |
| 已确认条目的改写 | — | 没有新的用户确认就不能降级（`downgrade_confirmed`） | 与任务计划同一条立场：宁可拒绝，不要静默改写用户决定 |

## 5. 剩余限制（如实登记）

| 项 | 说明 |
|---|---|
| 没有检索 | 索引只有「指纹 → 指针」。S3 才能回答「哪几条和当前问题有关」，本片**不引入** n-gram / 向量 |
| 没有调用方 | `commitKnowledge` / `deleteKnowledge` 目前只被单测调用；`yan knowledge propose` 在 S4，界面在 S5 |
| 逻辑删除**不能恢复**（还没有 API） | 数据层可恢复（正文 revision 还在，`listKnowledge({includeDeleted:true})` 读得到），但缺一个显式的 `restore` 入口 —— 那是 S5 的「删除 / 恢复」动作，本片不发明 UI 语义 |
| 崩溃窗口可能采用一次未提交完成的写入 | 索引重建取每个条目最高的**可解析** revision。若崩溃发生在「正文写完、manifest 未提交」之间，重建会采用那份正文（内容是用户提交的，不是编造的）。要彻底避免需要写前写日志（WAL），本片按「宁可采用用户刚提交的内容」取舍 |
| 孤儿 revision 文件 | 正文写完而 manifest 提交失败时会留下一个没人引用的 `r<n>.json`（下次写同一个 revision 会覆盖它）。**崩溃遗留的临时文件**（`*.pid.seq.tmp`）会在下一次抢到锁时清掉，但没人引用的 revision 没有 gc |
| 同机 pid 复用 | 上一个实例崩溃、pid 又被无关进程复用时，锁会被判成「还活着」而一直等（表现为 `locked`）。当前出口是用户删掉 `lock.json`；未做「启动时按 lock 里的时间戳+进程启动时刻」的更强核实 |
| 别的主机的锁 | `kill(pid, 0)` 只对本机有效。跨机（网络盘 / 便携数据目录）只能靠「TTL + 10 分钟宽限」回收，不是核实 |
| 只有单进程单元测 | 锁的互斥语义在单测里用「另一个进程真的死了 / 还活着」来判，没有起两个真进程同时抢锁的压力测试 |
| `validFor` 只是数据 | 「文件 / 分支变化 → 需复核」只有纯函数判据（`knowledgeNeedsReview`），还没有人在真实会话里喂它（S3 检索时用） |

## 6. 交给 S3 / S4 / S5 的接口

1. **身份**：CLI / UI 侧一律先 `resolveProjectIdentity(requested, settings.projects)`，
   再把 `ProjectIdentity` 交给 store。**不要**自己拼 `<projectId>` 字符串或从 `cwd` 派生 ——
   存储层只接受那个形状。
2. **读**：`listKnowledge(identity, { includeDeleted })` 拿到的就是**可检索集**（S3 在此基础上做
   关键词 / n-gram + 标签加权）。`knowledgeNeedsReview(entry, {branch, commit, existingPaths})`
   是「需复核」的唯一判据，S3 / S5 不要各写一份。
3. **写**：`commitKnowledge({ identity, request, hostCheck })`。
   - `request` 里**只有内容与 `expectedRevision`**；`id` 只在更新时给；
   - `hostCheck.userConfirmed` 必须是**用户在会话里的原话**（`quote` 非空），
     `hostCheck.evidenceVerified` 必须是宿主真核实过引用存在；
   - 失败回执里 `latest` / `latestManifest` 就是合并依据（`duplicate` / `revives_deleted` 还带 `existingId`）。
4. **删**：`deleteKnowledge`；永久删除必须传 `userAction: { by: 'user' }`。
5. **错误分层**：请求级失败回 `ok:false + code`（模型可自纠），
   存储级失败抛 `ProjectKnowledgeStoreError`（`locked` / `read_failed` / `write_failed` / `bad_project_id`）——
   后者**不要**翻译成「已保存」。
6. **S5 UI 的现成数据**：`status`（候选 / 生效 / 被替代 / 已删除）、`confidenceClass`、
   `tombstone.at`、`evidence`（sessionId / entryId / file / excerpt）都在条目上，界面直接显示真实来源，
   不要显示未经校准的可信度百分比。

## 2. 逐题结论

### 2.1 Q1 · 薄适配层：允许保留，但必须配防腐化机制

**定案（2026-09-18 用户拍板）：允许保留一个砚自有薄适配层。**
但它不是插件生态 —— 只承载「宿主无法通过 CLI / RPC 表达」的生命周期桥接与策略执行，
能落地到宿主服务 / 随包 `yan` 子命令的一律不得留在扩展里。

三方讨论的差别只在**怎么防止它退化**：

- 我原来只给了**一次性条件**（不注册模型工具、不冒充内置、诊断里标为应用能力）。
- GPT 指出真正的风险是「薄层会重新长成现在的 10 个扩展」，主张**规定允许的 hook、代码职责与依赖方向，并加 CI / 架构检查**。

**已落进** [实施-01 §1](实施-01-默认pi架构迁移.md)：一次性条件 + 持续约束（允许钩子清单、职责边界、架构检查）同时写入；
§1 已从「待确认的开放项」改为**已确认的边界**。

### 2.2 Q2 · N21-9：架构决策基准，不是现实现验收

GPT 与我结论相同（都要做），但它多给了一层**定性**，这层是有价值的：

- A/B 测的是 **State-First / Trace 这两个策略值不值得保留**，不是「当前扩展实现得好不好」。
- 所以必须**冻结现实现**（只跑既定四组与既定指标，不再追加功能或工程化），
  结论只能表述为「**该策略在当前实现下的收益**」，不能反推「未来载体必须是 pi extension」。

**已落进** [实施-06](实施-06-上下文管理收尾.md)。

### 2.3 Q3 · 澄清模式：验收要「真实受限」，实现可以跨轮

三方在「跨轮续行可以接受」上一致；分歧只在**兜底口径**：
方案允许退到「如实标注未满足」，我和 GPT 都要求**至少 allowlist 这一层必须真做**，不接受滑到提示词约束。

GPT 另外补了三个具体故障模式（我原话只写到「防重复消费 / 防抢先执行」）：

1. handoff 被**重复消费**；
2. 恢复后**重复执行**；
3. 标准轮在 readiness 记录**落盘前抢跑**。

对策：唯一 `transitionId`、消费幂等、**先持久化再启动**的顺序保证。

**已落进** [实施-05 §4](实施-05-工作模式与长任务续接-已完成.md)。

### 2.4 Q4 · 安卓：冻结「状态机与能力边界」，而不是冻结全部协议

方案 §7 自己就矛盾（「先补协议」但开发顺序把 A 原型排在前面）。三方给出的切分里 **GPT 的最精确**：

- 并行可以，但界面只能做到**「协议无关原型」**；
- 真正必须先冻结的是**连接状态机与能力边界**（连接态、授权态、能力可用性、断线语义），不是所有协议细节；
- `pairing` / `auth` / `transport` 必须做成**抽象状态**，否则原型会把「token 手填、局域网直连、单设备权限」这些临时机制固化成产品。

**已落进** [实施-08](实施-08-安卓远程管理.md)——这是对旧方案口径的**修订**（原方案允许原型与协议完全并行）。

### 2.5 Q5 · Git 两项：一项进 v2 backlog，一项留待决策

- 「按行 / 按块暂存」→ 明确列入 **v2 backlog**（有归属，不再是「待决策」）。
- 「丢弃工作区改动」→ **留待决策**；GPT 点出我漏掉的具体风险边界：
  预览不完整时 **rename / untracked / submodule** 都可能造成真实数据损失，
  其测试与确认成本远高于普通 Git action。

**已落进** [实施-07 §4 / §5](实施-07-Git与环境菜单收尾-已完成.md)。

### 2.6 Q6 · 两个可选入口（**已定：不做**）

这是三方里**唯一真正的冲突**：

| | 立场 |
|---|---|
| 方案 | `pi config`「需要时应**派一个真实终端**，而不是在设置里重新实现一遍」——等于给入口 |
| 我 | 默认不做 |
| GPT | 不做，而且「打开终端」本身就是**伪集成**；空壳入口会形成长期兼容债并让用户误判能力边界 |

我和 GPT 同侧。**定案（2026-09-18 用户拍板）：两个入口都不做** —— 设置里继续只提供
安装 / 卸载 / 更新，**不加「打开终端」入口**；托管站 PR 继续只支持 GitHub，界面如实说明。
方案的不同意见已记在 [实施-07](实施-07-Git与环境菜单收尾-已完成.md) 正文里作为历史依据。

### 2.7 Q7 · AGENTS.md 措辞：**实施前先改**（我改判）

我原来主张「随代码一起改」，理由是怕文档描述尚未实现的状态。**这条被驳回，理由更硬**：

- AGENTS.md 会**自动进入每次会话的系统提示**，它是**实际执行约束**，不是说明文档；
- 随代码改意味着实施那几轮里，agent 会**同时**收到「任务面板保持现状（不许改）」和
  「把任务工具收归内置（要改）」两条互相冲突的要求。

**结合后的解法**（同时满足两边顾虑）：措辞写成**「边界方向 + 明确标注未实施」**，
而不是「已经做完」。这样既不冲突，也不会把未实现状态写成现实。

**已落进** [AGENTS.md 第五节](../../AGENTS.md)（本次已同步改动），并作为
[实施-02](实施-02-任务工具内置化-已完成.md) / [实施-03](实施-03-项目知识与旧记忆清理-已完成.md) 的**第 0 步复核项**。

### 2.8 Q8 · 工程清单复选框：加注解 + 统一 stale 标记

同意 GPT 的加强版：只写一句注解**会被忽略**，要给已确认的旧项加**统一标记**。

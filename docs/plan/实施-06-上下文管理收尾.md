**N21-9 的定性（2026-09-18 三方结论，见 [决策记录 §2.2](决策记录-三方意见对照-2026-09-18.md)）**

它不是「给现实现做验收」，而是**架构决策基准**：

- 测的是 **State-First / Trace 这两个策略值不值得保留**，不是「当前扩展实现得好不好」；
- 因此必须**冻结现实现**：只跑既定四组与既定指标，**不再追加功能或工程化**；
- 结论只能表述为「**该策略在当前实现下的收益**」，**不能**反推「未来载体必须是 pi extension」；
- 收益不明显 → 该削减复杂度（薄层里对应的钩子就可以撒掉）；收益明显 → 薄层保留这些钩子的理由成立。
  两种情况都直接决定 [01](实施-01-默认pi架构迁移.md)-S1 第 7 项那份**允许钩子白名单的长度**（边界已允许保留薄层）。

### N21-9 的指标口径（已由第四轮外部意见补全，方案 §17.5.4）

- **主判据**：LCR（Lost Constraint Rate）相对下降 **≥ 25%**；成功率 non-inferior（不低于 baseline −3pp）。
- 另加：semantic contradiction rate（<1% / 1–3% / >3% 三档）、
  harmful-state attribution（>1% 则**关注入**而不是调阈值）。
- 成本要**单列** `stateGenerationInputTokens` —— 真正的开销是每 1–3 个 settled turn 的**全量快照输入**，
  不是 6000 输出上限；`stateOverhead > 25%` 则把增量 delta 从 P2 升 P1（当前决策是「不做」，升 P1 需重新评估）。
- LCR 要能在压缩后**逐条核对**用户约束。

## 3. ⚠️ 与架构迁移的冲突（本主题最重要的一段）

**现状**：N21 全部实现依赖 `resources/pi-extensions/` 里的
`context.js` / `context-transform.js` / `context-deep.js` / `context-producer.js` /
`context-safety.js` / `context-stage-runtime.js`，走的是 pi 扩展的 `context` 与
`session_before_compact` 钩子。

**边界已定（2026-09-18 用户拍板）**：砚**允许保留一个自有薄适配层**，
所以这些钩子**不是必须整体放弃** —— 但只有「宿主无法通过 CLI / RPC 表达」的才允许留在薄层里。
01 §6.1 已核实：**RPC 没有与 `context` / `before_provider_request` 等价的通用请求重写入口**，
所以这批钩子正是薄层的**候选成员**，不是要一律删掉的东西。

**仍有一个必须实测的未知**：pi 当前版本的这批钩子**是否都在**、载荷**是否够本文用**。
因此本主题的分支判定取决于 [01](实施-01-默认pi架构迁移.md)-S1 的实测结论：

| 分支 | 触发条件 | 06 要做什么 |
|---|---|---|
| **分支 A（钩子可用 → 走薄层）** | 01-S1 实测确认 `context` / `session_before_compact` 等钩子可用且载荷足够（**默认预期**） | 对应文件**迁进薄层并瘦身**（去掉业务逻辑与「注册模型工具」的部分），按 §2 正常收尾；同时落实 01 §1 的白名单与架构检查 |

> **实测进展（2026-09-18）**：一次 `--print` 跑通后确认
> `resources_discover → input → before_agent_start → context → before_provider_headers →
> before_provider_request → message_end`，且 `context` / `before_provider_request`
> **每一轮都触发**（见 [证据-01-S1 §6](证据-01-S1-可行性验证.md)）。
> **因此大概率落分支 A**（迁进薄层）。`session_before_compact` 要等一次真实压缩才能验，归本片 S1 完成。
| **分支 B（钩子缺失或载荷不够）** | 01-S1 实测发现某能力在 pi 里**没有等价钩子**（版本不提供，或载荷不足） | §2 的 N21-9 仍可做（它衡量的是**不同策略**的收益，可退化为「原生压缩 vs 宿主回合边界压缩」）；受影响能力按下方**止损表**逐项处理，**不再一律登记为未满足** |

两个分支可以**按能力分别命中**（不是全有全无）。

#### ✅ 分支判定已完成（2026-09-19）：**分支 A 成立**，逐能力结果如下

判定输入：01-S1 的钩子实测（[证据-01-S1](证据-01-S1-可行性验证.md) §6/§9，加上 HANDOFF 里真实链路的压缩接管记录）
+ [01 §1](实施-01-默认pi架构迁移.md) 的**语义契约 5 条**与三个出口。

| 能力 | 需要的时机 / 接口 | 官方路径是否保持契约 | 出口 |
|---|---|---|---|
| Tool Sweep（墓碑 + `ctx://`） | 请求前 `context` | ✗（无等价 RPC 入口） | **② 薄层**（`context.js`） |
| Task State 前置注入 | 请求前 `before_provider_request` | ✗ | **② 薄层** |
| 压缩两段式接管 | `session_before_compact` | ✗ | **② 薄层**（真实压缩下 `takeover 1 / fallback 0` 已取证） |
| 状态生成器（无工具 completion） | `agent_settled` + `ctx.modelRegistry.complete()` | ✗ | **② 薄层** |
| Deep Context Pass 1 | 同上 | ✗ | **② 薄层**（默认关 + 设置开关） |
| 请求前硬预算 | 请求前 `before_provider_request` | ✗ | **② 薄层** |
| `response-detail` / `language` 注入 | 请求前 `before_agent_start` / `before_provider_request` | ✗ | **② 薄层**（已实现） |
| 交互提问（`question`） | **回合中**等待回答 | ✗（官方只能回合后触发） | **② 薄层** —— 提问本身可以 `yan question ask` 表达（**不需要注册模型工具**），归 05-S3 |
| `context_recall`（模型工具） | — | **补齐必须注册模型工具** | **③ 登记为未满足**：去留由 N21-9 的 A/B 结论决定 |
| 浏览器控制 | 按需调用 | **五条全过** | **① 宿主服务 + `yan browser` CLI** —— ⚠️ **尚未迁移**（[01 §4](实施-01-默认pi架构迁移.md)），当前是 01-S5 的硬阻塞 |
| 任务清单写入 | 按需调用 | **五条全过** | **① 宿主服务 + `yan tasks apply`** —— ✅ 已完成（02） |

**三条结论**：

1. **没有任何一项落进分支 B 的止损表** —— 钩子都在、载荷够用（与 2026-09-18 的「大概率落分支 A」一致，
   现在由真实链路证据定为确定）。止损表降级为「pi 未来版本移除钩子时的预案」，
   **当前不启用**，也不得在任何文档里把预案写成现状（§3 的口径纪律仍适用）。
2. 薄层**允许钩子白名单** = 上表 ② 用到的五项：`context`、`before_provider_request`、
   `before_agent_start`、`session_before_compact`、`agent_settled`（已写回 [01 §1](实施-01-默认pi架构迁移.md)）。
3. 唯一的出口 ③ 是 `context_recall` —— 它不是钩子，而是**注册给模型的工具**，与薄层口径冲突。
   N21-9 若显示 State-First / Trace 收益不明显，就连钩子带工具一起撒；
   若收益明显，需要为它单独定一个落点（例如 `yan context recall`），**不得**以「反正要保留薄层」为由继续注册模型工具。

### 分支 B 的止损表（2026-09-18 二轮外部咨询定口径，见 [二轮记录 §2.4](决策记录-二轮外部咨询-2026-09-18.md)）

**能近似保住的三项** —— 做，但**必须始终标为「近似」，不得写成等价**：

| 能力 | 降级做法 | 丢掉了什么 |
|---|---|---|
| 请求前硬预算 | 宿主在**回合边界**做预算守卫（下一轮开始前按 token 估算裁剪） | 不是请求前拦截：本轮仍可能超限，只是下一轮不再变坏 |
| 压缩的两段式接管 | 退化为**宿主触发压缩**（调官方 `compact`，无法在摘要生成与替换之间插入自己的逻辑） | 失去原子接管：中间态不可控，失败恢复更粗 |
| Deep Context | 用**独立状态归纳**近似（宿主定期让模型产出状态块并存到宿主侧） | 归纳时机与请求时机脱钩，可能滞后一到两轮 |

**应直接标未满足的两项** —— **不要**硬找替代：

| 能力 | 为什么替代不了 |
|---|---|
| `<TASK_STATE>` 的位置保证 | 没有请求前重写入口就**无法**在任意位置插入内容——只能在回合边界追加，位置语义不成立 |
| `recall` 工具 | 模型若没有**可调用的回读入口**，它就无法主动取回归档内容；宿主 / 提示词代劳只是把它塞进上下文，**不是 recall** |

**口径纪律**：本节写完后，任何「近似」都不许在其它文档里被简称成原能力名
（例如「回合边界预算守卫」**不得**写成「请求前硬预算」，「宿主触发压缩」**不得**写成「两段式接管」）。

**在判定之前**：

- **不要删**任何 `context*.js` 代码、**不要**把它们从打包里移除、**不要在文档里写「已迁移」**。
- **不要**因为「反正要迁移」就停止 N21-9 —— 它的指标口径与策略对照与实现载体无关，先做不浪费。
- 分支判定结果要同时回写到本文、[01](实施-01-默认pi架构迁移.md) §5 矩阵、HANDOFF 的「剩余限制」。

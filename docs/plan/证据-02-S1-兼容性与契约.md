## 1. 事实核查（先说清 pi 的机制，别拿假设当契约）

| 事实 | 怎么核的 | 对契约束意味着什么 |
|---|---|---|
| pi **会自动发现** `<PI_AGENT_DIR>/extensions/` 下的扩展 | 在隔离 piDir 放一份 `.ts` 扩展（本轮用用户本机 `left-info-panel.ts` 的只读副本做对照），`get_commands` 里出现它的 `/panel`（`source=extension`） | 迁移期「旧扩展同时存在」是**现状**，不是我方假设。01-S5 之前，砚**不能**声称「默认不加载用户扩展」 |
| `get_entries` 给的是**会话文件里的条目**，不是「当前上下文」 | pi 运行时源码：`get_entries` → `sessionManager.getEntries()`（`resources/pi-runtime/dist/bundle`） | 旧任务快照不会因为压缩而「只剩尾巴」（与 D38 里 `get_messages` 的坑不同） |
| 载入会话时 **pi 自己会往文件追加**一条 `thinking_level_change` | 原封不动的 fixture 会话，`switch_session` 后末尾多一行，**前缀逐字节一致** | S1 出口的「逐字节比对」必须写成**「前缀不变 + 只允许追加」**；否则会得到一个必然失败或必须放宽的断言（方案原文的措辞据此修正，见 §5） |
| 不加载旧扩展时，旧 `left-panel-tasks` 条目**照样读得到** | 同一 fixture 会话，piDir 里**没有**任何用户扩展 → `todos` 仍是 4 条 | 「旧历史可读」不依赖旧扩展存在，是宿主对会话文件的只读解析 |
| 旧扩展的写入是**模块级全局 + appendEntry**（跨会话风险的来源） | 读用户扩展（只读）：`state.todos` 是模块级，`session_start` 从 entries 恢复 | 砚侧要能兜住「两个来源同时写」：见 §2 的单写者原则 |

## 2. 契约定稿（S2–S4 都按这份写）

### 2.1 数据

| 项 | 定稿 |
|---|---|
| 旧标识（**只读兼容**） | `left-panel-tasks`，形状 `{ todos: [{text, done, status?}] }` |
| 新标识（宿主日志，S3 写入） | `yan-task-plan`，形状 `{ schemaVersion, revision, operationId, todos }`（**保留** `todos` 兼容字段） |
| 身份判定 | `isTaskPlanCustomType()` **精确匹配**上面两个常量。**不再**用 `/task|todo/i` —— 那会让 `my-task-log` 这类第三方条目冒充任务（实施-02 §3：来源必须由受信清单决定） |
| 版本 | `TASK_PLAN_SCHEMA_VERSION = 1`；版本对不上按「读不了就当没有」，不猜 |
| 上限 | `maxItems: 200`、`maxTextLength: 2000`；超限**返回可读错误**，不静默截断 |

### 2.2 来源优先级（单写者原则）

1. 砚**只写** `yan-task-plan`（S3）；`left-panel-tasks` **永不回写、不批量转换**。
2. 同一轮里两种来源都写了 → **宿主日志优先**，与落盘先后无关
   （宿主与旧扩展是两个进程，谁先落盘是时序骰子）。
3. 旧条目只在该轮**没有**宿主快照时显示（所以升级用户的旧历史照旧看得到）。

> 已实现的是 2/3 的**解析规则**（`todoSnapshotsFromEntries`）与单测；1 要等 S3 真的开始写。

### 2.3 工具契约（`yan tasks apply`）

沿用 01-S2 的管道（**身份不由模型自报**）：

- `operationId` 绑定「会话 + 一次工具调用」；**同一 `operationId` 重放不得重复 `add`**、`revision` 不涨。
- 身份校验沿用能力端点：token + `(sessionId, projectId)` 逐一比对（伪造直接 403）。
- 回执含 `operationId`、结果 `revision`、实际变更项；结果文件仍是「摘要 + 落文件」。
- 六个操作：`set / add / complete / uncomplete / remove / clear`；`index` 从 1 开始，越界不得改状态。
- 取消：提交前取消 → 不写；提交后取消 → 返回**已提交结果**（避免用户误重试）。

### 2.4 恢复语义

按**当前会话条目**还原（不是「最近一个任意会话」的缓存）；空会话 → 空列表；分叉后只写当前分支。
旧扩展那份「模块级全局」不参与判断 —— 界面历史就是会话文件（AGENTS.md 第五节）。

### 2.5 旧扩展共存：可预期行为 + 诊断口径

**目标**：不双写、不串会话。**现状**（S1 时点）：

- 砚**不写**旧标识 → 结构上不可能「双写同一份数据」；
- 砚的读取只来自当前会话文件 → 不串会话；
- 但旧扩展**仍被 pi 加载**（它会向模型注册同名 `panel_todos`），这是迁移期事实，
  真正的收敛在 01-S5（默认不加载用户扩展）+ S3（宿主开始写 `yan-task-plan`）。

**诊断样例**（新增，输出到右栏「日志」分区，来源诊断见 §4）：

```text
[来源] 用户扩展 1 项：left-info-panel.ts（pi 启动时会自动发现并加载它们；砚不删除、不改写）
[来源] 砚内置薄层 6 项：browser.js、question.js、response-detail.js、language.js、capability-guide.js、context.js（显式传入，只挂生命周期钩子，不注册模型工具）
[来源] 检测到用户扩展：当前任务清单仍由扩展写入 `left-panel-tasks`，砚只读取并显示；砚内置任务计划落地后写入改走宿主日志，旧条目保持只读（两者不会互相覆盖）
```

第三行是**只在检测到用户扩展时**才输出的一句 —— 没有它，用户无法判断「同一份清单底下有几套写入路径」。
文案**不能**写「任务由内置任务计划维护」：S3 之前宿主根本不写任务，那是撒谎（单测里有一条专门钉住它）。

### 4.3 旧 JSONL「未被改写」的判据与结果

判据（`afterExit: taskFixtureReadonly`，`todos` / `taskext` 都挂）：

1. **前缀逐字节一致** —— 原有内容一个字节都不许动；
2. **追加的行里不许出现任务快照条目** —— 砚不得替模型伪造任务写入。

实测追加的是 pi 自己的 `thinking_level_change`（两个场景都一样）：

```text
{"type":"thinking_level_change","id":"...","parentId":"task0","timestamp":"...","thinkingLevel":"off"}
```

> ⚠️ **对方案原文的修正**：实施-02 §5-S1 原文写的是「旧 JSONL 逐字节比对证明未被改写」。
> 实测 pi 载入会话时会自己追加一行，所以「整文件 sha 不变」不可达；
> 现在钉的是「**前缀不变 + 只允许追加 + 追加里不许有任务写入**」，
> 这既覆盖了真正的风险（回写/批量转换/伪造工具调用），也不会因为 pi 的正常行为长期红着。

## 6. 顺手修掉的一个既有测试脆弱（不是产品缺陷）

`todos` 第 6 节有四条断言依赖探针**合成**的「回合运行中」状态
（`store.setState({ session: { isAgentRunning: true } })`）。
第 4 节为了找「没有任务的会话」连续切了几次会话，而 pi 的 hydrate 是**异步**的：
它迟到地推一次真实 `state`（store 里是**整体替换** `session`），把合成状态清成 false
→ 四条断言全红，而界面上根本没有回合在跑（诊断打印过现场：`isAgentRunning=false`、
`sessionId` 是第 4 节切过去的那条无任务会话）。

修法：注入前**等一次静默**（连续 1.5s 没有新的 `session` 对象），而不是加固定 `sleep`。
这是**测试脆弱**，不是产品回归；AB 验证过（临时注释掉本轮新增代码，四条照旧红）。

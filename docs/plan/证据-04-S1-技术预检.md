### 1.3 ⚠️ 附带发现：内置运行时的 `--version` 读的是**我们生成的清单**

`scripts/vendor-pi.mjs` 第 334–338 行会写一份最小 `package.json`
（注释原文：「最小 package.json：bundle 会读它取版本号」）。用副本改版本号即可复现：

```bash
T="$TEMP/yan-04s1"; cp -r resources/pi-runtime "$T/rt"
node -e "const fs=require('fs'),p='$T/rt/package.json',j=JSON.parse(fs.readFileSync(p,'utf8'));j.version='9.9.9';fs.writeFileSync(p,JSON.stringify(j,null,2))"
node resources/pi-runtime/dist/bundle/cli.js --version   # → 0.85.1
node "$T/rt/dist/bundle/cli.js" --version                # → 9.9.9   ← 变了
```

而同一份改过版本号的副本 **RPC 握手仍然正常**（`get_state` 返回 `{"success":true,…}`）。

**影响**：`--version` 是「跑起来实测」的证据，形式上强于读 `package.json`；
但对**内置**运行时代它读的就是 vendor 脚本写的那份清单，所以二者在正常流程下必然一致。
真正的代码身份由「vendor 时的源包版本 + 握手成功」共同保证（`vendor-pi.mjs` 末尾会真跑
`cli.js --version` + 一次 `get_state`，失败就非零退出）。**不要把「版本字符串」当成完整性校验。**

**砚的项目 lockfile 里根本没有 pi**（pi 不是本项目的 npm 依赖）。所以「锁定」实际由两件事承担：

1. `resources/pi-runtime/` 是一次 **vendor 快照**（`scripts/vendor-pi.mjs` 从全局/`YAN_PI_SRC`
   指定的 pi 包「原样搬运 bundle + 补最小依赖」），随应用分发；
2. pi 自己带 `npm-shrinkwrap.json`（它的依赖树被 pi 官方锁死在**源包**里）。

### 2.2 随包依赖 vs pi 的 shrinkwrap（逐项比对）

```bash
node -e "
const fs=require('fs');
const sw=require('C:/Users/YuDaTou/AppData/Roaming/npm/node_modules/@earendil-works/pi-coding-agent/npm-shrinkwrap.json');
for (const n of ['@earendil-works/chord','typebox','undici','@silvia-odwyer/photon-node','jiti']) {
  const v=JSON.parse(fs.readFileSync('resources/pi-runtime/node_modules/'+n+'/package.json','utf8')).version;
  const k=Object.keys(sw.packages).find(k=>k.endsWith('node_modules/'+n));
  console.log(n, 'vendored='+v, 'shrinkwrap='+sw.packages[k].version);
}"
```

```
@earendil-works/chord            vendored=0.85.1   shrinkwrap=0.85.1
typebox                          vendored=1.3.7    shrinkwrap=1.3.7
undici                           vendored=8.9.0    shrinkwrap=8.9.0
@silvia-odwyer/photon-node       vendored=0.3.4    shrinkwrap=0.3.4
jiti                             vendored=2.7.0    shrinkwrap=2.7.0
```

**判定：有限实现。** 三条关系成立且可复现：

- 运行实例版本（0.85.1）== vendored 清单版本（0.85.1）== 全局源包版本（0.85.1）；
- 随包 5 个「bundle 里扫不到、必须自带」的依赖与 pi 官方 shrinkwrap 版本**逐项相同**；
- 但 **没有任何机制阻止它们漂移**：vendor 快照是人工/脚本动作（`npm run upgrade:pi`），
  不参与 `npm ci`；换一台机器、全局 pi 是别的版本时，内置运行时**不会**自动变。

**对 04 的含义**：`capabilities` 若要「按候选固定依赖版本」，参照物就是这个
「vendored 快照 + pi shrinkwrap」模式；不要指望 pi 侧的 lockfile 帮我们钉住 MCP 相关包。
**MCP 官方 SDK 目前不在任何 lockfile 里**（§7.4），S3 必须显式新增依赖并写进 lockfile。

### 4.3 按需读正文：没有「读技能正文」RPC，有两条官方替代路径

**路径 ①（模型侧，官方设计）**：system prompt 只放 `name` + `description` + `location`，
正文由模型用 `read` 工具去读。系统提示原文（0.85.1 代码 `formatSkillsForPrompt`）：

```
The following skills provide specialized instructions for specific tasks.
Use the read tool to load a skill's file when the task matches its description.
When a skill file references a relative path, resolve it against the skill directory …
<available_skills>
  <skill><name>…</name><description>…</description><location>…SKILL.md</location></skill>
```

**路径 ②（宿主侧，确定性）**：把 `/skill:<name>` 当**普通 prompt 文本**发过去，
pi 会自己读文件、去 frontmatter、包成 `<skill name location>` 块（`_expandSkillCommand`）：

```
_expandSkillCommand(text){ … skill=…getSkills().skills.find(s=>s.name===skillName);
  let content=readFileSync(skill.filePath,'utf-8'), body=stripFrontmatter(content).trim(),
      skillBlock=`<skill name="…" location="…">\nReferences are relative to ${skill.baseDir}.\n\n${body}\n</skill>`;
  return args?`${skillBlock}\n\n${args}`:skillBlock … }
```

触发条件也已核对：`session.prompt(text, options)` 里
`let expandPromptTemplates = options?.expandPromptTemplates ?? true`，
而 RPC 的 `case"prompt"` 调 `session.prompt(command.message, { images, streamingBehavior, source:'rpc', … })`
**没有**关掉它 → RPC 来的 `/skill:x` 会被展开。`docs/rpc.md` 也明写
「Input expansion: Skill commands (`/skill:name`) and prompt templates are expanded before sending/queuing」。

### 4.4 判定与对 04 的含义

| 子项 | 结论 |
|---|---|
| 枚举已发现技能 | **可实现**（`get_commands`，含绝对路径与来源） |
| 按需读正文 | **有限实现**：无 `skill.read` RPC；但 ① 模型 `read` 路径 ② 宿主 `/skill:<name>` 展开路径都可用 |

[command-registry.ts](../../src/main/command-registry.ts) 第 102 行），发送走普通 prompt 文本 = 路径 ②。

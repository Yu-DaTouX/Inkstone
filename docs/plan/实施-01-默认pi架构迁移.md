## 0. 一句话结论

采用**未经修改的官方 pi 运行时**，继续走正式 RPC 管会话；新增能力由**砚主进程服务 + 随包 `yan` CLI** 提供。
模型用 pi 原生 `read` / `bash` 等基础工具读短说明、调命令、看结果。
不预装 pi 插件，不在首次启动暗中装回，不把同一插件改个名称为「原生」。

## 1. 目标与不可退化项

**目标结构**

```text
砚 Electron UI / 会话与目标调度器
       ├── 官方 RPC ── 默认 pi
       │                 └── read / bash / 其它原生基础工具
       │                               │
       └── 砚能力服务 ← 本机 IPC ← yan CLI
              ├── 搜索源与候选目录
              ├── Skill / 普通工具的接入管理
              ├── API / CLI 适配
              ├── 可选 MCP 客户端与服务器进程管理
              ├── 任务、项目知识、交互请求
              └── 产物 / 日志 / 结果文件
```

**不可退化（迁移期间任何一项丢失都算回归，必须逐项登记）**

| 现有能力 | 载体 | 迁移期的硬要求 |
|---|---|---|
| 任务清单写入（panel_todos） | `left-info-panel.ts` 扩展（用户本机） | 新安装环境在没有该扩展时仍能维护任务；旧历史可读 |
| 浏览器控制 | `resources/pi-extensions/browser.js` | 身份、页面范围、缩放、下载等边界不变；不更换原生 `WebContentsView` |
| 交互提问 | `question.js` | 等待 / 取消 / 回答必须对应**同一个请求**；不能从自然语言猜用户点了什么 |
| 回复详细度 | `response-detail.js` | 当轮 / 下轮生效要明确；不承诺改设置会刷新正在执行的 system prompt |
| 界面语言 | `language.js`（唯一真源） | 现生效链（`before_provider_request` 贴近用户消息 + 系统提示兜底）**不能直接删**，先验证替代 |
| 上下文管理 | `context.js` / `context-transform.js` / `context-deep.js` / `context-producer.js` / `context-safety.js` / `context-stage-runtime.js` | 见 §5；请求前硬预算**可能无法等价迁移**，必须实测后如实标注 |

> ✅ **边界已确认（2026-09-18 用户拍板）**：用户新增的边界是「完成版只包含默认 pi」；
> **允许保留一个砚自有薄适配层**，但它**不是插件生态** ——
> 唯一职责是承载「宿主无法通过 CLI / RPC 表达」的**生命周期桥接与策略执行**。
> **准入判据（2026-09-18 二轮外部咨询补全，见 [二轮记录 §2.3](决策记录-二轮外部咨询-2026-09-18.md)）**：
> 不要问「有没有对应的 CLI 命令」，要问**「官方路径是否保持必要的语义契约」**。逐条打勾，缺一即判「不等价」：
>
> | # | 契约 | 判否的例子 |
> |---|---|---|
> | ① | **调用时机等价** | 官方路径只能在回合结束后触发，而能力必须发生在请求发出前 |
> | ② | **输入 / 输出结构等价** | CLI 只回自然语言文本，拿不到原来那份结构化数据 |
> | ③ | **失败 / 取消语义等价** | CLI 失败后无法区分「没执行」与「执行了一半」 |
> | ④ | **延迟预算可接受** | 需要额外一次模型往返才等价，用户可感知变慢 |
> | ⑤ | **宿主可观测并正确渲染** | 拿不到工具名 / 入参 / 结果指纹，业务卡片只能靠猜 |
>
> **判定出口只有三个，不要造第四个**（适用于本节表格里那 6 项）：
>
> 1. 五条全过 → 落**宿主服务 / 随包 `yan` 子命令**，**不得**留在扩展里；
> 2. 有契约不满足，且**补齐不需要注册模型工具** → 允许进**薄层**，登记进白名单；
> 3. 有契约不满足，且**补齐必须注册模型工具** → 结论是**「当前架构做不到」**，
>    如实登记为未满足，**不得**拿它当进薄层的理由。
>
> 判定集中在本文件 S1 与 [实施-06](实施-06-上下文管理收尾.md)。
>
> **为什么只允许「薄」**（2026-09-18 外部咨询，见 [决策记录 §2.1](决策记录-三方意见对照-2026-09-18.md)）：
> 真正的风险不是技术，而是**边界腐化 —— 薄层会重新长成现在这 10 个扩展**。
> 因此下面两组约束**缺一不可**（不再是「若确认保留」的条件句）：
>
> **一次性边界（写进代码与诊断）**
> - 不调 `registerTool`、不注册 pi 命令、不 import pi 内部模块；
> - 不增加用户可见功能、不改变 pi 默认工具集；
> - 诊断里标为「应用能力」，**不冒充内置插件**；
> - 只承载**准入判据第 2 条通过**的能力（生命周期桥接与策略执行），**不承载业务逻辑**。
>
> **持续约束（防止长回去）**
> - 维护一份**允许的钩子白名单**：新增钩子必须走一次显式评审并更新清单；
> - 规定**依赖方向**（薄层只能依赖宿主服务，不能让业务模块反向依赖它）；
> - 加一条**架构检查**（脚本级断言：薄层目录里出现业务逻辑、或出现白名单外钩子即失败），
>   与现有 `typecheck` / `lint:css` 一起进门槛。
>
> 上述约束**即刻生效**：本文提到的每个能力先按「宿主服务 / `yan` 子命令 → 薄层」顺序找落点，
> 只有确实无等价物的才进薄层，并登记进白名单。S1 第 7 项的判定结果要回写到
> [06 §3](实施-06-上下文管理收尾.md) 的分支表与 HANDOFF 的「剩余限制」。
>
> **✅ 允许钩子白名单（2026-09-19 定，来自 [06 §3](实施-06-上下文管理收尾.md) 的逐能力判定）**：
> `context`、`before_provider_request`、`before_agent_start`、`session_before_compact`、`agent_settled`。
> 实测存在但**不入白名单**的：`resources_discover` / `input` / `before_provider_headers` / `message_end`
> —— 当前没有任何能力需要它们，新增一个需要走一次评审。
> ⚠️ 白名单只管**钩子**：薄层里**不得注册模型工具**。当前唯一违反这一条的是 `context_recall`
> （去留见 06 §3 的出口 ③）；`browser.js` 的 16 个模型工具已经改成 ①（`yan browser` CLI，
> **2026-09-19 落地**，见 §4 判定表与 [证据-01-S4b](证据-01-S4b-browser-CLI迁移.md)）。

## 3. 边界（明确不做）

- **不改** `resources/pi-runtime/` 生成物；不 patch pi；不用非官方开关「碰运气」。
- **关加载只用官方两个开关，而且两个都要**：`--no-extensions`（扩展）+ `--no-skills`（技能）——
  实测只给前者时**技能仍会加载**（见 [证据-01-S1 §9](证据-01-S1-可行性验证.md)）。
  另：pi **自带一个 inline 扩展 `llama`**，不受 `--no-extensions` 影响，属于默认 pi 自身。
- **不删**用户已安装的扩展，也不改用户独立 pi 终端的配置（`~/.pi/agent/...` 保持用户自己的样子）。
- **不**把「能力」重新包装成「只是换个名字加载到 pi 的扩展」。
- **不**声称 CLI 服务校验等于整个 agent 沙箱（见 §6.2）。
- 打包从**干净资源清单**构建，不复制开发者自己的 `pi-agent` / 插件缓存 / 凭证。

## 4. 会话切片

每片都是「一次会话能做完 + 能独立交证据 + 能安全停下」。

### S1 · P0 可行性验证（规模约 1 天，**02–06 的共同前提**）

**做什么**：在隔离 `piDir` 里用官方 pi、**不带任何 `--extension`**，逐项实测：

1. 实际**加载清单**（扩展 / 包 / 技能分别是什么来源，能否完整打印）。
2. 原生基础工具集（`read` / `bash` / 其它）在 RPC 模式下是否都可用。
3. 从模型侧调用本机 CLI（`yan`）的完整往返：能否启动、能否拿到结构化结果、大结果落文件是否可行。
4. **提示入口**：短「砚能力入口说明」能通过哪种**已验证支持的官方提示配置**送达
   （项目级上下文文件 / 会话专用提示文件 / 官方参数），且**必须显示在砚的提示来源诊断里**，不伪造用户发过的话。
5. 模式切换与上下文边界：同会话内能否安全改有效工具集；`context` 级请求前拦截是否还有等价入口。
6. 工具只读白名单（供 05 的澄清模式用）：`--tools` 允许集能否覆盖 `read`/`grep`/`find`/`ls` 等只读集。
7. **钩子分类草案**：把 §1 的不可退化项逐条归为「必须扩展钩子 / 有 CLI 等价物 / 无任何等价物」——
   这份分类既喂给 S4，也**直接充当薄层的允许钩子白名单**，
   并作为 §1 那条架构检查的断言依据。

**必测项 · 端到端最小闭环**（与上面 7 项并列，**不能只交单点证据**）

用一个最小场景把链路串起来：**模型 → 调本机 CLI（`yan`）→ 拿到结构化结果 → 回到模型 → 基于结果继续下一轮**。

- 单点验证只能证明「组件各自存在」，证明不了协议、权限、进程边界、工具结果回填、
  后续推理能否串起来（二轮咨询 §2.5）。
- 闭环要**极小**：一个命令、一个结果文件、一轮后续推理即止；
  **不要**做成半实现 —— 那会掩盖验证目标，也违反本片「不做产品改动」的约束。
- 闭环不通过，S1 的出口**不算完成**：02–06 全都建立在「串得起来」这个前提上。

**出口**：一张表，每项标注 **可实现 / 有限实现 / 缺官方接口**，并附可复现的命令与实际输出
（最小闭环另附一段完整会话记录）。
**这一片不做任何产品改动**，只产出证据。**遇到“缺官方接口”不要绕过、不要 patch**，原样记录。

> **实测进度（2026-09-18）**：主要项已跑通，结果见 [证据-01-S1](证据-01-S1-可行性验证.md)。
> 其中三条**推翻了原假设**：① `--tools` 是硬门禁（工具表直接移除）；
> ② `setActiveTools` 运行时可用，**不必重建实例**；③ `context` / `before_provider_request` 每轮都触发。
> 另发现：`--no-extensions` **只关扩展、不关技能**，且 pi 自带一个 inline 扩展 `llama`
> —— 严格的「零扩展」做不到，§1 与 §3 的措辞要据此修正。

**必须在 S1 一并回答的三个硬问题**（对应归档 §8，CLI 掩盖不了）：

| 问题 | 若答案为否，则 |
|---|---|
| 有没有**请求前**上下文控制（等价 `context` / `before_provider_request` 钩子）的官方入口？ | 退化为**宿主回合边界预算守卫**（**不是**请求前硬拦截），如实标为软预算；严格硬门登记为**未满足**。其余能力按 [06 §3 分支 B 的止损表](实施-06-上下文管理收尾.md)逐项判定 |

| `yan` CLI 的会话身份能否由宿主可靠传递（runId / generation / project / operationId）？ | 不让模型自报 `projectId`，改为宿主绑定；无法绑定的动作不开放进 CLI |

### S2 · P1 能力基础：宿主服务 + `yan` CLI 骨架（规模 1–2 天）

**做什么**

- 新增砚宿主能力服务（主进程侧）：会话 / 项目身份、操作 ID、结果文件、日志、受限 IPC 端点。
- 新增随包分发的 **`yan` CLI 可执行入口**：不调 `registerTool`、不注册 pi 命令、不 import pi 内部模块。
- 向 pi 子进程注入**会话专用 PATH 或明确绝对入口**，不改用户系统 PATH。
- Windows 下用**实际打包的可执行文件 / 启动器**，不假设用户有 `node`、`bash` 或 `.js` 文件关联。
- 参数文件统一 UTF-8 JSON（避免 shell 转义、命令注入、模型拼接凭证）；stdin / 输出文件可选，用法一致。

**拟议命令（拟建接口，不是当前命令）**

```text
yan capabilities search --query-file query.json --scope available
yan capabilities discover --query-file query.json
yan capabilities prepare --candidate ID
yan capabilities acquire --plan ID
yan operations status --id ID
yan skill read --id ID
yan mcp describe --server ID --tool NAME
yan mcp call --request-file request.json --output result.json
yan tasks apply --request-file task-update.json
yan knowledge search --query-file query.json
```

**出口**：CLI 骨架可运行、身份校验生效（伪造 `projectId` 被拒）、大结果落文件 + stdout 只回受限摘要
（类型 / 路径 / 大小或条数 / 错误 / 操作 ID）。**出口标准是「身份与结果管道能跑」，不是「功能已实现」。**

### S3 · 提示与上下文组织（规模 0.5–1 天）

- 给模型一段**短的**砚能力入口说明：何时读帮助、怎样查可用能力、能力不足时怎样联网发现、
  文件结果怎么读；完整命令用法**按需读**（`yan --help` 或 Skill 正文）。
- 模型只看到 pi 基础工具 schema，**不增加一大组自定义工具定义**。
- 入口说明必须走 S1 验证过的官方提示配置，并出现在提示来源诊断里。
- 大结果由砚服务 / 脚本落文件：stdout 返回受限摘要；模型用文件工具筛必要片段。
  JSON / 二进制 / 图片分别处理；**路径不是渲染成功证据**；图片需单独验证 pi 原生读取 + 砚附件显示链。
- 能力使用优先顺序写进入口说明：**已有本地工具 / 脚本 → 合适的 Skill 流程 → 发布方 CLI / API → 确实需要的 MCP**。
  用户明确指定 MCP 或某能力时优先满足，不以此排序否定要求。

**出口**：真实请求 token 的**实测值**（本地中间结果确实减少上下文传输），
并记录一条反例：CLI 反复打印巨量输出仍会撑爆上下文，**不能把 CLI 等同于天然省 token**。

## 6. 不可用 CLI 掩盖的约束

### 6.1 请求前上下文控制

本篇核实的 RPC 文档只提供 `compact` 与状态事件，**未找到**与 `context` / `before_provider_request`
等价的通用请求重写入口。

**边界已定（2026-09-18 拍板：允许薄适配层）**，所以「请求前硬预算」**不必直接放弃** ——
它属于「无 CLI 等价物」的候选，可以留在薄层里实现。但仍有两点约束：

- P0（S1）必须用未修改的 pi 验证安全暂停 / 截断边界，并核实这批钩子在**当前版本**里存在且载荷够用；
- 若实测证实钩子**缺失或载荷不足**：保留原生自动压缩 + 宿主**安全回合边界**压缩，
  严格「请求前硬门」作为**未满足项**登记，不得偷偷 patch pi、不得把进程中止当成安全暂停，
  也不得把原生自动压缩写成等价替代（与 [06 §3](实施-06-上下文管理收尾.md) 分支 B 一致）。

### 6.2 模式只读与 CLI 权限

`yan` 服务只允许当前身份和模式对应的动作，**但允许 pi 的原生 `bash` 就仍可绕开 `yan` 执行其它命令**。
**CLI 服务校验 ≠ 整个 agent 沙箱。**

澄清阶段若要**硬只读**：通过官方 tools allowlist（启动参数 `--tools read,grep,find,ls`，或运行时 `setActiveTools`）
把 `bash` / `write` / `edit` 从工具表移除，只用已核实的原生只读工具；联网检索由宿主完成，
再以可追溯材料交给模型。

**2026-09-18 实测**（见 [证据-01-S1 §3/§4](证据-01-S1-可行性验证.md)）：
`--tools read,ls` 之后 `getAllTools()` 只剩 `read,ls` —— 是**真移除**，不是「禁用调用」；
`pi.setActiveTools([...])` 在 `before_agent_start` 里调用后**后续每一轮都生效**。
→ 转执行**不需要重建实例**；重建降级为可选手段（留给「要改 systemPrompt 前缀」这类场景）。
⚠️ 另注意：`grep` / `find` / `ls` **默认不在激活集里**，只读白名单必须**显式列全**。
**不可**写「有 CLI 所以澄清全工具硬门禁已实现」。

### 6.3 会话身份与本机服务

CLI 会话身份由宿主传递，校验 `runId` / `generation` / 项目 / 操作 ID；
**不能**由模型随意传一个 `projectId` 就跨项目操作。权限针对宿主操作，
**不声称**能防同一用户下的恶意本地进程。认证不进入模型输出，不复用跨项目服务器凭证。

## 8. 能力获取与安装的分流规则（04 直接复用）

下载来源确定后按**资源类型**分流，**不按「能不能装进 pi」决定**：

| 类型 | 落到哪 | 要求 |
|---|---|---|
| Skill | 砚受管目录（项目隔离），按需读取 | 下载并验证 `SKILL.md`、必要脚本与资源，**固定版本**；**不自动启用同包内的 pi extensions** |
| 普通 CLI / API 客户端 | 项目受管目录 | 检查平台 / 依赖；按受信来源策略执行 |
| MCP server | 由砚连接或启动 | 不要求安装 `pi-mcp-adapter`；按需返回单个工具 schema，调用结果先落文件 |
| 仅作为 pi 扩展工作的包 | **标记不适用于默认 pi 路线** | 可另找独立 CLI / API 实现；**不能以完成任务为由偷偷装入 pi** |

其它硬规则：

- 同时含 Skill 和扩展的包：只有当 Skill **不依赖**该扩展注册的工具 / 提问 UI / 生命周期钩子时才可单独取用。
- 必须保留许可与来源；**不能**只改清单剥掉扩展就声称兼容。
- 搜索、自动接入、真实业务使用是**三个阶段**。缺认证就保存 `needs-auth`；
  已授权范围内自动接入后继续任务，不让用户重复目标。
- **首次启动的包目录应为空**，不联网下载一套固定的「必备插件」。

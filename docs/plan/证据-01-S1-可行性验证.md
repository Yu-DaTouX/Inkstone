## 0. 三个改变方案的结论（先看这里）

| # | 结论 | 影响 |
|---|---|---|
| **①** | **`--tools` allowlist 真的把工具集限制住**：`--tools read,ls` → 实际可用工具只剩 `read` / `ls`（连扩展注册的 `panel_todos` 也被排除） | 05 的「澄清模式硬只读」**有官方支持**，不必退化成提示词约束 |
| **②** | **`pi.setActiveTools([...])` 运行时生效，且持续到后续请求** | 05 原假设「运行时不能改工具集 → 需安全重建同会话实例」**不成立**：可以直接切，**不用重建** |
| **③** | **`get_commands` 返回完整加载清单**（含 `sourceInfo` 的 path / source / scope / origin / baseDir） | S1 第 1 项不需要自己造探针；诊断页可以直接消费它 |

## 1. 加载清单（S1 第 1 项）

`get_commands` 是**官方 RPC 方法**，返回的每一项都带来源：

```json
{"name":"panel","source":"extension",
 "sourceInfo":{"path":"C:\\Users\\YuDaTou\\.pi\\agent\\extensions\\left-info-panel.ts",
               "source":"auto","scope":"user","origin":"top-level"}}
{"name":"footer","source":"extension","sourceInfo":{"source":"npm:pi-zh-cn","origin":"package"}}
{"name":"skill:radare2","source":"skill","sourceInfo":{"source":"npm:pi-reverse-basics","origin":"package"}}
```

**判定：✅ 可行**。扩展 / 技能 / 提示模板都能列出真实路径与来源类型，
足以支撑「受信内置清单 + 实际加载路径」的产品要求（[实施-02](实施-02-任务工具内置化-已完成.md) §3）。

## 2. 原生工具集（S1 第 2 项）

在扩展里调 `pi.getAllTools()` / `pi.getActiveTools()`（这是**唯一**能观测工具集的入口，RPC 没有对应方法）：

| 场景 | `getAllTools()` | `getActiveTools()` |
|---|---|---|
| 不带 `--tools` | `read, bash, powershell, edit, write, grep, find, ls, panel_todos` | `read, bash, edit, write, panel_todos` |
| `--tools read,ls` | `read, ls` | `read, ls` |

**两个要点**：

1. 原生基础工具齐全：`read` / `bash` / `edit` / `write` / `grep` / `find` / `ls` / `powershell`。
2. **默认激活集 ≠ 全部**：`grep` / `find` / `ls` 默认**没启用**，要用 `--tools` 或 `setActiveTools` 显式打开。
   → 05 的澄清模式/只读场景**必须显式列白名单**，不能假设「只读工具默认都在」。

## 3. 工具 allowlist = 硬门禁（S1 第 6 项）

同上一张表第二行：`--tools read,ls` 之后 `getAllTools()` 也只剩 `read, ls` ——
说明它**不是**「禁用调用」而是**从工具表里移除**，连能被模型看到的定义都没有。

**判定：✅ 官方支持真只读**。05 可以按「工具集真实受限」写验收标准（三方结论 §2.3 的口径成立）。

## 4. 运行时切换工具集（S1 第 5 项）

最小扩展：

```js
export default function (pi) {
  pi.on('before_agent_start', () => {
    log(pi.getActiveTools())        // ['read','bash','ls']
    pi.setActiveTools(['read'])
    log(pi.getActiveTools())        // ['read']  ← 立即生效
  })
  pi.on('before_provider_request', () => log(pi.getActiveTools()))
}
```

实测轨迹（`--tools read,bash,ls` 起手）：

```
{"hook":"setActiveTools@start","before":["read","bash","ls"],"after":["read"],"err":null}
{"hook":"activeTools@request","tools":["read"]}   ← 后续每一轮都是 ["read"]
{"hook":"activeTools@request","tools":["read"]}
```

**判定：✅ 运行时切换可行且稳定**。→ [实施-05](实施-05-工作模式与长任务续接.md) 的
「安全重建同会话实例」**从必需降级为可选**（只在需要重建 `systemPrompt` 前缀缓存等场景才用）。

## 5. 提示入口（S1 第 4 项）

- **没有扩展时，零注入点**：所有可改写提示的钩子都必须由扩展注册。
- 有扩展时实测可用：
  - `before_agent_start` 的载荷是 `{type, prompt, images, systemPrompt, systemPromptOptions}` → **可改 `systemPrompt`**；
  - `before_provider_request` 的载荷是 `{type, payload}` → **可改请求体（含 messages）**。
- 砚现有的 `language.js`（双钩子：payload 插入 + systemPrompt 追加）在这条链上**实测被完整调用**。
- `--append-system-prompt` 仍在 CLI 里存在，但架构修订已明确否决（会迫使重建实例）。

**判定：✅ 用钩子注入提示可行**，且**必须靠薄层**（这是「无 CLI 等价物」的典型一类）。

## 9. 零扩展下的真实清单（`--no-extensions` 复测）

| 启动开关 | `get_commands` 返回 |
|---|---|
| 无（真实 agentDir） | 13 项：`panel` + `footer`（扩展）、10 个 `skill:*`、`llama` |
| `--no-extensions` | **11 项**：扩展自动发现关闭，但 **10 个技能仍在** |
| `--no-extensions --no-skills` | **1 项**：只剩 `llama` |

**两个结论**：

1. **`--no-extensions` 只关扩展，不关技能** —— 技能要 `--no-skills` 单独关，
   两个开关不能互相替代（[实施-01](实施-01-默认pi架构迁移.md) 的启动参数清单要写清）。
2. **pi 自带一个 inline 扩展 `llama`**（`source:"inline"`、`scope:"temporary"`、
   `<inline:llama.cpp>`），**不受 `--no-extensions` 影响**。
   → 严格的「零扩展」做不到：**默认 pi 至少带这一个内置扩展**。
   它不属于第三方插件，就是默认 pi 自己 —— 01 的边界描述要据此修正，
   不能再写「不注册任何 pi 扩展」。

## 10. 端到端最小闭环（S1 必测项）✅

**命令**（免费模型，零成本）：

```
node resources/pi-runtime/dist/bundle/cli.js --print --no-session \
  --model commandcode/inclusionai/ling-3.0-flash-sante:free \
  --extension ./s1-loop.tmp.js --tools bash \
  '请用 bash 工具执行这条命令：node -e "process.stdout.write(JSON.stringify({ok:true,n:42}))" 然后只回答 ok 和 n 的值。'
```

**轨迹**（观测扩展记录）：

```
{"hook":"start","tools":["bash"]}                        ← --tools 生效
{"hook":"tool_call","name":"bash",
 "input":{"command":"node -e \"process.stdout.write(JSON.stringify({ok:true,n:42}))\""}}
{"hook":"tool_result","name":"bash","isError":false,
 "keys":["type","toolName","toolCallId","input","content","details","isError","usage"]}
```

**模型最终回答**：`ok 的值是 true，n 的值是 42`。

**判定：✅ 闭环成立** —— 模型 → 结构化工具调用 → 本机命令执行 → 结构化结果回填 →
模型基于结果继续推理并正确作答。四个环节都真实跑通，不是单点模拟。

**顺带确认了工具事件的载荷形状**（S2 起要用）：

- `tool_call` = `{type, toolName, toolCallId, input}`
- `tool_result` = `{type, toolName, toolCallId, input, content, details, isError, usage}`

## 1. 用户要求与交付行为

用户现场反馈：两次完整压缩之后，交接过程缺乏提示，且偶尔报错。用户要求底层新会话交接在后台进行，前端始终是同一条会话；自主模式的推理窗口随聊天中的正式回复位置移动。用户已明确最后一项指**聊天正式回复**，不是右侧输出文件或预览窗口。

### 1.1 同一条用户会话，后台更换上下文片段

- 继续沿用多份底层 JSONL 和旁挂会话链；不强行把多个 pi 会话写进同一 JSONL，不回灌全量历史给模型。
- 交接不新增用户可见的会话条目，不切走当前聊天，不抢用户正在看的另一条会话，不重新命名或重排成一条“新会话”。
- 标题、用户目标与验收标准、工作模式、输入草稿、排队消息、滚动位置、未读状态、右侧资源和当前逻辑回合保持连续。
- 不在聊天里插入伪造的用户消息、交接包长正文或要求用户“打开新会话继续”的提示。底层片段身份只在诊断详情中出现。
- “无感”指**不暴露会话迁移操作**，不等于隐藏错误或让用户无法判断是否仍在工作。采用非阻塞状态：`正在整理上下文，任务继续中` → `已继续`；正常完成状态短暂呈现后收起，历史诊断可追溯。
- 失败显示准确状态，如 `整理未完成，已保留当前进度`；只有确实还能在源片段运行时才说“继续执行”。需用户处理时提供明确原因与重试／停止入口，不循环弹技术错误。

### 1.2 两次压缩的准确口径

当前计数只包括本片段成功的**自动完整压缩**（宿主 policy 或 pi 原生 threshold/overflow）；手动压缩、失败、取消、tool sweep、状态摘要不混入。用户所见“两次完整压缩”是否均属这一类，尚无现场日志核实，不能预先认定。

本档案默认修复口径：第二次符合条件的压缩完成后登记“待交接”，在下一个安全边界自动交接；仍有工具／子代理／用户队列时等待并显示原因，不为凑安全边界中断工作。对于需要 pi 自身结束回合才能安全换片段的情况，明确等待，不声称可在任意工具中途切换。

当前源码注释同时存在“累计两次后，下一次压缩需求才交接”的旧口径，而调度实现检查 `count >= 2` 后可在空闲状态直接交接。实施时统一实现、文案和测试为以上行为；不顺带改动压缩容量、600K/700K 档或 C-6 参数。

### 1.3 推理跟随当前回复的位置

- 同一逻辑回合可以有多次“推理 → 工具 → 正式文字 → 自动继续”；后一次推理显示在**上一段已输出正文之后、接下来的正文之前**，不继续写回整轮靠前的旧推理块。
- 已输出正文保持原顺序和位置；新工具出现不能把旧正文重新归类、搬到上面。
- 每个工作段绑定真实消息／run 身份；当前段推理随当前位置推进，历史段保留可展开入口，不复制整轮推理。
- 保留一个逻辑回合外壳和整轮用量／计时，不为每次 API 往返重复头像、整轮页脚或用户气泡。
- 保留默认限高、尾部最新内容、顶部渐隐，以及显式“展开全部／收起”；默认态不新增内部滚动条。主动展开仍遵循既定固定范围。
- 用户在底部时跟随新增内容；用户上滚阅读时不抢滚动，提供回到最新位置入口。展开状态、键盘焦点及选中文本不因新一段内容到达而被重置。
- 无推理输出时不造推理块；标准模式保持当前产品行为，共享数据结构变化必须覆盖其回归。持续目标处于标准档时是否采用新排布，作为显式策略，不凭数据聚合偶然决定。

## 4. 新增交接与推理审查

### H1 / P1：交接与正常续跑缺少同一调度所有者（E2）

`index.ts:pushFrom` 在同一空闲 state 分别 `void maybeArmHandoff()` 与 `void maybeArmGoalContinue()`；生成交接包后又异步 commit。交接资格只在开始读取状态时检查，生成期间目标、用户输入、工具状态可能变化；提交前没有对应的源水位／目标 revision／暂停代次复核。

后果风险：源已继续推进，但仍用旧包停源换段；停止、新消息或目标完成后，旧结果继续提交。不能用加长 sleep 解决。需要单一调度决定下一步是普通续跑、错误重试、能力续接还是交接。

### H2 / P1：超时与收集按 runner 匹配，缺操作级隔离（E2）

`maybeArmHandoff` 的 90 秒 timeout 只捕获 runner id；`abandonHandoff` 查当时的 `handoffPending.get(id)`。旧操作提前完成后，旧 timeout 未被保存并撤销，可能影响同 runner 后续操作。`collectHandoffResult` 还有 interval 与 timeout 的并发调用入口，await 之后没有统一的操作所有权复核。

修复须让 timer、poll、结果收集、取消与事务提交绑定同一 operationId/epoch；清理旧操作只能清旧请求，旧回调不能终止新操作。

### H3 / P1：用户会话与物理会话尚未完全解耦（E2）

已有 `SessionChain.chainId`、侧栏代表段、`readChainMessages`；应复用，不另造第二套历史系统。但 `openHandoffSession` 调用 `runners.select`、remember、pushRunners、pushRunnerSnapshot，仍走普通选择会话流程。链要等目的文件建好后才 link，存在目的片段先暴露的阶段；后台源会话交接也可能影响当前选择。

目标状态不继承，当前要求模型在目的段重新 report；`inheritWorkMode` 发生在 commit（包含发送 resume）完成之后，而且向当前 active runner 写模式快照。由此存在首轮按默认模式启动、推到错误活动实例，以及用户明确的 pursue/brief 丢失风险。模型重建目标不能替代宿主保留用户意图。

### H4 / P1：交接控制消息冒充用户消息，消费证据过弱（E2）

HandoffRunner.deps.send 接 `agent.send(text)`；`buildResumeText` 携带长交接包，`hasResumeEvidence` 要求 user，`containsResumeEvidence` 则只查全文是否含 marker。它只能证明标记曾落盘，不能证明目的运行已开始或已接管任务。交接实现应复用已经能 `custom + triggerTurn` 的薄层能力，验证实际 pi 版本，不沿用“custom 不触发回合”的旧注释作为结论。

新写入控制消息必须带可信宿主元数据，默认不呈现为聊天正文；区分 dispatched / persisted / started。历史 user marker 只读识别，不重写旧 JSONL、不保留第二条写入入口；不能凭正文匹配隐藏用户自己粘贴的相似文本。

### H5 / P2：有 toast，但没有持久的交接可见状态（E2 + U）

源码并非完全没提示：请求生成、失败、成功均有 notify。然而主 UI 未检索到 `getHandoff()` 消费入口；资格拒绝通常直接 return，外层 catch 部分静默吞错；执行器通知按“当前活动 runner”路由，不保证归属原逻辑会话。

`yan:getHandoff` 为历史展示回到链首取 tally/package，但触发判定读当前片段计数。新面板必须区分“当前片段已压几次”与“整条会话历史交接次数”，避免拿首段旧计数表示当前进度。

这能解释为何现有提示机制不足，但**尚未证明用户那次没有看到提示的具体原因**。需要真实操作日志与 UI 事件关联证据。

### R1 / P1：整轮聚合丢失推理与正文的相对顺序（E2 + D）

`shared/turns.ts:groupIntoTurns` 把 thinking 拼成一个字符串，把文本按是否带工具分为 commentary/response，再合并正文；`TurnView` 固定渲染 commentary → TurnActivity（整轮推理和工具）→ response。自主续跑有多次正式输出时，后续推理仍追加到同一旧位置；“有没有工具”也不等于消息真实发生的先后次序。

这是数据模型和渲染结构共同的问题，仅改 CSS 的 sticky/order 或强制 scrollIntoView 不能恢复丢掉的顺序。应保留按来源消息排序的工作段，活动推理只归属当前段。

## 5. 实施设计与不变式

### 5.1 一条用户会话的稳定身份

优先以现有 chainId 为长期用户会话身份，未成链的会话按首段稳定文件键映射；不要以 active runner 或最新物理文件当全部 UI 状态的唯一主键。至少分清：

| 身份／状态 | 职责 |
|---|---|
| conversationId（映射现有 chainId） | 侧栏、标题、草稿、目标、工作区、滚动锚点的稳定身份 |
| segmentId / sessionFile | pi 当前上下文片段、当前片段压缩计数 |
| runId / runtime epoch | 进程生命周期、拒绝迟到事件 |
| logicalTurnId | 原用户回合，跨自主续跑与片段延续计时、用量 |
| goalId + goalRevision | 用户目标及可追溯进展，不由摘要随意替换 |
| operationId + controlEpoch | 某次续跑／交接的所有权，取消和消费幂等 |

持久化迁移须幂等，可读取旧数据；目标用户原话、验收标准和 pause/pursue 是宿主事实，跨片段保留。模型生成的 done/remaining 属摘要输入，不提升为新验证事实；既有证据保留来源片段和时间。两者不可混为“复制旧摘要就是完成”。

### 5.2 调度、停止与切换

对同一逻辑会话串行决定执行动作。优先级：用户停止／取消 > 用户待发输入 > 已成立的交接事务 > 普通目标续跑／模型错误重试。能力激活续接也必须经过同一所有权检查，不能抢写同一快照文件。

交接建议阶段：待安全边界 → 准备交接包 → 验证源水位 → 准备目的片段 → 提交映射 → 启动确认 → 完成；错误进入可恢复状态。复用现有 transaction store，按需要补生成期与运行确认元数据，不并建另一套事务。

关键顺序：先登记操作所有权并冻结源续跑 → 等真实安全边界 → 生成/校验包 → 复核水位与用户意图 → 释放源执行租约 → 后台建立目的片段 → 安装继承状态与模式 → 提交链映射 → 发内部续接 → 确認新 run 开始。源历史在整个过程保持可读；保持同 cwd 单执行者，不绕开租约。

新用户消息到达时：提交前使旧包失效，在源处理或按队列重新生成；提交后的消息按稳定会话身份排到目的段，恰好发送一次。停止在任何阶段都使旧操作代次失效，迟到结果只记诊断，不能恢复执行。

失败边界：提交前可回源；提交后先判断目的是否已启动，不能盲目回源重做，也不能同时运行两边。启动证据不明确时显式保留“待确认”，核对证据后恢复；不能拿超时等同于从未执行。

### 5.3 后台切片与原地展示

给 runner 编排增加不改变前端选中会话的内部打开/绑定能力；正常用户切换仍走原 select。更新运行绑定时发送带稳定会话身份、版本号的快照，前端原地替换 runtime 绑定，不清空旧消息/草稿/资源，不触发新会话欢迎页。

JSONL 历史仍逐段读，消息身份至少含来源片段，防不同文件 id 冲突。artifact、工具关联、fork entryId、计时与 usage 均保留来源；不从 DOM 或拼接后的消息 id 猜分支位置。内部续接不新增用户逻辑回合，控制文本不进入正式回复聚合。

### 5.4 推理／正文顺序模型

增加有序工作段（如 `segments` 或等价结构），保留 sourceMessageId、runId、正文、推理、工具与 artifact 的归属；具体类型名实施时确定。不得继续用“整轮 thinking 字符串 + 整轮 response 字符串”作为唯一展示输入。

展示示例：

```text
用户请求
  第 1 段推理与工具
  正式回复 A（已输出，保持原位）
  第 2 段当前推理与工具 ← 自动继续时活动位置在这里
  正式回复 B
  第 3 段当前推理……
  整轮页脚（按实际证据汇总）
```

流式事件有实际 block 顺序时保留；旧 JSONL 只有分离 text/thinking 时按原消息顺序降级，不伪造字级先后。不要求模型暴露未提供的推理。DOM key 使用稳定段身份，避免将历史推理重新打字、丢展开状态。视觉令牌如需变动先改 DESIGN.md，再同步 CSS。

## 7. 验收矩阵

### 7.1 确定性自动检查（必须先使缺陷用例失败，再实现修复）

| 场景 | 必须断言 |
|---|---|
| 已排 continue 后 completed/blocked/取消/替换目标 | 旧 operation 永不发送；存储、快照、运行资格一致。 |
| 报告 8 次但未启动下一轮 | 不耗尽 8 轮额度；只保留同一待发操作；到限有可见原因。 |
| 旧 consumed 文件存在，新指令延后到达 | 能消费新指令一次；无新指令最终可观测退出。 |
| 两次历史重复拦截后创建新目标 | 新目标不受旧 blocks 污染；同一拦截不重复计入。 |
| 第二次自动压缩完成，重复 state 重放 | 当前片段计数准确，仅一条待交接操作；手动/失败/sweep 不计。 |
| 正常续跑与交接同一 tick；工具/子代理未结束 | 只允许一个调度动作，等待真实安全点，不停掉未完任务。 |
| 生成/打开目的/提交/启动确认各阶段插话、停止、切档 | 用户意图优先；消息不丢不重发，旧包不提交，不重启已停任务。 |
| 旧 timeout 到达新操作；interval 与超时同时收结果 | 新操作不被清理；一次结果只提交一次。 |
| 包错误、无权限落盘、目的创建失败、模型/凭证不可用 | 原进度保留，错误按阶段分类，可恢复；不虚报已继续。 |
| 提交前后崩溃；控制消息已落盘但尚未启动 | 恢复不重建多份目的、不双跑；persisted 不冒充 started。 |
| 目标 A 设置中切到 B；后台 A 交接时用户看 B | B 的目标、草稿、选中状态和通知归属不被污染。 |
| A→B→C 三片段及重启、历史片段缺失 | 用户只有一条会话；计数按当前片段，缺失段明确报告；用量/计时不过算或丢段。 |
| 推理1→正文A→推理2→工具→正文B | DOM 顺序符合事件段；正文A不搬动；控制消息不把一轮切成伪用户回合。 |

优先扩展现有 `test-goal`、`test-goal-resume`、`test-repeat-guard`、`test-handoff-*`、`test-session-chain`、`test-turns`、`test-turn-timing-store`；宿主+薄层跨层用例不能仅检查单个 store。不要以源码字符串包含代替时序验证。

## 9. 复审修复 · 2026-09-23（节约额度）

用户授权修复复审发现的问题，并要求节约额度。五项均已修改：

1. **暂停后仍交接**：资格/复核/发送前检查暂停；停止取消在途操作和目的续接；未提交的目的实例清理后回源。
2. **结果重复消费**：收集前认领、读后核对操作所有权，提交结束才释放 pending；超时遇到收集中操作延后复核。
3. **推理定位过晚**：从首段开始使用稳定的分段 DOM；第二段仅有推理时已经位于上一段正式回复之后，正文到达不重挂推理节点。
4. **交接切换界面**：隐藏目的实例在写链提交之后发布；发布当时重新判断用户是否仍在源会话，发送原位接续事件，传递稳定 conversationId/conversationFile，保留历史/草稿/右栏身份。交接期间的用户发送等待提交结果后绑定确定的运行实例；用户切换到其他会话不会改变该发送目标。
5. **生成失败后停住**：模型错误、解析失败、必填字段缺失、落盘失败均释放占用，并交回正常续行调度。

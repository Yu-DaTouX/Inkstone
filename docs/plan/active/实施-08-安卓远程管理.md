## 0. 一句话结论

**电脑端协议已落地并实测；Android 客户端尚未开始。**
pi、桌面工具、会话文件与凭证**继续留在电脑上**；Android 不直接读电脑文件，也不运行 Electron 或 pi。

```text
Android
  │ HTTP + SSE（第一阶段）
  ▼
Electron 主进程 Remote API
  │
  ├─ RunnerRegistry / AgentController
  ├─ pi RPC
  └─ 会话 JSONL
```

## 1. 已完成（当前第一阶段）

- 远程 API 放在**主进程**，不放 renderer，也**不使用** `remote-debugging-port`。
- **默认关闭**；显式设置 `YAN_REMOTE_ENABLE=1` 或 `YAN_REMOTE_PORT` 后才监听。
- 路由：`/remote/v1/health`（免 token）、`/info`、`/status`、`/sessions`、`/sessions/:id?limit=200`、
  `/events`（SSE）、`POST /sessions/new`、`/sessions/:id/select`、`/sessions/:id/messages`、
  `/sessions/:id/rename`、`POST /runs/abort`。
- 鉴权：`Authorization: Bearer <YAN_REMOTE_TOKEN>`（除 health 外）。
- 已有证据：`typecheck` / `build` / `test:unit`（远程协议 14 条）/ `audit:refs` 通过；
  隔离 Electron 实例实测 `/health`、带 token 的 `/status` / `/sessions`。
- 实现位置：[remote-server.ts](../../src/main/remote-server.ts)、[index.ts](../../src/main/index.ts)、
  协议单测 [test-remote.mjs](../../scripts/test-remote.mjs)。

**2026-09-20 缺陷修复与隔离 Electron 端到端证据**：会话消息直接寻址并以 `activate:false` 准备后台实例；abort 必须带合法 `runId` 并在主进程定向到对应 `AgentController`。新场景 `npm run test:live -- remoteroutes` 全绿：真实 Electron 远程服务完成 health / 鉴权 / 新建会话 / 定向消息 / runId abort；合成目标落在后台 runner `r2`，桌面视图保持在新会话；退出后本机 provider 证明确有目标请求且对应未完成流被关闭。整个场景不读取真实 `auth.json` / `models.json`、不访问上游，cost 0。自动层仍由协议单测覆盖 sessionId/runId 传递、非法 runId 拒绝及 RunnerRegistry 后台目标行为。

## 2. 安全边界（**已经成立，改动时不要放宽**）

- 远程服务**不默认启动**。
- token 只在**当前进程内存**中有效，**未写入**用户数据目录。
- 会话历史只能按**稳定 `sessionId`** 查找；网络请求**不能传任意文件路径**。
- API **不提供**任意 shell、任意文件读取、任意 Electron API 或调试端口。
- 会话列表与状态**不返回**会话文件绝对路径，只返回目录名等展示字段。
- Android 的写操作必须经过认证，并使用**显式的操作路由**。
- `POST /sessions/:id/messages` 必须只对 URL 指定的稳定 `sessionId` 发送，不能隐式切换桌面当前视图；必要时使用独立后台 runner，并服从同 cwd 忙碌冲突与 runner 数量上限。
- `POST /runs/abort` 的 JSON body 必须包含 `runId`，只中止该 runner；缺失或格式错误的目标在协议层拒绝。
- 当前 SSE **只转发**远程管理需要的事件，**不转发**内置浏览器状态与桌面 UI 模态事件。

## 4. 会话切片

> **口径修订（2026-09-18）**：旧方案「先补协议，再完善交互」与它自己的开发顺序（原型排在前）互相矛盾。
> 三方讨论后的切分是：**先冻结「连接状态机与能力边界」，协议细节可以后补**；
> 界面可以并行，但只能做到**「协议无关原型」**（见 [决策记录 §2.4](决策记录-三方意见对照-2026-09-18.md)）。

| 片 | 内容 | 规模 | 依赖 |
|---|---|---|---|
| **S0** | **先冻结「连接状态机与能力边界」**：连接态（未配置 / 已配置 / 连接中 / 在线 / 离线 / 被撤销）、授权态、能力可用性、断线语义、错误分类；`pairing` / `auth` / `transport` 定义成**抽象状态**，不绑定具体实现 | 0.5–1 天 | — |
| **S1** | 协议：配对（二维码 + 设备密钥）、撤销设备、权限分级；把 token 从「环境变量」升级为「设备凭证」 | 1.5–2 天 | 实现 S0 定义的抽象状态 |
| **S2** | 协议：WebSocket（可选）、TLS / 中继方案与本地网络配置说明 | 1–1.5 天 | S1 |
| **S3** | 页面设计与交互原型（六类页面 + 全部交互状态，**协议无关**） | 1–1.5 天 | **S0**（不依赖协议细节） |
| **S4** | 内部前台客户端：能真实连本机 API 的最小可用版（会话列表 / 对话 / 工具详情 / 停止） | 2–3 天 | S1、S3 |
| **S5** | 完整远程管理与正式分发：断线重连、双端交互、APK 签名与更新 | 2–3 天 | S4 |

**依赖关系（三方结论）**

- 可以**并行**，但界面只能做**「协议无关原型」**，它依赖的是 **S0 的状态机与能力边界**，不是协议细节；
- 原型里**不得**把「token 手填、局域网直连、单设备权限」这些临时机制画成正式流程 —— 那会被固化成产品；
- S4 之前必须先有 **S1 的设备凭证**落地，否则客户端要返工。

## 5. 验收

| 栏 | 标准 |
|---|---|
| 实现 | 远程服务**默认关闭**；不在 renderer、不用调试端口；新增路由有显式操作路由与鉴权 |
| 自动检查 | `typecheck` / `build` / `test:unit`；协议单测随新增路由扩展；`audit:refs` 干净 |
| 真实运行 | 隔离 Electron 实测远程 health / status / sessions / new / messages / abort；`remoteroutes` 覆盖鉴权、后台目标不抢桌面视图与定向取消；`test:packaged` 确认默认关闭且显式开启可启动 |
| 视觉验收 | 客户端页面截图（深 / 浅、窄屏 / 横屏、断线 / 未授权 / 无会话等状态） |
| 应用与包 | 解包产物里服务默认关闭、显式开启可启动；不泄漏 token 到用户数据目录 —— **已补齐（2026-09-19，实施-09 S4）**：`test:packaged` 断言默认不监听（`127.0.0.1:37892` → `ECONNREFUSED`，解包与便携版各一次）、**带 `YAN_REMOTE_ENABLE=1` 的第二个实例能起来**（`/health` 200、无 token 401、带 token 200），包里含 `/remote/v1/health`。token 不落盘仍由协议单测覆盖（它本来就不写盘，见 §2） |
| 剩余限制 | §3 未完成项如实列出；**不写「支持外网 / 支持任意设备」** |

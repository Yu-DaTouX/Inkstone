## 1. 总体策略

1. **新旧并存，逐屏切换（绞杀者模式）。** 新界面放在新目录，由设置项 `ui.version`（`v2` / `v3`，开发时也可用环境变量 `YAN_UI=v3`）选择外壳。两者共用同一个 store、IPC 与主进程服务。v3 达到功能对等之前，默认仍是 v2。**用户每天用砚开发砚**，任何时候都必须能一键切回 v2。
2. **先建地基，再做状态呈现，最后扩展。** 顺序：令牌与组件（P0）→ 运行模型与状态呈现（P1，价值最高）→ 外壳与会话（P2）→ 右侧面板与成果（P3）→ 能力与设置（P4）→ 扩展功能（P5）→ 手机端（P6）→ 清理收尾（P7）。
3. **每个阶段结束都可以发布。** P1 的运行注册表与注意力路由在 v2 外壳下也能用（托盘、通知、任务栏、迷你小窗），新外壳完成之前就能得到核心收益。
4. **一个运行模型。** 所有“谁在跑、处于什么状态”的判断只在主进程的运行注册表里做一次（§2），侧栏、提醒条、运行总览、托盘、手机只做投影。
5. **简洁是验收项。** 02 §3.3 的硬规则（两块区域、会话头 ≤3 个操作、输入框底部 ≤5 个控件、步骤默认折叠、只有一种强调）在每个界面工单里逐条核对。
6. **不改的东西**：pi 子进程与 JSONL RPC、会话文件格式、`YAN_DIR` 数据布局（只新增文件）、preload 白名单机制、离线 HTML 预览协议与 CSP、危险操作确认语义、两档权限语义。
7. **遵守仓库 AGENTS.md**：中文沟通；先读 `.local-docs/STATUS.md` 与 `DECISIONS.md`；不回滚别人的改动；热点文件小范围编辑；大测试先问；未经授权不提交、不推送。
8. **先让进行中的批次落地。** 2026-10-15 核对时，主工作区有 183 处未提交改动，分属 STATUS「进行中」的几个批次（后端缺陷修复与会话续接、使用向导、pi 原生操作、流式循环防护、会话统计等），并覆盖 v3 的多数热点文件。v3 工单要等这些批次提交或明确归属之后，从最新 `main` 拉 worktree 开工（WP-00 负责核对）。

## 2. 运行模型（架构核心）

### 2.1 为什么放在主进程
运行状态有多个消费者：渲染进程的侧栏状态点、提醒条与运行总览，托盘与任务栏，迷你小窗，系统通知，Android 远程端，Hermes。状态在主进程**只计算一次**，避免“每个视图各自推断状态”；渲染进程卡顿时，停滞计时也照样准确。

### 2.2 类型（建议放在 `src/shared/runs.ts`）
```ts
export type RunKind = 'session' | 'subagent' | 'scheduled' | 'review';
export type StallCause = 'no-output' | 'tool-silent' | 'retry' | 'rate-limit' | 'loop';
export type FailCause = 'model-error' | 'pi-exit' | 'tool-fatal' | 'host';
export type RunActivity = 'waiting-model' | 'thinking' | 'streaming' | 'tool' | 'compacting' | 'subagent';

export type RunPhase =
  | { kind: 'queued'; since: number; reason: 'followup' | 'concurrency' | 'scheduled'; at?: number }
  | { kind: 'running'; since: number; activity: RunActivity; tool?: { name: string; label: string; callId: string } }
  | { kind: 'needs-you'; since: number; request: { id: string; type: 'danger' | 'select' | 'confirm' | 'input' | 'editor'; summary: string } }
  | { kind: 'stalled'; since: number; cause: StallCause; detail?: string; retry?: { attempt: number; max: number; resumeAt?: number } }
  | { kind: 'failed'; at: number; cause: FailCause; errorKind?: string; message: string; seen: boolean }
  | { kind: 'stopped'; at: number; by: 'user' | 'host' }
  | { kind: 'done'; at: number; seen: boolean };

export interface RunSnapshot {
  runId: string;               // 运行实例 ID（每轮一个）
  code: string;                // 显示编号：S12 / S12·1 / T03 / R04（会话级稳定）
  kind: RunKind;
  sessionId: string; sessionPath?: string; projectId?: string;
  parentRunId?: string;        // 子 Agent
  title: string;               // 会话标题
  model?: { provider: string; id: string; label: string; thinking?: string };
  startedAt: number;
  phase: RunPhase;
  context?: { used: number | null; window: number; percent: number | null };
  costUsd?: number;
  counts: { tools: number; edits: number; errors: number };
}
```

### 2.3 pi 事件 → 运行状态（纯函数 `reduceRun(run, event, now)`）

| pi / 宿主事件 | 状态变化 |
|---|---|
| `prompt` 返回 `disposition: "queued"` / `queue_update` | 输入框队列更新；无运行时进入 `queued`（reason=followup） |
| `agent_start` | → `running`（activity=waiting-model） |
| `message_update`：`thinking_*` / `text_*` / `toolcall_*` | activity = thinking / streaming / streaming |
| `tool_execution_start` / `update` / `end` | activity = tool（记录工具名与目标）；end 后回到 waiting-model |
| `compaction_start` / `compaction_end` | activity = compacting / 恢复 |
| `auto_retry_start` | → `stalled`（cause=retry，attempt/max，resumeAt=now+delayMs） |
| `auto_retry_end` success / fail | → `running` / `failed` |
| 流式循环防护中止（本地开发中：宿主请求 `abort`，原生记录 `interrupted`） | → `stalled`（cause=loop）；自动续接后回到 `running`，不再续接时保持停滞并提示。宿主须在中止前标记原因，避免随后的 `agent_settled` aborted=true 被当成“用户停止” |
| `extension_ui_request`（select/confirm/input/editor） | → `needs-you`（type 同方法名） |
| 宿主危险确认（danger-guard 发起的 `danger.confirm`） | → `needs-you`（type=danger） |
| 上述请求得到答复 / 超时自动处理 | → 回到 `running` |
| `message_update` 的 `error` / 被归类的模型错误且不再重试 | → `failed`（cause=model-error，errorKind 来自 `shared/model-errors.ts`） |
| `agent_end` | 暂不结束（之后可能还有重试、压缩恢复、队列消息） |
| `agent_settled` aborted=false / true | → `done` / `stopped`（by=user） |
| pi 进程在运行中退出 | → `failed`（cause=pi-exit） |
| 子 Agent 事件（现有 `subagents.ts` 的推送） | 以子运行（kind=subagent，parentRunId）同样归约 |

> pi 文档明确：`agent_end` 之后仍可能继续工作，需要等 `agent_settled` 才能确定 pi 不会再自动继续。随包 pi 1.2.0 具备上表依赖的全部事件（00 §7 已核实）。

### 2.4 停滞监测与运行历史
- `stall-monitor`：每秒检查一次运行中的条目，按 02 §4.5 的阈值把 `running` 转为 `stalled`；有新事件就恢复 `running`。阈值与命令豁免列表来自设置。
- 运行历史：每次运行结束追加一行到 `YAN_DIR/runs/YYYY-MM-DD.jsonl`（运行快照 + 状态时间段 `[phase, from, to][]`），供运行总览页、运行时间线和用量统计使用。它只是索引，**会话内容仍以 pi JSONL 为准**。写入沿用现有的持久化约定（失败不覆盖、串行写）。
- 会话编号：`YAN_DIR/session-codes.json` 维护 `sessionId → S数字`，新会话递增；v3 首次启动时按创建时间给旧会话补号。编号不写进 pi 会话文件。

### 2.5 接口与推送
- IPC（新文件 `src/main/ipc/runs-ipc.ts`，经 `registrar.ts` 注册）：`yan:runs:snapshot`、`yan:runs:history(date|range, filters)`、`yan:runs:stop(runId)`、`yan:runs:markSeen(runId)`、`yan:runs:setStallSettings`。
- 推送：新增 `MainPush` 通道 `runs`，内容为增量 `{upsert: RunSnapshot[], remove: string[]}`，按 250ms 合并；状态类变化（进入 needs-you / failed / done）立即推送。
- 远程协议：`src/shared/remote-protocol.ts` 增加运行快照与增量，供 Android 与 Hermes 使用（WP-61）。
- 渲染进程：`state/runs.ts` 切片，以 `runId` 归一化；侧栏行与总览行各自只订阅自己的运行。

### 2.6 与现有代码的关系
现有 `push-routing.ts`、`session-runtime.ts`、`run-status.ts`、`subagents.ts`、`session-work-scheduler.ts` 都**保留**。运行注册表从同一条事件管道旁路订阅，不改动消息投影。`run-status.ts` 里与阶段相关的判断逐步改为读取注册表的结果，避免两套结论。

## 3. 前端架构

### 3.1 目录（新增，旧目录原地不动，WP-70 再删）
```

  app/           外壳：ShellV3、会话头（兼标题栏）、两栏布局、并排视图、路由、快捷键注册表、主题挂载、ErrorBoundary
  design/        tokens.css（生成）、主题、字体声明、图标、品牌标志

    runs/        运行状态选择器、RunsPopover、运行总览页、运行时间线、MiniWindow 视图
    session/     对话流、消息、步骤摘要与列表、确认/提问、子 Agent 行、停滞卡、分支、回退、大纲轨
    composer/    输入框、队列、「＋」菜单
```

`design/tokens.json` 是令牌唯一来源；`scripts/design/build-tokens.mjs` 生成 CSS 变量、Android `theme.ts` 与 MCP Apps 变量映射（02 §5.10–5.11）。

### 3.2 外壳切换
`main.tsx` 只决定加载哪个外壳：`ui.version === 'v3'` 时动态导入 `app/ShellV3` 与 `design/index.css`；否则导入现有 `App` 与现有样式。**v3 不加载任何 v2 样式文件**，v2 也不加载 v3 样式。现有全局 CSS 的导入位置需要先移到 v2 外壳内部（WP-20 的第一步）。

### 3.3 状态与路由
- 继续使用 zustand；新增 `ui` 切片保存 `{ route: { name, params }, back: Route[] }` 与侧栏、面板、浮层的开合。路由与 `location.hash` 双向同步，供深链接使用。不引入路由库。
- 选择器细粒度订阅；侧栏会话行、总览行各自订阅自己的数据。

### 3.4 样式规则
- 级联层：`@layer reset, tokens, base, primitives, patterns, features, utilities;`。
- 控件外观只来自 `ui/` 与 `patterns/`；`features/` 只写版面。
- 不引入 CSS-in-JS 与 Tailwind。现有 `lint-css`、`css-layer-check`、`check:css-budget`、`check:motion` 按新层级更新规则（WP-01）。
- React Aria Components 提供交互状态的 `data-*` 属性，样式直接选择这些属性。

### 3.5 组件工作台
建议采用 Storybook（仅开发依赖，Vite builder）：故事与组件同目录；`addon-a11y` 做自动可访问性检查；`play` 函数做交互测试；`npm run storybook` 与 `npm run test:stories`；不打进产品包（待定决定 D5）。

### 3.6 现有能力的复用
只换界面、逻辑复用：`push-routing`、`session-runtime`、`split-view` 系列、`resource-owners`、`workspace-key`、`outline-turns`、`at-query`、`slash-query`、`attachment-files`、`interaction-state`、`shared/visual-blocks.ts` 的解析、`model-errors`、`checkpoints`、`file-refs`、`html-artifact-preview` 全链路、`virtua`、xterm 配置；以及本地已有的 `lib/host-actions.ts`（命令面板动作）、`main/terminal-status.ts` 与 `index.ts` 里的任务栏信号、`main/schedule-service.ts`（开发中）、`resources/pi-extensions/native-session-bridge.js`（开发中）、`settings/onboarding-state.ts`（开发中）、`shared/stream-loop-detector.ts`（开发中）。

5. 截图：浅/深 × 标准宽度/窄窗口，使用新文件名，不覆盖旧图。
6. 对照 02 §3.3 的简洁规则逐条核对（区域数、操作数、默认折叠、强调只有一种）。

8. 涉及性能的工单附测量对比（与基线同类的运行方式）。
9. 更新 CODE_MAP 中对应条目与 `.local-docs/STATUS.md`。
10. 交付说明写明：改了什么、跑了什么、**没跑什么（NOT RUN）**、剩余限制。

### 9.2 证据规则（沿用仓库约定）

## 10. 风险

| 风险 | 应对 |
|---|---|
| 主工作区有大量未提交的进行中批次（2026-10-15 核对时 183 处），与 v3 的热点文件重叠 | WP-00 先核对，等这些批次提交或明确归属；v3 一律在从最新 `main` 拉出的 worktree 中进行 |
| 简洁过头，状态又变得“素淡” | 状态点 + 提醒条 + 停滞计时是硬性要求（02 §3.4）；WP-11 验收里专门检查需要关注的状态是否一眼可见 |
| 功能越加越多，界面重新变挤 | 每个界面工单核对 02 §3.3 的硬规则；新增入口优先放进「＋」「更多」或设置 |
| 范围过大，长期处于半成品 | 分阶段、每阶段可发布；P1 先在 v2 下交付核心收益；`ui.version` 随时切回 |
| 多个会话并行修改同一热点文件 | §7.2 所有权表 + STATUS 登记 + 新 IPC 放新文件 |
| 性能回退 | WP-00 先采集基线；每个阶段复测；行级订阅与按需加载 |
| pi API 变化 | 运行注册表只依赖文档化事件；升级时跑注册表测试；MCP Apps 路线 A 依赖的扩展 API 先由 PoC 核实 |
| MCP Apps 规范仍在演进 | 以 `2026-01-26` 稳定版实现，draft 功能放到后续版本 |
| 新通道带来的安全面（App、深链接、全局快捷键、无人值守的定时任务） | 每个通道写安全清单并在工单验收中逐条核对；深链接只导航；定时任务不会替用户允许 |
| 视觉过于接近参照产品 | 只借布局与克制；不用 Claude 的颜色、字体、标志（02 §3.2）；WP-71 记录差异 |
| 字体渲染差异（Segoe UI Variable 在 Windows 10 缺失） | 字体栈回退到 Segoe UI；WP-01 实测 |
| Windows 通知与任务栏 API 差异 | AttentionService 设平台适配层；macOS/Linux 留空实现，不宣称支持 |
| 用户日常开发依赖砚本身 | v3 默认关闭直到 P2 可用；任何时候都能切回 v2 |

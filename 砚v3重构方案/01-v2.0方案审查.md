# 01 · 《Inkstone UI 升级参阅方案 v2.0》审查

> 审查对象：`InkstoneUI升级参阅方案v2.0.md`（基准提交 `e109cc6`，2026-10-13）。
> 审查日期：2026-10-15。审查依据：用户 2026-10-15 的四项确认（见 [00-导读与决策](00-导读与决策.md) §2），公开仓库的产品/架构/代码地图文档，以及本轮实际访问到的外部资料（见本文 §4）。
> 按用户要求，本审查**不以现行设计规范为准绳**，没有读取 `docs/DESIGN_SYSTEM.md`、`BRAND.md`、样式表或设计脚本。

---

## 1. 结论（一句话）

v2.0 是一份合格的**只读审计计划**，证据纪律和安全边界值得保留；但它没有回答这次真正的问题：重做一个功能完整、先进、美观、舒适的砚。它只给审计流程，不给设计；它把现行设计当作权威，把“最小改动”当成目标；它漏掉了用户最在意的痛点（长任务与并行运行时**看不见 Agent 的状态**）；参考资料部分还有三处事实已经过时。v3.0 保留它的安全与证据内核，其余部分重写。

## 3. 主要问题

### 3.1 目标错位：审计计划交不出设计
v2.0 的交付物是“单份审阅报告”，并明确禁止改代码、禁止新建 RFC、禁止设计提案落地（v2.0 §8.1、§10）。按它执行，最好的结果是一份发现清单；用户现在要的是**完整的新设计和完整的重构计划**。两者不是同一个工作。

### 3.2 锚定旧设计，与“不看现有设计”的要求相反
v2.0 把 `docs/DESIGN_SYSTEM.md` 文首的“方向 E”当作冲突时的最高依据（§2.5、§3 I-09），并把“同等收益下优先修改现有组件”作为决策原则（§0）。用户本次明确要求**不受现有设计方案约束**。v3.0 的做法是：保留产品事实、功能、约束和名字，替换整个视觉世界与组件体系（理由见 02 §1）。

### 3.3 没有任何设计内容
通读全文，v2.0 没有给出：信息架构、导航模型、视觉语言（色彩/字体/间距/动效）、组件规范、状态词汇、交互与键盘模型、文案规范、移动端设计、空状态与引导。对“先进、美观、舒适”三个要求，它没有一条可执行的回答。

### 3.4 优先级失衡：P0 是一个嵌套按钮
v2.0 的 P0 是 `Tab` 组件里 `<button>` 套 `<span role=button>`（I-01），以及设计文档多版本并存（I-09）。这两件事值得修，但它们不是这款产品最重要的问题。

**漏掉的核心问题：** 砚的主要用户是同时跑多个会话与子 Agent 的重度用户（已确认）。用户明确把“过于素淡，长任务里看不清 Agent 在做什么、卡在哪”选为**最不能接受**的结果。v2.0 通篇没有涉及运行总览、停滞识别、注意力路由（谁需要我）、跨会话状态汇总，这正是 v3.0 的签名能力（02 §4「运行状态的呈现」）。

### 3.5 参考资料的三处事实已过时（本轮已实测更正）

| v2.0 判断 | 本轮核实（2026-10-15） | 影响 |
|---|---|---|
| Claude Storybook 站“直接访问失败”，证据等级 D | **可以访问**。站名「Claude Design System (CDS) - Storybook」，中文界面。内容：Foundations（Colors & Surfaces、Border Radius、Heights & Sizing、Shadows & Elevation、Typography & Align、Icons & Glyphs、Motion Tokens）、Components（Chat Composer、Message Bubbles、Thinking Accordion、Buttons & Controls、Segmented Control、Attachment Tiles、Code Block & Copy）、Motion Lab（Grapheme Reveal、Thinking Quiet Dots、Spring Physics Presets）。该站自称“Verified from Claude.app / REA Extracted Tokens 100% Fidelity”，**这是第三方复刻站的自述，未经核实**，只能当作工艺参考 | v3.0 吸收其中可迁移的**工艺规则**（等宽数字、暗色字重补偿、图标基线、标题 balance/正文 pretty、长标识符断行、时长与缓动阶梯），不吸收 Claude 的外观（02 §5.9） |
| Figma《MCP Apps for Claude》“未取得原始画板”，不可做设计比对 | 社区页可访问：Anthropic 设计团队出品，UI kit v1.1，CC BY 4.0，画板需登录。但**同一套指导已以文字发布**在 Anthropic 文档《MCP Apps design guidelines》《Blend your MCP App with Claude's theme》《Supersede older widget instances》：三种显示模式及其约束、移动端规则、完整的样式变量表（含浅/深色取值） | 宿主侧的显示模式、尺寸、主题变量、加载态、全屏返回位置等不再需要“猜”，可直接据此设计（02 §12） |
| pi 原生 MCP 是否把 UI 元信息传到砚宿主“待验证” | pi 官方 `docs/mcp.md` 明确写道：MCP Apps 资源（`ui://` 或 `text/html;profile=mcp-app`）**会被省略，因为 pi 不渲染它们**。本地方案合集 02 在 2026-10-13 已得出同样结论（“pi 上游阻塞”），见 [00 §8](00-导读与决策.md#8-与本机仓库的核对2026-10-15) | 目前任何 MCP App 都无法经 pi 原生 MCP 到达砚。宿主必须自建 App 桥（02 §12.2、03 WP-52 给出三条路线与推荐） |

另外：v2.0 只引用了 MCP Apps 规范 `2026-01-26` 版。规范仓库另有 `draft`，比稳定版多出 `ui/download-file`、`ui/notifications/request-teardown` 等方法，并写入了 `sampling/createMessage` 与 App 自带工具（App-provided tools）。宿主设计应以稳定版为准，同时跟踪 draft（02 §12.3）。

### 3.6 流程过重，拖慢一个人的项目
九段式报告结构、每条发现 12 个字段、四级证据等级、`现象→证据→期望→复现→影响→最小修复→备选→验证→是否建议` 的固定链条……对团队审计是合理的，对“个人开发者 + 多个 Agent 轮流开发”的仓库（AGENTS.md）是负担，会把产出变成文书。v3.0 把证据要求收进每个工单的“验收与证据”一栏，只要求能复现、能截图、写明没跑什么。

### 3.7 范围与新决定冲突
v2.0 明确排除“市场、账号系统、插件注册中心、跨设备 Host”（§6 C4），并沿用“精简方向”。用户已确认**全面扩展**：要成为完整的 Agent 工作站，纳入代码评审/PR、定时任务、跨设备同步等。v3.0 的应对不是恢复旧模块，而是**一个运行模型承载所有扩展**（02 §2 原则 2、03 §2），避免重蹈“多套任务状态机”的覆辙。

### 3.8 几处技术判断需要修正

| v2.0 线索 | 问题 | v3.0 做法 |
|---|---|---|
| I-02 `WidgetBlock` 高度上限 560px + 内层滚动 | 把“内嵌滚动”当成可接受的体验问题去测；MCP Apps 指南的结论是**内联不允许嵌套滚动**：内容自适应高度、宿主设上限、超出则提供“展开到全屏” | 统一的「成果视图」尺寸模型：内联自适应（上限按窗口高度计算），超限显示渐隐与“展开”，全屏关闭后回到原滚动位置（02 §11） |
| I-03 状态键含 `html` 哈希 | 内容一变身份就变，编辑、恢复、重挂载都会丢状态 | 身份 = `(sessionId, messageId, partIndex)`，可叠加服务器下发的版本键（参照 supersession 模式），同一内容多实例时只保留最新一个可交互（02 §11.3） |
| I-04 消息桥 | 继续沿用 `window.postMessage` 逐条校验 `source` | 握手后改用 `MessageChannel` 专用端口，按实例绑定；schema 校验、速率与体积上限、实例销毁即关闭端口（02 §12.5） |
| I-08 inline 与 expanded 是否共享状态 | 留作开放问题 | 明确规定：同一实例**移动而不重建**；做不到移动时（跨窗口），经桥接做状态转移，并把“转移失败”作为可见的降级状态（02 §11.2） |

### 3.9 Shaders ASCII：从“可选实验”降为“暂不纳入”
v3.0 选定的视觉方向是简洁（参照 Claude 新版桌面端，02 §3），字符画着色器与之没有功能联系，也违背“只有一种强调、不加装饰”的原则；WebGPU 常驻着色还有 GPU 成本与降级负担。v3.0 不纳入；将来若要做品牌时刻，只考虑离线生成的静态资产（v2.0 的 D1）。

## Platform

web

（桌面端为 Electron 渲染进程，属 web 技术栈；Android 远程端为 React Native 应用，与桌面共用同一套设计语言。）

## Users

- **主要用户（已确认）：开发者与重度 Agent 用户。** 每天长时间开着砚：用 pi 写代码、同时跑多个会话和指定模型的子 Agent、看工具过程、审阅改动与成果、旁边开着文件/终端/浏览器。非开发者也应能上手，但不是首要优化对象。
- 界面以中文为主，提供英文（仓库：README_EN、两份 i18n）。
- 同一用户离开电脑时，用 Android 远程端看进度、回消息、回答提问、查看成果；任务仍在电脑上执行（仓库）。

## Product Purpose

砚是基于官方 pi 的图形 Agent 客户端：选择模型、交代任务，直接查看工具过程与结果（仓库 README，标语「让想法成形」）。

成功的标准：用户能同时运行长时间、多路并行的 Agent 工作，并且**随时知道每个 Agent 在做什么、卡在哪里、改了什么**，在恰当时刻介入：批准、插话、停止、回退、分叉。

## Positioning

- **pi 是引擎，砚是驾驶舱。** 模型循环、上下文、压缩、工具、技能由官方 pi 子进程（JSONL RPC）负责；砚负责呈现、调度、授权与宿主资源（文件、终端、浏览器、预览），不复制 pi 的循环（仓库）。
- **模型自由。** 服务登录、API Key、兼容端点；Claude Code 订阅经 pi-claude-bridge；子 Agent 可指定不同模型（仓库）。
- **本地优先。** 会话与设置保存在用户电脑上；无自有账号系统（仓库）。
- **电脑执行，其他设备参与。** 手机、Hermes 插件、砚对砚互通都是对电脑上运行的观察与控制，不独立运行 Agent（仓库）。
- **可逆。** 会话树（分支/fork/clone）、发送前影子 Git 检查点与代码回退（仓库）。

## Operating Context

- 主力平台 Windows 11 x64；macOS/Linux 是已确认目标但未交付；iOS 尚无工程（仓库）。
- 典型流程：选项目目录 → 新会话 → 输入（`@` 文件、贴图、语音转写、斜杠命令/技能/提示模板）→ 流式文字 + 工具调用 → 危险操作审批 → 审阅 diff / 成果 / HTML 预览 / 结构化图表 → 必要时回退或分叉。
- 并行：分屏磁贴同时显示多个会话；后台会话继续运行；子 Agent 全应用并发上限 10（仓库）。
- 工作面板：文件树与预览（含 docx/xlsx/pptx/pdf 文字预览）、内置浏览器（WebContentsView）、多个终端（node-pty）、磁贴布局，资源归属会话（仓库）。
- 长会话：2,000 条以上消息的历史需要流畅滚动与导航（仓库性能夹具）。
- 其他入口：Ctrl+K 会话与正文搜索、插件市场（砚/pi 两页）、MCP（pi 原生 `mcp.json` + 旧宿主兼容层）、上下文与压缩控制、用量与费用、数据备份与迁移、Android 配对、Hermes 外部控制、砚对砚互通（仓库）。

## Capabilities and Constraints

**现有能力（仓库，源码层面存在，不代表全部经过真实验收）：** 会话（项目/目录、历史与分支、后台运行、搜索、归档置顶、流式与工具详情、插话/排队、书签）；模型（登录、API Key、自定义端点、思考档位、收藏、主/子分别记忆）；子 Agent（指定模型、独立上下文、只读/worktree 隔离、停止、恢复历史）；两档权限（「自动批准」危险操作请求批准 /「不受限制」）；工作面板；成果（附件、文件引用、离线隔离 HTML 预览、`yan-chart`/`yan-stats`/`yan-cards`/`yan-record`/`yan-flow`/`yan-steps`、Mermaid、`yan-widget` 交互小部件）；检查点与代码回退；pi 原生压缩、skills、MCP、扩展、Codemode；插件市场；语音输入（whisper.cpp）；生图通道；电脑操作（windows-mcp）；用量统计；备份校验；Android 远程端；Hermes；砚对砚。

**扩展范围（已确认，2026-10-15）：** 「全面扩展」——目标是完整的 Agent 工作站，在现有能力之上纳入代码评审/PR、定时任务、跨设备同步等。

**本地开发中（未提交，2026-10-15 核对本机仓库）：** 定时任务服务（`yan schedule`，每天 / 每周 / 间隔 / 一次）、pi 原生操作桥（会话树导航、热重载等）、流式循环防护（命中重复输出时中止，同一任务最多自动续一次）、六步首次使用向导。

**约束（仓库）：**
- 保留 TypeScript、React、Electron、官方 pi、React Native；个人开发者的维护成本是选型条件；不以换语言或换应用壳作为性能结论。
- 渲染进程只经 preload 白名单与 IPC 使用宿主能力；后台事件必须核对会话归属。
- 现有 HTML 成果预览的离线 CSP 不放宽；新的 MCP Apps 通道必须独立隔离。
- pi 原生 MCP 不渲染 MCP Apps：`ui://` / `text/html;profile=mcp-app` 资源被 pi 省略（pi 官方 `docs/mcp.md`）。砚不为此新建或扩充自己的 MCP 连接（本地方案合集 02 的原则）；旧宿主 MCP 已收口到 pi 原生（方案合集 06）。
- 手机不独立运行完整 Agent，不复制电脑的任务状态机。
- 先在 Windows 适配和验收；不提前扩建全平台空壳。

**未决（需用户决定，不得由实现者自行发明）：**
- 跨设备同步的机制（设备间直连/中继，还是引入云端）。现行文档写明「不提供跨设备自动同步」「云端多租户和自有账号系统不属于当前目标」，与「全面扩展」存在张力。DECISIONS 里“砚自有账号与跨设备同步保持未接入”（2026-09-27 前）由 2026-10-15 的「全面扩展」取代，待 WP-00 写入 DECISIONS。
- 定时任务在电脑休眠/关机时的行为。
- macOS/Linux 交付时间；iOS 是否启动。

## Product Principles

1. **状态永不隐身。** 任何运行中的 Agent 都要说清：正在做什么、在等谁、卡了多久、改了什么。素淡到看不见状态是最不能接受的失败（已确认）。
2. **一个运行模型，多个视图。** 会话、子 Agent、定时任务、评审、远程端都投影自同一套运行与事件；扩展功能不得再造一套状态机。
3. **pi 负责思考，砚负责看见与掌控。** 新能力优先适配 pi 原生实现；宿主只做 pi 做不到的部分。
4. **强大但不铺满。** 功能全面，但按需展开：默认视图服务当前任务，深层能力在需要时出现。
5. **默认可逆。** 改动前留检查点，分叉代替覆盖，危险操作先问。

## Accessibility & Inclusion

- 键盘可完整操作、深浅主题、窄窗口可读（仓库现行约束）。
- Windows 显示缩放 100% / 125% / 150%；中英混排与 CJK 排版质量。
- 目标 WCAG 2.2 AA 对比度与焦点可见性（推断，来自 v2.0 方案的验收矩阵，未经用户单独确认）。
- 遵从系统「减少动态效果」设置。

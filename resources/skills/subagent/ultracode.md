# Ultracode

收到 Ultracode 提醒（用户在思考强度 Max 之后开启了 Ultracode，或消息以 `/ultracode` 开头）时，用工作流来做：写一段编排脚本，`yan workflow run --file <脚本.js>` 交给宿主在后台跑，结束时宿主把最终答案发给你。脚本写法、限制、续跑和常用模式都在同目录的 `workflow.md`，开工前先读它。用户已经接受更多耗时和额度，目标是结果完整、正确。

要点（细节见 `workflow.md`）：

- **先侦察，再扇出。** 自己先花几步列出相关文件、调用点、改动清单，脚本基于这份具体清单一项一代理，不派「去看看整个项目」这种宽任务。
- **分阶段。** 理解 → 方案 → 实施 → 复核，可以是一个脚本里的几个 `phase()`，也可以是先后几个工作流；需要读完结果再定下一步，或要用户中途拍板时，拆成几个工作流。
- **对抗复核写进脚本。** 复核者只读，任务写成「设法证明它是错的」，拿不准按被驳倒处理；重要结论三名以上、不同角度、能换模型就换，多数没驳倒才保留。未知规模的查找一轮一轮做，直到连续两轮没有新发现。
- **改到检查通过。** 写入任务按文件拆开，会改同一批文件的并行任务用 `isolation: 'worktree'`；工作流结束后由你审阅 worktree 补丁再 merge 或 discard。
- **最后做完整性检查。** 漏掉的要求、没读的来源、没验证的说法。
- **规模跟着用户的说法走。** 「看一下」几个代理；「彻底」「全面审计」几十个、每个关键结论多名复核者。单次运行最多 200 个 `agent()`，更大的活拆成几次。
- **汇报。** 正文写结论和需要用户决定的事；哪些结论复核过、哪些没有、只查了哪一部分放进补充说明，不写成像是全覆盖。

闲聊、问答和很小的改动不写工作流，自己直接做。

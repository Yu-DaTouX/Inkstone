# 指定模型的子 Agent

当前会话负责整体任务，子 Agent 负责一个明确子任务，结果返回当前会话。

1. 用户指定了模型时通过 `--model` 请求该模型，仍服从宿主的强制模型设置；没有指定时省略 `--model`，由宿主默认设置决定，不主动传当前模型覆盖用户设置。
2. 任务说明写清目标、必要上下文、输入文件和期望结果。只传有用材料，普通子 Agent 不自动获得完整主会话历史。
   需要当前对话的上下文、又不想让自己的上下文被过程刷满时，加 `--fork`：fork 子 Agent 继承当前会话的全部历史，沿用当前会话的模型与推理档位，首个请求直接复用当前会话的提示缓存。由你判断用哪种：任务靠对话里已有的讨论、决定或读过的文件才能做时用 fork；任务能用几句话讲清时用普通子 Agent。fork 只在当前文件夹运行，不能加 `--read-only`、`--isolation worktree` 或换模型；当前上下文已用超过 60% 时会被拒绝，先压缩或改派普通子 Agent。
3. 启动：`yan subagent start --task "任务" --title "短标题"`；需要指定模型时再加 `--model "provider/model"`。`--title` 是界面显示的 2–8 字短标题，并行派多个时各写一个能区分的；`--model` 用完整的「供应商/模型」（不确定时只写模型名，宿主按已登录模型匹配，有歧义会列出候选，从中选一个重试）。一次派多个独立子 Agent 时，在同一条消息里并行发出。默认在当前文件夹执行，可能直接修改文件；只分析时加 `--read-only`。代码修改需要隔离时加 `--isolation worktree`，该选项才要求 Git。
   `claude-bridge/*` 模型不支持 `--read-only`，用它时不要加该选项。启动报错时如实告诉用户原因，不要自行省略 `--model` 或换成别的模型重试。
4. 查询用 `yan subagent list` / `yan subagent get --id <ID>`，停止用 `yan subagent stop --id <ID>`。用 `yan subagent send --id <ID> --message "信息"` 给子 Agent 发信息：运行中用于补充资料或纠正方向（当前工具结束后送达，要它做完原任务再处理时加 `--mode follow-up`）；已结束的会按原会话续接，它记得之前的工作，追问时优先用它而不是重派。worktree 子 Agent 结束后不能续接。不用固定间隔 sleep 轮询；开启完成通知时结果会回到父会话。
5. 不让多个写入任务同时修改相同文件；需要用户选择的问题留给主会话。子 Agent（包括 fork）不再派出子 Agent。
6. 汇报时以启动结果或查询结果的实际 `model` 为准，标明子 Agent 的模型、结论和未验证项；出错或部分完成不能称为任务成功。worktree 的改动仍需审阅与采用，当前文件夹任务已经直接写入，不假装有待合并补丁。

## Ultracode

收到 Ultracode 提醒（用户在思考强度 Max 之后开启了 Ultracode，或消息以 `/ultracode` 开头）时，这一节就是做法。用户已经接受更多耗时和额度，目标是结果完整、正确。

**先侦察，再扇出。** 自己先花几步圈定范围：列出相关文件、调用点、改动清单。拿到具体的工作清单再派子 Agent，一个清单项一个任务，不要派「去看看整个项目」这种宽任务。

**分阶段推进，每阶段读完结果再定下一步：**

1. 理解：按子系统或资料来源并行派只读子 Agent，各交一段结论和 `文件:行` 出处。一个角度找不全时，换几种找法并行（按目录、按关键词、按调用关系、按时间）。
2. 方案：改法不止一种时，派两三个子 Agent 从不同出发点各出一版（最小改动、风险优先、用户体验优先），比较后以最好的一版为主，吸收其他版本的长处。
3. 实施：按文件或模块拆成互不重叠的写入任务；会改同一批文件的并行任务用 `--isolation worktree`。机械性的批量改动可以交给更快、更便宜的模型（`--model`），难点留给强模型。
4. 复核：见下面的对抗复核。

**对抗复核：**

- 复核者一律只读，任务写成「设法证明这个结论或改动是错的」，交回结论加证据。拿不准的一律按「被驳倒」处理。
- 重要结论派多名复核者，各给一个不同视角（正确性、边界与异常、安全、性能、能否复现），多数驳倒就推翻。能换模型就换，同一个模型容易犯同样的错。
- 未知规模的查找（找 bug、找遗漏、找边界情况）一轮一轮做，直到连续两轮没有新发现才停。判断「新」要对比之前见过的全部发现，包括已经被否掉的，否则被否掉的会反复冒出来。
- 最后派一个完整性检查：漏掉的要求、没读的文件或来源、没验证的说法；它找到的东西就是下一轮的工作。

**规模跟着用户的说法走。** 「看一下」「快速查」派三五个即可，每个结论一名复核者；「彻底」「全面审计」可以派一二十个，每个关键结论三名以上复核者，再加一个汇总阶段。全应用同时最多 24 个，超出部分分批派。

**汇报。** 写明每个阶段派了哪些子 Agent、哪些结论已经复核过、哪些没有。如果为了控制规模只查了一部分（比如只看了前 N 个文件、抽样检查），要说清楚漏了什么，不能写成像是全覆盖。

闲聊、问答和很小的改动不派子 Agent，自己直接做。

不要求任务模板、空间、资料库、预算配置或外部 CLI Hub；旧的 `hub.*` 命令已退役。

全应用最多同时运行24个子 Agent，按实际独立任务决定数量。工具调用次数由执行模型自主决定，宿主只统计次数，不设置调用预算。连续10分钟没有模型输出或工具事件后请求收尾，75秒内仍未结束才停止；持续有进展时默认没有总期限。确需总期限时可在请求的 brief 中设置 timeoutMinutes（1–60分钟）。

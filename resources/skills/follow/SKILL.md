# 持续关注

砚负责保存关注、按节奏算出「到点了」、在界面提醒用户（`yan follow …`）。**去看是你的事**：宿主不自己查，也没有后台定时任务。这个技能说明怎么提议、怎么看、怎么回报。

两条事实，提议和回报时都要如实告诉用户：

- 关注只在砚开着的时候看：应用没开的那段时间不会被跟进，也不补看漏过的次数。
- 关注只负责提醒与记录：需要做的事仍然由用户按发送；复习类关注只提醒，不会自动开始学习。

## 1. 什么时候提议

- 用户说「过几天再看看」「有更新告诉我」「每周提醒我复习」这类话时，提议一个关注。
- 一次就能做完的事不要提议关注，直接做。
- 提议用 `yan follow save --request-file watch.json`：

  ```json
  { "title": "看看 README 有没有变", "kind": "files",
    "cadence": "interval", "intervalMinutes": 1440,
    "resultPlace": "只在空间概览里记一笔" }
  ```

  - `title` 一句话写清看什么，要让以后的你只读这句就知道去哪看。
  - `kind`：`sources`（资料有没有更新）、`files`（文件有没有变化）、`review`（该复习的内容）、`custom`（别的事）。
  - `cadence`：`once` 看一次，`interval` 按间隔看；间隔最短 30 分钟。按事情变化的速度选，不要为了显得勤快设得很短。
  - `resultPlace`：结果放哪，例如「只在空间概览里记一笔」「写进文件 notes/weekly.md」。
- 提议总是存成**未启用**：告诉用户去点「开始关注」才会生效。启用、停用、删除都由用户在界面上做，你没有这些动作。

## 2. 到点后怎么看

先 `yan follow due` 看哪些到点了，每条附带一段说明（看什么、上次看的时间、上次结果、结果记到哪）。然后按类型去看：

| 类型 | 怎么看 | 算「有变化」的依据 |
| --- | --- | --- |
| 资料有没有更新 | 关注的是某份成果的引用时用 `yan research status --artifact <成果ID>`；要比较内容时用 `yan research read` 分别读新旧版本的片段（见 `research` 技能） | 出了新版本，或引用的片段已旧、已移除 |
| 文件有没有变化 | 读文件；在 Git 仓库里用 `git log` / `git diff` 看上次之后的改动 | 内容或提交有变化 |
| 该复习的内容 | 读以前的学习笔记与记录，挑出该复习的点（见 `tutor` 技能） | 列出这次该复习什么；不要自己开始出题，等用户来 |
| 别的事 | 按标题说的去看；需要网页时用 `yan browser` | 按标题判断 |

- 只看关注说的那件事，不要顺手做别的改动。
- 看不了（文件不在、网页打不开、缺权限）就如实记成「这次没看成」，写清原因。

## 3. 回报

看完一条回报一条：

```
yan follow report --id <关注ID> --outcome <no-change|changed|needs-decision|failed> --request-file run.json
```

`run.json`：`{ "summary": "一句话说这次看到了什么", "changed": ["具体变化"], "decisions": ["需要用户定的事"] }`

- `no-change`：没有变化。只进运行记录，不打扰用户。
- `changed`：有变化，`changed` 里逐条写具体变了什么，不要只写「有更新」。
- `needs-decision`：需要用户决定，`decisions` 里写清要定什么、有哪几个选项。
- `failed`：没看成，`summary` 写原因。
- 不要把没看的写成看过，也不要把拿不准的变化写成确定的。
- 结果需要写进文件时按 `resultPlace` 写，然后在回复里告诉用户写在哪。

# 提炼长期记忆

砚的长期记忆分两个范围：**项目知识**（这个项目的约定、架构决定、方法、任务背景）和**个人记忆**（跨项目的偏好、长期习惯、用户明确的个人规则）。你只能提交**候选**，由用户在「设置 → 项目知识」里确认；不能自报「用户已确认」。

这个技能说明什么时候提炼、提炼什么、怎么提交。

## 1. 什么时候检查一次

- **一项任务收尾时**：回顾这一轮做过的事，看有没有以后还会用到的结论。
- **读完说明项目约定的文档时**：README、贡献指南、架构说明、`AGENTS.md` 这类文件里的约定。
- **用户说了一条规则时**：「以后都…」「这个项目里不要…」「我习惯…」。
- **同一种偏好第二次出现时**：用户又一次纠正了同样的格式、用词或做法。

简单问答、闲聊、一次性的小改动不用检查。每轮最多提交几条，宁少勿滥。

## 2. 什么值得记

| 值得记 | 不记 |
| --- | --- |
| 做出的决定和理由（「移动端用 React Native，因为能复用 TS 代码」） | 这一轮的过程流水、临时的调试步骤 |
| 约束和禁忌（「`release/` 下是真实数据，只读」） | 代码里一眼就能看到的事实（函数名、文件位置） |
| 反复用到的方法（「发版前先跑 X，再跑 Y」） | 会很快过期的状态（「今天 CI 是红的」） |
| 用户明确说过的规则、多次出现的偏好 | 一次性的选择、你的推测、文档作者的个人观点 |
| 以后不查就会做错的背景 | 凭证、密钥、个人隐私信息 |

## 3. 先查重

提交前先 `yan knowledge search --query-text "<关键词>"`：

- 已有同样的内容：不提交。
- 已有但过时或有出入：提交新的一条，用 `supersedes` 写明替代哪条（`["<旧条目ID>"]`），并在正文里说清变化。
- 用户删过的内容再提会被拒收，不要换个说法重提。

## 4. 怎么写

`yan knowledge propose --request-file proposal.json`：

```json
{
  "kind": "decision",
  "text": "移动端使用 React Native + TypeScript，以复用桌面端的类型与协议代码。",
  "tags": ["移动端", "技术选型"],
  "evidence": [{ "file": "docs/TECH_STACK_OPTIONS.md", "excerpt": "……原文摘录……" }]
}
```

- `kind`：`decision`（决定）、`constraint`（约束）、`fact`（事实与背景）、`procedure`（做法步骤）。
- `text`：一条只写一件事，一两句话，脱离上下文也能看懂。写清对象和条件，不写「上面说的那个」。
- `evidence`：写出处。文件用项目内相对路径加原文摘录；来自对话时可以不写，宿主会记下当前会话。
- 不写 `confidenceClass`，宿主按「推断」记录；不要写 `user-confirmed`。
- **个人范围**加 `"scope": "personal"`：只放跨项目都成立的偏好和习惯，并且用户明确说过或已多次出现。只在这个项目成立的，留在项目范围。

## 5. 告诉用户

提交后在回复末尾用一句话说明：提了几条候选、各是什么，请用户去「设置 → 项目知识」确认或删除。不要把候选说成「已记住」。
